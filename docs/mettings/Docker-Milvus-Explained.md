# Docker 与 Milvus 部署详解（小白友好版）

## 一、核心概念解释

### 1.1 镜像（Image）vs 容器（Container）

**镜像 = 模板，容器 = 实例**

```
镜像（Image）                 容器（Container）
┌─────────────────┐           ┌─────────────────┐
│ 就像一个蛋糕模具 │    运行    │  从模具做出来的蛋糕 │
│                 │ ───────→  │                 │
│ 可以反复创建     │           │ 独立的实际运行体  │
│ 不会变化        │           │ 可以修改、删除   │
└─────────────────┘           └─────────────────┘

# 例子
镜像: milvusdb/milvus:v2.6.16   （官方发布的安装包）
容器: docker-milvus-standalone   （从镜像运行的实例）
```

**为什么需要这个区分？**
- 一份模具可以做出多个蛋糕
- 一个镜像可以启动多个容器
- 修改蛋糕不影响模具本身

### 1.2 端口映射（Port Mapping）

**为什么需要端口映射？因为容器是隔离的。**

```
你的电脑（宿主机）                    Docker 容器内部
┌─────────────────────┐              ┌─────────────────────┐
│                     │              │                     │
│  应用想访问 Milvus   │              │   Milvus 服务        │
│        ↓            │   19530      │   监听 19530        │
│  浏览器:8501         │ ←──────────  │                     │
│  API:8000            │              │                     │
│                     │              │                     │
└─────────────────────┘              └─────────────────────┘

"19530:19530" 的意思是：
  宿主机端口:容器内部端口
  把容器的 19530 映射到宿主机 19530

类比：医院挂号柜台（外部）→ 内部诊室
挂号柜台端口 80 → 内部诊室 8080
```

**没有端口映射会怎样？**
```
外部电脑 ──→ 无法直接访问 ──→ 容器内部的服务
           因为是隔离的！
```

### 1.3 网络隔离与内部通信

```
Docker 创建的虚拟网络
┌────────────────────────────────────────────────────┐
│                                                    │
│   ┌──────────┐       ┌──────────┐       ┌───────┐ │
│   │  etcd    │ ←───  │  milvus  │ ←───  │ minio │ │
│   │ :2379    │       │ :19530   │       │ :9000 │ │
│   └──────────┘       └──────────┘       └───────┘ │
│                                                    │
│   容器之间可以直接互相通信                          │
│   但外部无法直接访问这些端口                        │
│   只有 19530 和 9091 暴露给外部                    │
│                                                    │
└────────────────────────────────────────────────────┘
```

**关键概念：**
- **内部端口**（2379, 9000）：容器间通信用，外部看不到
- **暴露端口**（19530, 9091）：通过 `ports:` 映射到宿主机

## 二、为什么有这么多 docker-compose 文件？

### 2.1 一句话解释

**每个文件对应不同的部署场景，不是每个容器一个文件。**

```
docker-compose.yml           → 完整部署（App + Milvus）
docker-compose-milvus.yml    → 单独 Milvus（备用/开发用）
docker-compose-offline.yml   → 官方推荐 Milvus（生产推荐）
```

### 2.2 文件对比

| 文件 | 场景 | 包含内容 |
|------|------|----------|
| `docker-compose.yml` | 一键部署 | App 容器 + Milvus 容器 |
| `docker-compose-milvus.yml` | 单独运行 Milvus | 仅 Milvus 容器 |
| `docker-compose-offline.yml` | 官方推荐部署 | Milvus 3容器（etcd+minio+milvus） |

### 2.3 不是每个容器一个文件！

```
错误理解：有一个容器就应该有一个 docker-compose 文件 ❌

正确理解：一个 docker-compose 文件可以定义多个容器 ✓
```

**一个文件多容器的例子：**
```yaml
# docker-compose.yml
services:
  app:           # 容器1：你的应用
    build: .
    ports:
      - "8000:8000"

  milvus:        # 容器2：Milvus 主服务
    image: milvusdb/milvus:v2.6.16

  etcd:           # 容器3：元数据存储
    image: quay.io/coreos/etcd:v3.5.25

  minio:          # 容器4：对象存储
    image: minio/minio:latest
```

## 四、Docker 在这整个架构中的角色

### 4.1 Docker 是什么？

**Docker = 集装箱标准化**

```
传统方式（混乱）：              Docker 方式（标准化）：
┌─────────────────┐            ┌─────────────────┐
│ 应用A依赖Python3.8│           │ 应用A的集装箱   │
│ 应用B依赖Python3.11│   →     │ 应用B的集装箱   │
│ 应用C依赖Redis6.0 │          │ 应用C的集装箱   │
│ 依赖冲突！        │          │ 独立互不干扰    │
└─────────────────┘            └─────────────────┘
```

**核心能力：**
1. **环境一致**：Build once, run anywhere（构建一次，到处运行）
2. **隔离**：每个容器独立，互不影响
3. **可移植**：容易迁移到其他机器/服务器

### 4.2 Docker vs 虚拟机

```
虚拟机（VM）                    Docker 容器
┌─────────────────┐            ┌─────────────────┐
│ ┌─────┐ ┌─────┐ │            │  ┌─────┐        │
│ │AppA │ │AppB │ │            │  │AppA │ 容器1  │
│ │OS1  │ │OS2  │ │            │  ├─────┤        │
│ │     │ │     │ │            │  │AppB │ 容器2  │
│ └─────┘ └─────┘ │            │  ├─────┤        │
│ ┌─────────────────┐          │  │AppC │ 容器3  │
│ │    Hypervisor    │          │  └─────┘        │
│ │   (重量级)       │          │  ┌────────────┐  │
│ └─────────────────┘          │  │ Docker引擎 │  │
│                              │  │ (轻量级)   │  │
└─────────────────┘            └─────────────────┘

VM: 完整操作系统，几GB大小          容器: 共享宿主机OS，MB级别
启动: 几分钟                        启动: 几秒钟
```

### 4.3 沙箱概念

**Docker 是隔离的，但不是绝对安全的沙箱。**

```
隔离程度：
┌─────────────────────────────────────────┐
│  容器内                                 │
│  - 进程隔离（看不到其他容器进程）        │
│  - 文件系统隔离（COPY 的文件）          │
│  - 网络隔离（内部端口外部无法访问）      │
│  - 资源隔离（CPU/内存限制）              │
│                                         │
│  不隔离：                               │
│  - 共享宿主机的内核                      │
│  - 共享操作系统资源                      │
│  - 如果容器有 root 权限，理论上可逃逸    │
└─────────────────────────────────────────┘
```

**对于 Milvus 这种数据库：**
- 数据存在容器内的 volume 中，删除容器不丢数据
- 网络隔离防止未授权访问
- 但不适合作为多租户高安全需求的环境

### 5.2 部署命令

```bash
# 1. 启动 Milvus（官方推荐）
docker-compose -f docker-compose-offline.yml up -d

# 2. 启动完整应用（App + Milvus）
docker-compose up -d

# 查看运行状态
docker ps

# 查看日志
docker logs -f docker-ragmi-app

# 停止
docker-compose down
```

### 5.3 为什么需要 Docker？

**没有 Docker 时的问题：**
```
用户A: 我电脑 Python 3.8，项目需要 3.11 ❌
用户B: 我装了 MySQL 8.0，项目需要 5.7 ❌
用户C: Windows 开发，生产用 Linux， 环境不一致 ❌
```

**有了 Docker：**
```
开发者: 写好 Dockerfile → 构建镜像 → 推送到仓库
运维:   从仓库拉取镜像 → 运行容器 → 完事

不管什么操作系统，什么环境，都一样运行
```

## 六、快速问答

**Q: 我已经装了 Ollama，为什么还要 Docker？**
A: Ollama 是本地模型服务（不是必须的），Milvus 是向量数据库。Milvus 也可以装在 Docker 里，也可以装在服务器上。Docker 只是为了让部署更简单。

**Q: 为什么 Milvus 需要 3 个容器？**
A: etcd 存元数据（集合叫什么、有哪些字段），minio 存实际向量数据，milvus 是处理搜索请求的服务。分开设计是为了更稳定、方便扩展。

**Q: 容器和镜像的区别是什么？**
A: 镜像是只读的模板（就好比模具），容器是从镜像启动的运行实例（就好比用模具做出的蛋糕）。

**Q: 端口映射是什么意思？**
A: 把容器里的端口"暴露"到宿主机上，让外部可以访问。就像医院的挂号窗口（外部）映射到内部诊室。
