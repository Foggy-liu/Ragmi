## §1 判定口径：两层尺子

一句话：**锚点层判真实性，其余判忠实性。**

| 层 | 范围 | 独立事实来源 | 判什么 | 判错意味着 |
|---|---|---|---|---|
| **锚点层** | 7 个配置常量：`chunk_size=300` / `chunk_overlap=30` / 向量维度 `1024` / `bge-m3` / `MAX_ITER=3` / `MAX_REFL=3` / `timeout.{llm:30, tool:30, total:90}` / `RECURSION_LIMIT=42` | YAML 与代码本身 | **真实性** —— 答案说的和真配置一致吗 | 知识库错了，或模型在编 |
| **其余** | 机制解释、边界陈述、后果推断 | 检索到的语料片段 | **忠实性** —— 答案说的和素材一致吗 | 生成端不忠实 |

**为什么分两层**：设计稿 §1.1（v1）原话是"只判忠实性，不判真实性"。这条在**线 B** 完全成立
（反思节点判的就是"答案与素材是否一致"），但用在**线 A** 会漏掉一种真实的失败：

> 语料里那行数字本身写错了（切块参数被改成 500），模型忠实地转述了 500 ——
> 判"忠实"是满分，判"真实"才是失败。

所以线 A 分两层：**能独立验证的常数用真相判，其余用素材判。** 两层的分界不是拍脑袋，
是"这个事实在 YAML / 代码里能不能查到一个独立的、不依赖语料的答案"。

> **设计稿已同步**（v2）：§1.1 现在就是这个两层尺子，并新增 §6.1.1 说明两层在判分时怎么落地
> —— 判分器看到的仍是**一份扁平的 `must_contain` 列表**，分层是我们**出题时**的纪律，
> 不是判分时的规则。答案键的真相来源（配置文件的 `file:line`）见设计稿 §6.1.1。

> 顺带：**语料里那些"函数值"（块数、耗时、字符数）一律不进锚点层** ——
> 它们是语料的函数，不是配置的函数（设计稿 §4.4 决策 4）。

## §2 每题字段与判分方式

| 字段 | 含义 | 判分器怎么用 |
|---|---|---|
| `query` | 题面（**最终版**，已过召回检查） | 直接问 Agent |
| `type` | `fact` / `mechanism` / `honesty` / `placeholder_honesty` / `tool` | 决定进不进总分 |
| `must_contain` | **可判定的命题**（不是裸 token） | 判语义等价，逐条命中/不命中 → **进 `hit_rate` 分母** |
| `should_contain` | **题面没问、但答对了更好**的加分项 | 判语义等价 → **不进 `hit_rate` 分母**，单独报**深度率** |
| `must_not_contain` | 负例命题 | 命中任一条 = 幻觉 |
| `reference_answers` | 参考答案（3 条，用于判分器对齐口径） | 只给判分器，**不给被测体** |
| `anchors` | **召回锚点**：正则 + 语料原话 | 跑评测前过召回检查（§7） |
| `notes` | 出处、改题原因、边界条件 | 不参与判分 |

### 2.1 为什么 `must_contain` 必须是命题而不是裸 token

【实测 2026-11-27】`"30" in "300"` 是**假阳性** —— A01 的 `overlap=30` 一度被误判为命中。

判定规则：**命题 = 一个可以被判分器判"语义等价"的完整事实句**。
禁止写 `"300"`、`"30"`、`"bge-m3"` 这种裸 token —— 判分器会拿它做子串匹配，
`"bge-m3"` 在 `"bge-m3:latest"` 里算命中，在 `"bge-large 和 bge-m3 都是 1024 维"` 里也算命中，
但后者说的是**历史**不是**当前**。

### 2.2 为什么 `anchors` 用正则而不是裸 token

召回检查要确认的是"**答案锚点对应的内容**出现在 top-5 里"，不是"某个字符串出现过"。
所以锚点正则必须**带上下文**：

```
❌ "30"                            # 命中 "300"
✅ r"overlap\s*[=:：]?\s*30(?!\d)"  # 只命中 "overlap 30" / "chunk_overlap=30"
```

### 2.3 锚点正则的写法约定

1. **允许多种语料说法**：一个事实在语料里有几种写法，正则就枚举几种
   （例：「Python 杀不掉线程」在语料里有 4 种写法 → 正则写 4 个分支）。
   枚举来源是**语料全文**，不是某一次检索的结果 —— 否则就是拿检索结果反推标准，等于自证。
2. **`(?!\d)` 收尾**：防止 `30` 命中 `300`、`3` 命中 `30`。
3. **`.` 不跨行**（默认行为），除非显式加 `(?s)` —— 表格里上下两行的内容不该被当成连续一句。
4. **上限 4 个锚点/题**：与 R3（要点 ≤ 4）对齐。锚点多了就变成"必须召回到整个章节"。

### 2.4 `must_contain` 与 `should_contain` 的分工

【实测 2026-11-27 定稿自查】发现 **3 处答案键超纲**：答案键里的某条命题，
**题面根本没有问**。判分器判它不命中 → 一份**完全正确**的答案被扣分。

设计稿 §5.0 规则 3 只要求 `must_contain` 是「可判定的命题」，
**没说它还必须是"题面问到的"命题** —— 这是漏洞，这里补上：

| 字段 | 判什么 | 进 `hit_rate` 分母 | 单独指标 |
|---|---|---|---|
| `must_contain` | **题面问到了、且答对了** | ✅ | — |
| `should_contain` | 题面**没问**，但答对了是加分 | ❌ | **深度率** `depth_rate` |

**深度率** = 命中的 `should_contain` 条数 ÷ `should_contain` 总条数。
它**不进总分**，单独报 —— 它看的是「模型有没有主动多说一层」，
而不是「模型有没有答到题」。所以它叫深度率，不叫准确率。

**为什么不能把超纲项留在 `must_contain`**：一个只答了题面所问内容的答案，
本来是**完全正确**的答案，却只能拿部分分。
按 A/B 组 8 题、`must_contain` 共 **24 条**算，一处超纲 =
全卷 `hit_rate` 丢 1/24 = 0.042 → 总分丢 0.042 × 0.6 = **0.025** ——
量级不大，但**性质是错的**：正确答案被判成错答案。

**为什么不能直接删掉**：这 3 条都是**这个项目的真知识**
（最坏 32 步撞默认上限 25、`_resolve_model_name()`、返回 0 重置），
删了可惜；扩题面又会把答案写进题面（B04 变成「重置是怎么做的」→ 违反 R2）。
**降级成 `should_contain` 是唯一两头都不亏的做法**。

### 2.5 `should_contain` 的**可达性**要求

`must_contain` 有召回前提（§7 的锚点检查）—— 支撑它的事实必须在 top-5 里。
**`should_contain` 同样有这条要求**，而且更容易被忽略：

> 模型**只能看到 top-5**（`agent/tools/rag_tool.py:62` 的 `top_k=5`，
> 和召回检查用的是同一个参数）。
> 一条深度项的支撑素材如果不在 top-5 里，模型**根本答不出来** ——
> 留着它，`depth_rate` 就从「模型有没有多说一层」退化成「检索有没有多给一块」，
> **测的是检索，不是深度**。

所以 `should_contain` 的准入条件是两条：

1. **题面没问**（否则它是 `must_contain`）；
2. **支撑素材在本题 top-5 里**（否则它测的是检索）。

【实测 2026-11-27】A04 按第 2 条砍掉了 3 条（5 条 → 2 条），见 §7.5。

### 2.6 本轮降级清单（3 处）

| 题 | 原 `must_contain` 的哪部分 | 降级理由（题面问了吗） | 去处 |
|---|---|---|---|
| **A02** | ③「最坏情况 32 步会撞 LangGraph 默认上限 25，触发 `GraphRecursionError`」 | 题面只问「是多少」「是不是写死的」，**没问"为什么需要它"** | `should_contain` |
| **B04** | ①里的「`reflection_count` **永不重置**」 | 题面问「上限各是多少」，问的是**上限**，不是**重置策略** | `should_contain` |
| **B04** | ③「约定『返回 0 表示重置』；纯累加型 reducer 写 0 清不掉」 | 题面问「reducer 是累加还是覆盖」，问的是**性质**，不是**约定** | `should_contain` |

> B04 的 ① 被**拆成两半**：`must_contain` 留「两个独立计数器各管哪条循环 + 各自上限」，
> 「永不重置」单独进 `should_contain`。

### A02 recursion_limit

- **类型**：`fact`
- **题面**：

  > Agent 图的 recursion_limit 是多少？这个值是写死的吗？

- **素材来源**：`txt/术语表_md.txt:27`、`txt/项目优化_md.txt:357`、`txt/项目速览_md.txt:560`

  ```
  RECURSION_LIMIT = 8×4+10 = 42（按 MAX_ITER/MAX_REFL 推导，不写死）
  RECURSION_LIMIT = _STEPS_PER_ROUND * (MAX_REFL + 1) + 10   # = 42
  …最坏情况 = 每轮2*MAX_ITER + 2步 ×(MAX_REFL + 1)轮 =8 × 4 = 32步 > LangGraph 默认 25 → 撞GraphRecursionError
  ```

- **`must_contain`**（2 条命题）

  1. `recursion_limit = 42`
  2. 由 `MAX_ITER` / `MAX_REFL` 推导得出，不是写死的常量

- **`should_contain`**（1 条 —— 题面没问，答对了加分）

  1. 最坏情况 32 步会撞 LangGraph 默认上限 25，触发 `GraphRecursionError`

  > ⚠️ 这条**本轮从 `must_contain` 降级**（§2.6 第 1 行）。
  > 题面问的是「是多少」「是不是写死的」，**没问"为什么需要它"** ——
  > 一份只回答这两问的答案是完全正确的，不该因此拿 2/3。

- **`must_not_contain`**（1 条负例）

  - 把 32 当成实际传给 LangGraph 的 `recursion_limit`（32 是最坏步数，不是上限值）

- **`reference_answers`**

  1. recursion_limit 是 42，由 _STEPS_PER_ROUND × (MAX_REFL+1) + 10 推导，不是写死的。最坏情况 32 步会撞 LangGraph 默认 25，所以要显式传 42。
  2. 42。由 MAX_ITER/MAX_REFL 算出来的，改常量它会跟着变；32 是最坏步数，真正传的是 42。
  3. 运行时显式给 LangGraph 42，公式是 8×4+10；写死默认 25 会撞 GraphRecursionError。

- **召回锚点**（4 个）

  | 锚点 | 正则 | 语料原话 |
  |---|---|---|
  | `=42` | `(?i)recursion_limit[^\n]{0,120}\b42\b` | `RECURSION_LIMIT = 8×4+10 = 42` |
  | `推导非写死` | `(?i)(?:recursion_limit[^\n]{0,140}(?:推导\|不写死\|算出\|而不是写死)\|MAX_REFL[^\n]{0,40}推导\|推导[^\n]{0,40}MAX_REFL)` | `按 MAX_ITER/MAX_REFL 推导，不写死` |
  | `GraphRecursionError` | `GraphRecursionError` | `超了抛 GraphRecursionError` |
  | `最坏32步` | `最坏(?:情况)?\s*32\s*步\|8\s*×\s*4` | `=8 × 4 = 32步 > LangGraph 默认 25` |

- **备注**：负例直接取自素材 —— `txt/项目速览_md.txt:755` 明写"代码里两个数都对，
  但指的是两件事：32 是最坏步数，42 才是实际传的值"。
  锚点 `最坏32步` 用 `32\s*步` 而不是裸 `32`，是为了避开语料里的 `32.6 s`（实测最慢单次耗时）。

### A04 重建索引后怎么切到新集合（alias 原子切换）

- **类型**：`fact`
- **题面**：

## §6 D 组 —— 工具确定性型（2 题，零 LLM 判分）

### 6.1 为什么 D 组不能用 `exact_match`

【实测 2026-11-27 定稿自查】`scoring: "exact_match"` 是**恒 false** 的：

- 工具层返回的是 **`"16"`**（`agent/tools/calculator_tool.py:81` 的 `str(result)`）；
- 但 `agent/prompts/synth_prompt.py:29` 的【撰写规则】第 6 条写死「**中文输出，结构清晰**」
  → Agent 的实际答案是 **「计算结果是 16。」**。

字符串全等 → **永远判错**。这不是模型答错，是**判分方式写错了**。

### 6.2 `number_extract` 的判定规则（纯函数，零 LLM）

```
1. 从答案文本里抽取所有阿拉伯数字（含小数、带千分位逗号）→ number_tokens
2. 归一化：去逗号；"16.0" → 16；"-0" → 0
3. 期望值 expected 也做同样归一化
4. 判定：expected ∈ {归一化后的 number_tokens}
```

- **同时**要求 `expected_tool` 命中（`calculator` 被调用过）。
- 结果 JSON 里**额外记两个字段**便于人工复核：
  `extracted_numbers`（抽到的全部数字）、`last_number`（最后一个数字 = 结论位）。
- **已知局限（如实记录）**：只要期望值出现在答案的**任何**位置就算过 ——
  理论上存在「答案提到 16 但结论是别的数」的情况。
  用 `last_number` 字段 + 快照留档来兜住这类异常，而不是把规则做得更复杂。
  （D01/D02 的表达式都短、结论唯一，实测不会触发。）

### D01 calculator

```json
{
  "id": "D01", "type": "tool",
  "query": "用计算器算一下 (3+5)*2 等于多少？",
  "expected_tool": "calculator", "expected_answer": "16",
  "scoring": "number_extract",
  "notes": "agent/tools/calculator_tool.py:66-81 用 AST 白名单求值，输出 str(result)。scoring 从 exact_match 改成 number_extract —— 见下方说明。"

```

### D02 calculator

```json
{
  "id": "D02", "type": "tool",
  "query": "用计算器算一下 7 的 3 次方等于多少？",
  "expected_tool": "calculator", "expected_answer": "343",
  "scoring": "number_extract",
  "notes": "同上。指数上限 100（calculator_tool.py:33），7**3 未越界。原题『2 的 10 次方』=1024 与 A01 的向量维度 1024 撞数字，判分器锚点必须唯一 —— 已换题。"
```

> **为什么这两题重要**：① **判分器锚点** —— 答案已知对错，判分器必须全对，
> 否则判分器不合格、全量不许开始；② 零幻觉零争议，不需要 LLM 判分；

## §9 跑评测时要一起带上的东西

建 `test/eval_quality/data/answer_quality_cases.json` 时，每条 case 除 §2 的字段外还要带：

```json
{
  "id": "A01",
  "query": "…",
  "type": "fact",
  "must_contain": ["…", "…", "…"],
  "should_contain": ["…"],
  "must_not_contain": ["…"],
  "reference_answers": ["…", "…", "…"],
  "anchors": [{"id": "chunk_size=300", "regex": "chunk_size\\s*[=:：]?\\s*300(?!\\d)", "desc": "chunk_size = 300"}],
  "retrieval_required": true
}
```

- `anchors[].regex` 用 **JSON 转义后的字符串**（`\\s` / `\\d` / `\\|`）。
- C01 的 `anchors` 保留，但**期望命中数为 0** —— 脚本要把它当"反断言"处理：
  命中了反而说明语料被污染了。
- C02 的 `retrieval_required = false`；D01/D02 同理。
- `scoring` 字段：A/B 组 = `"llm_judge"`，C 组 = `"binary"`，D 组 = `"number_extract"`（**不是** `exact_match`）。
- **没有 `should_contain` 的题也要写这个字段**（空数组 `[]`）——
  脚本靠它区分"这题没有深度项"和"这题漏填了"。
- `depth_rate` 的分母 = 该题 `should_contain` 的条数；
  **全卷分母 = 所有题的 `should_contain` 条数之和**（A01=1、A02=1、A04=2、B04=2，其余 0 → 全卷 6 条）。
- `should_contain` 的准入有**两条**（§2.5）：① 题面没问；② 支撑素材在该题 top-5 里。
