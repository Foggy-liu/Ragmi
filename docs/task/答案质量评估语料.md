## §1 线 B 到底在测什么

线 A 测的是"**答案好不好**"。线 B 测的是"**反思节点那双眼睛准不准**"。

具体是三件事：

| # | 能力 | 怎么测 | 测错了的后果 |
|---|---|---|---|
| 1 | **不误报**（假阳性） | 给一个**好答案**，看它判不判 `rewrite` | 反思不停 → 每轮多烧一次 LLM → 又慢又贵 |
| 2 | **能发现问题**（真阳性） | 给一个**坏答案**，看它判不判 `rewrite` | 反思形同虚设 → 图白转一圈就结束 |
| 3 | **知道自己的边界** | 给一个素材里**根本没提**的错，看它判不判得出来 | 把"判不出"报成"判出来了" → 高估反思能力 |

第 3 条最容易被忽略，也最重要：
**反思节点只能拿素材当依据**（`agent/prompts/reflect_prompt.py:44` 的判断维度是"答案与素材是否一致"）。
素材没说的东西，它**无从质疑** —— 这是信息边界的必然结果，不是失职。

> 这正是"占位数据怎么判断"的答案：**判断不了**。
> 而这个"判断不了"本身就是面试可讲的诚实边界 —— 反思节点在信息边界内有效，
> 超出边界无能为力，所以项目用三层超时和双计数器兜底，而不是指望它兜住一切。

## §2 测试用例怎么构造

### 2.1 零改代码的注入点

`agent/nodes/reflect_node.py:63` 的签名是 `reflect_node(state: AgentState, llm=None)` —— **LLM 可注入**。
这意味着可以**用生产代码里那个 prompt 构造**，把 LLM 换成一个可复现的实例，
**`agent/` 一个字不改**。

### 2.2 state 布局（**顺序有讲究**）

```python
state = {
    "messages": [
        HumanMessage(content=问题),                              # ← 必须是 messages[0]
        ToolMessage(content=素材, name="rag_search",
                    tool_call_id="call_test_1"),
        AIMessage(content=候选答案),
    ],
    "tool_status": {
        "call_test_1": {"tool": "rag_search", "status": "success",
                        "code": "OK", "retryable": False},
    },
    "last_critique": "",
    "reflection_count": 0,
    "iter_count": 0,
}
```

**为什么是这个顺序**（三个读取点决定了它）：

| 读取点 | 代码位置 | 要求 |
|---|---|---|
| 问题 | `reflect_node.py:97` → `state["messages"][0].content` | HumanMessage 必须在 **index 0** |
| 答案 | `reflect_node.py:98` → `_extract_latest_answer()` 倒着找最后一条 AIMessage | AIMessage 放最后 |
| 素材 | `reflect_node.py:100` → `collect_round_material()` 取"**最后一条** HumanMessage 之后的全部 ToolMessage" | ToolMessage 必须在 HumanMessage 之后 |

> ⚠️ 若把 ToolMessage 放在 AIMessage **之前**（设计稿 §7.4 的示例写法是 `[Human, AI, Tool]`），
> 两种顺序都能取到素材；但 `[Human, Tool, AI]` **更贴近真实链路**
> （真实轨迹是 `Human → AI(带 tool_calls) → Tool → AI(synth 的答案)`）。

### 2.3 素材与工具状态

- **标准素材**：`tool_status = success`（工具确实返回了内容）。
- **无关素材**：`tool_status` **仍然是 success**。
  理由：素材"不给"不等于"检索为空"。若把状态改成 `empty`，
  reflect prompt 的硬约束会介入（"工具 empty 时应判 end"），
  **诚实性维度会把测量污染掉** —— 测的就不是判别力，是 prompt 的一条特例规则。
  → 素材给的是**真实但无关**的内容，状态照常是 success。

### 2.4 `tool_status` 的渲染

`format_tool_status()`（`status_tool_wrapper.py:131`）只渲染 **工具名 + status**：

```
- rag_search: success
```

`code` 和 `retryable` **不进 prompt**（只有 status 字典里存着）。
所以线 B 的候选答案里若要考"code / retryable"，reflect 只能靠**素材正文**里的那张表。

```

本项目特有选择：切三层不是为了"多一层更保险"，而是职责不重叠：归一化管"错误叫什么"、第 2 层管"这一次等多久"、第 3 层管"整张图还能跑多久"。别的方案（只留总时限 / 只留单次超时）都有明确死角 —— 只留总时限，工具线程会把连接占着不放；只留单次超时，10 个节点各等 30 s 也能跑 5 分钟。
```

```
层 | 位置 | 管什么 | 不管什么
- | -- | --- | ----
第 1 层 异常归一化 | agent/errors.py + 工具函数 | 第三方异常 → AgentTimeoutError / AgentToolError | 不管时间
第 2 层 单次动作超时 | agent/timeout.py :: Timer | "这一次调用最多等 N 秒" | 不管全局预算
第 3 层 图级总时限 | state["deadline"] + is_expired() | "整张图最多跑 N 秒" | 不管单次调用
```

```
agent/timeout.py 里的关键代码：
with ThreadPoolExecutor(...) 在退出时会等所有任务跑完（shutdown(wait=True)），
那样超时形同虚设。所以必须 shutdown(wait=False) —— 但这只是「不等了」，不是「杀掉了」。
真实影响：一次工具超时后，那个线程会在几秒~几十秒后自己结束，短暂占着一个连接。
对个人项目 / 面试作品 完全可接受。要彻底解决需要：
- 换进程（multiprocessing，可 kill，但序列化开销大）
```

## §4 候选答案清单（4 题 × 6 份 = 24 份）

> **好答案全部手写**，不用 Agent 生成的 —— 用 Agent 自己的输出当"好答案"，
> 等于把"它平时就写这样"当成"写对了"，测不出反思的判别力。
>
> **每题两份好答案，差别是"有没有标注引用"**：
> `good-1` 写成生产链路的自然样子（不标注引用），
> `good-2` 在末尾加一句引用。
> 这么设计是为了**拆开一个混杂因素** ——
> `REFLECT_PROMPT` 的判断维度里有一条「引用：success 状态下是否标注引用？」，
> 如果好答案一律不标引用，而 reflect 恰好因为"没标引用"判 `rewrite`，
> 那么"假阳性率"这个指标测的就不是忠实性判别力，而是 prompt 里的一条引用规则。
> 两份好答案一对照，这个混杂就能被单独看见。

### B01 的候选答案

**问题**（与线 A 的 B01 完全一致）：

> RAGMI 的 Agent 有三层超时，分别负责什么？为什么「超时就杀掉线程」这个做法在本项目行不通？

#### B01-good-1（好答案 · 不带引用）

> RAGMI 的 Agent 有三层超时，各管一件事、互不重叠：第 1 层是异常归一化，把第三方库的异常翻译成自家的 AgentTimeoutError / AgentToolError，只管"错误叫什么"，不管时间；第 2 层是单次动作超时，用 agent/timeout.py 的 Timer 给单次调用套上限，只管"这一次等多久"，不管全局预算；第 3 层是图级总时限，把 deadline 写进 state，各节点动手前用 is_expired() 协作式检查，只管"整张图还能跑多久"，不管单次调用。不能靠"超时就杀掉线程"实现，是因为 Python 没有 Thread.terminate()，杀不掉正在跑的线程，超时只能做到"不再等"——底层线程还在跑、还占着连接，所以底层连接自己也得有上限。

#### B01-good-2（好答案 · 带引用）

> 三层超时是按"职责不重叠"切的，不是按"多一层更保险"堆的。异常归一化层负责把第三方异常翻成 AgentTimeoutError / AgentToolError，让上层只认自家两种异常；单次动作超时层用 Timer 包住单次 LLM 或工具调用，限制这一次最多等多久；整图 deadline 层给整张图一个总预算，各节点进图前协作式检查超没超。Python 线程无法被强制终止（没有 Thread.terminate()），所以超时的语义是"不再等"而不是"杀掉"——工具线程仍会跑完、短暂占着 Milvus 连接，这也是为什么底层连接必须自己也有上限。
> （依据检索到的《项目速览》§3.12 / §3.13 与《工业化评估与遗留清单》§4）

#### B01-bad-1（矛盾型 · 与素材矛盾）

> 三层超时分别是：第 1 层是异常归一化，管"错误叫什么"；第 2 层是整图总时限，管"整张图还能跑多久"；第 3 层是单次动作超时，管"这一次等多久"。至于"超时就杀掉线程"，Python 没有 Thread.terminate()，杀不掉线程，所以本项目的超时是"不再等"——底层线程仍在跑，仍占着连接，底层连接自己也得有上限。

> **矛盾点**：素材的三层顺序是「异常归一化 → 单次动作超时 → 图级总时限」，
> 本答案把第 2、3 层对调，且把三层的职责也一一错配。
> **注意**：后半段"杀不掉线程"是**正确的** —— 矛盾点只有层次错配这一处，
> 这样测出来的 `rewrite` 才干净（不会被误归因到别的错误）。

#### B01-bad-2（缺项型 · 少答一层）

> RAGMI 的 Agent 有两层超时：第 1 层异常归一化，把第三方异常翻译成 AgentTimeoutError / AgentToolError；第 2 层单次动作超时，用 Timer 给单次调用套上限。另外，Python 杀不掉线程，超时只能"不再等"，底层连接必须自己也有上限。

> **缺项点**：题干问的是**三层**，答案只给了两层 —— **漏掉整图 deadline 那一层**。
> 完整性缺陷对**题干**也成立，所以"无关素材"轴下仍应判 `rewrite`（见 §5 真值表）。

#### B01-bad-3（答非所问型 · 换成 A01 的答案）

> 本项目的文档切块参数是 chunk_size=300、chunk_overlap=30，嵌入模型用 bge-m3，向量维度 1024。切块时按 300 字符切、段落之间重叠 30 字符，避免语义被切断。

> **答非所问点**：整段在答切块参数，与三层超时毫无关系。

#### B01-bad-4（编造型 · 素材完全没覆盖的事实）

> RAGMI 的 Agent 有三层超时，各管一件事：第 1 层异常归一化，把第三方异常翻译成 AgentTimeoutError / AgentToolError；第 2 层单次动作超时，用 Timer 包住单次调用；第 3 层图级总时限，各节点动手前协作式检查。Python 杀不掉线程，超时只能"不再等"，底层连接必须自己也有上限。另外，超时发生时会**自动往监控面板推一条告警**，运维能实时看到哪些查询超时了。

> **编造点**：最后一句。素材从头到尾**没提监控、没提告警、没提日志** ——
> 这个事实域素材是完全沉默的，所以 reflect **无从质疑**。
> 而事实上项目里也没有这个机制（超时只走 `state["expired"]` + 条件边 END）。

### B02 的候选答案

**问题**：

> RAGMI 的 retrieve() 在检索失败时怎么处理？为什么不直接返回空列表？不这么做会造成什么后果？

#### B02-good-1（好答案 · 不带引用）

> RAGMI 用**抛异常 vs 返回空列表**来区分这两件事。检索失败（Milvus 连不上、查询报错、embedding 报错）时，core/rags/rags.py 的 retrieve() 往上抛 RetrievalError；只有"确实没检索到"才返回空列表 []。工具层 agent/tools/rag_tool.py 再把 RetrievalError 翻译成 AgentTimeoutError（原始异常是超时类时）或 AgentToolError，工具状态因此能记成 timeout / error 而不是 empty。不区分的后果是：异常被吞成空列表，工具层只看到"空"，状态一律记成 empty，Milvus 挂了和"库里没这内容"在日志里长得一模一样，排查方向从一开始就跑偏。

#### B02-good-2（好答案 · 带引用）

> 靠"抛"和"返回"两条路径区分。失败走异常路径——retrieve() 抛 RetrievalError，并且保留原始异常作为 __cause__；空走返回路径——返回 [] 表示确实没有匹配结果。不这么做的代价是 except Exception: return [] 把两者混成一个：工具层看到空串就把状态记成 empty，timeout 和普通 bug 分不开，日志里也看不出是 Milvus 挂了还是库里没这内容。
> （依据检索到的《项目速览》§3.10）

#### B02-bad-1（矛盾型 · 与素材矛盾）

> RAGMI 其实**不区分**这两种情况——检索失败和检索到 0 条都返回空列表，因为 Milvus 查询本身很少失败，失败了就当作没查到更省事。这样工具层统一记 empty 状态，代码里只有一条路径要维护。代价是检索失败会被当成"库里没有"，用户看到的是"未找到相关资料"，不会暴露后端故障。

> **矛盾点**：素材明写"retrieve()抛RetrievalError表示失败，返回[]只表示'确实没检索到'"。

#### B02-bad-2（缺项型 · 少答"后果"）

> RAGMI 区分这两种情况的方式是：检索失败时 retrieve() 抛 RetrievalError，只有真的没检索到才返回空列表 []。工具层会把 RetrievalError 翻译成 AgentTimeoutError 或 AgentToolError。

> **缺项点**：题干问了三件事（怎么处理 / 为什么不返回空列表 / 后果是什么），答案只答了前两件，
> **漏掉"不区分会造成什么后果"** —— 也就是素材里"不用它会怎样"那一段。

#### B02-bad-3（答非所问型 · 换成 B03 的答案）

> 工具调用状态有四种：success、empty、timeout、error，各自带 code 和 retryable。key 用的是工具调用的 id 而不是工具名，因为同一轮里 MiniMax 可能并发调同一个工具两三次，按工具名记会互相覆盖。

#### B02-bad-4（编造型 · 素材完全没覆盖的事实）

> RAGMI 区分这两种情况的方式是：检索失败时 retrieve() 抛 RetrievalError，只有真的没检索到才返回空列表 []。工具层会把 RetrievalError 翻译成 AgentTimeoutError 或 AgentToolError。不区分的话工具状态就全无意义，超时和 bug 分不开。另外，检索失败的异常在到达工具层之前，会**先在 Milvus 客户端层自动重试一次**。

> **编造点**：最后一句。素材里**没有任何重试机制**的描述，也没提 Milvus 客户端层的重试。

### B03 的候选答案

**问题**：

> 工具调用状态 tool_status 有哪几种状态？key 用的是什么？为什么不能按工具名记？

#### B03-good-1（好答案 · 不带引用）

> 工具调用状态有四种：success（工具返回非空内容，code OK）、empty（工具返回空串，code EMPTY_RESULT）、timeout（工具抛 AgentTimeoutError，code TOOL_TIMEOUT，retryable 为 true）、error（工具抛 AgentToolError 或其他异常，code TOOL_ERROR，retryable 为 false）。tool_status 的 key 是**工具调用的 id**，不是工具名——调用 id 由模型生成、每次唯一；同一轮 MiniMax 常常并发调同一个工具两三次，按工具名做 key 会让后一次覆盖前一次，实测成功的那条被 timeout 冲掉。value 结构是 {tool, status, code, retryable}。

#### B03-good-2（好答案 · 带引用）

> 四态：success / empty / timeout / error，分别对应 code OK / EMPTY_RESULT / TOOL_TIMEOUT / TOOL_ERROR，只有 timeout 的 retryable 是 true。key 不能用工具名，因为 MiniMax 一次决策可能并发发 2~3 个 rag_search，同名 key 会互相覆盖；用调用 id 就不会——id 每次唯一，是模型自己生成的。工具状态由官方钩子 wrap_tool_call 在工具真正执行的那一刻写入。
> （依据检索到的《项目全景图》§3.5 与《项目现状》§4.1）

#### B03-bad-1（矛盾型 · 与素材矛盾）

> 工具调用状态有四种：success、empty、timeout、error。tool_status 的 key 用的是**工具名**（tool_name）而不是调用 id —— 因为 id 是模型生成的、不受我们控制，用工具名更稳。value 结构是 {tool, status, code, retryable}。

> **矛盾点**：素材明写"key = 调用 id，不是工具名。调用 id 由模型生成、每次唯一"。
> ⚠️ 这条答案与**题干**也有张力（题干问"为什么不能按工具名记"），
> 详见 §5 真值表的备注。

#### B03-bad-2（缺项型 · 少答"为什么"）

> 工具调用状态有四种：success、empty、timeout、error。tool_status 的 key 用的是工具调用的 id，不是工具名。

> **缺项点**：题干问了三件事（四态 / key 是什么 / 为什么不能按工具名记），答案漏掉第三件
> —— **漏掉并发覆盖那整段**。

#### B03-bad-3（答非所问型 · 换成 A02 的答案）

> Agent 图的 recursion_limit 是 42，由 MAX_ITER / MAX_REFL 推导，不是写死的常量。最坏情况 32 步会撞 LangGraph 默认上限 25，所以要显式传 42。

#### B03-bad-4（编造型 · 素材完全没覆盖的事实）

> 工具调用状态有四种：success、empty、timeout、error。tool_status 的 key 是工具调用的 id，不是工具名。同一轮并发调同一个工具时按 id 各存各的，不会覆盖。另外，这四个状态是**按会话保存**的，同一个 thread_id 里的历史调用状态可以回看。

> **编造点**：最后一句。素材里没有会话、持久化、thread_id 这套说法。
> 而事实上项目里**根本没有 checkpointer**（CLAUDE.md 明说"Agent 多轮持久化未实现"）——
> 所以这句既是素材没覆盖的，也是事实错的。

### B04 的候选答案

**问题**：

> Agent 的 iter_count 和 reflection_count 两个计数器：上限各是多少，为什么用两个而不是一个？reducer 是累加还是覆盖？

#### B04-good-1（好答案 · 不带引用）

> 因为 LangGraph 对没声明 reducer 的字段默认是**覆盖语义**（LastValue，最后一次写赢），不是累加。iter_count 节点返回的是增量（返回 1 表示 +1），覆盖语义下计数器永远停在 1，MAX_ITER 的边界检查 iter_count + 1 >= MAX_ITER 永远不成立，Agent 会无限循环调工具直到撞 recursion_limit；而纯累加型 reducer（如 reflection_count 用的 _inc_refl）又做不到清零——旧 + 0 = 旧。所以拆成两个计数器，各挂各的 reducer：iter_count 用 _reset_or_inc（返回 0 表示重置，返回 >0 表示累加），上限 MAX_ITER=3，reflect 判 rewrite / re_iterate 时归 0；reflection_count 用 _inc_refl（纯累加），上限 MAX_REFL=3，永不重置，作为全局绝对上限防死循环。

#### B04-good-2（好答案 · 带引用）

> 两个计数器对应两条独立的循环：iter_count 管 iter/工具循环，上限 MAX_ITER=3，reflect 判 rewrite 或 re_iterate 时归零重来；reflection_count 管 reflect 反思循环，上限 MAX_REFL=3，永不重置，是防死循环的绝对上限。要拆成两个的原因是 reducer 语义：LangGraph 默认是覆盖（LastValue，最后一次写赢）而不是累加，覆盖下节点返回 1 会把旧值盖成 1，计数器永远不涨，边界检查失效；而纯累加的 reducer 写 0 清不掉（旧 + 0 = 旧），所以约定"返回 0 表示重置"——这个约定是 reflect 能重置 iter_count 的唯一办法。
> （依据检索到的《项目现状》§2.3 与《项目全景图》§3.3）

#### B04-bad-1（矛盾型 · 与素材矛盾）

> 因为 LangGraph 默认的 reducer 就是**纯累加**——节点返回几次就加几次，所以一个计数器不够用才拆成两个：iter_count 管 iter 调用次数（上限 MAX_ITER=3），reflection_count 管 reflect 调用次数（上限 MAX_REFL=3）。两个上限都是"达到就停"，reflection_count 也会在 reflect 判 rewrite 时归零重来，这样反思可以反复进行。

> **矛盾点**（两处）：① 素材明写默认是**覆盖**语义（LastValue），不是累加；
> ② 素材明写 reflection_count **永不重置**（绝对上限，防死循环）。

#### B04-bad-2（缺项型 · 少答"上限"）

> 用两个计数器是因为 iter_count 管 iter/工具循环、reflection_count 管 reflect/反思循环，各管各的。LangGraph 对没声明 reducer 的字段默认是覆盖语义（LastValue，最后一次写赢），不是累加；纯累加型 reducer 写 0 清不掉，所以约定"返回 0 表示重置"。

> **缺项点**：题干问"上限各是多少"，答案**没给 3 和 3**（= `must_contain` 第 2 条缺），
> 也没说 reflection_count 永不重置（那是**深度项**，见题集 §2.5）。

#### B04-bad-3（答非所问型 · 换成 A04 的答案）

> 重建时先新建一个带时间戳的真实集合 `txt_data_<时间戳>`，灌完数据建好索引后，用 Milvus 的 alias 机制把稳定名 `txt_data` 原子改指到新集合（`alter_alias`，首次走 `create_alias`）。检索侧只认 `txt_data` 这个别名，所以 alias 改指完线上立刻读新数据，不用改代码也不用重启。

> ⚠️ **2026-11-27 更新**：A04 已换题（原「嵌入模型与维度」→ 现「重建索引后怎么切到新集合」），
> 这里跟着换成**新 A04 的参考答案** —— "答非所问型"的性质不变（内容对，但答的不是 B04 的问题）。

#### B04-bad-4（编造型 · 素材完全没覆盖的事实）

> 用两个计数器是因为 LangGraph 默认的 reducer 是覆盖语义（LastValue，最后一次写赢），不是累加；纯累加型 reducer 写 0 清不掉，所以约定"返回 0 表示重置"。iter_count 上限 MAX_ITER=3（reflect 判 rewrite / re_iterate 时归 0），reflection_count 上限 MAX_REFL=3 且永不重置。另外，MAX_ITER 和 MAX_REFL 这两个上限**支持运行时热更新**：改 YAML 之后不用重启进程，下一轮就生效。

> **编造点**：最后一句。素材没提热更新。
> 而事实上 `agent/constants.py` 是**启动时加载 + assert 校验**的 —— 改 YAML 必须重启进程。

### 5.3 为什么坏答案是这样分配的

| 类型 | 有素材 | 无素材 | 理由 |
|---|---|---|---|
| **① 矛盾型** | 判得出 | **判不出** | 矛盾是"答案 vs 素材"的矛盾。没有素材，就没有可比对的另一方 → 反思节点**必然**判不出（这是信息边界的必然结果，不是失职） |
| **② 缺项型** | 判得出 | **判得出** | 缺项是"答案 vs **题干**"的缺陷。题干说"三层"而答案只给两层 —— 这个对比**不需要素材**。所以两种素材下都应判 `rewrite` |
| **③ 答非所问型** | 判得出 | **判得出** | 同上，是"答案 vs 题干"的缺陷。答的东西和问题对不上，跟有没有素材无关 |
| **④ 编造型** | **判不出** | **判不出** | 素材里**根本没有**这个事实域（监控 / 重试 / 会话持久化 / 热更新）→ 素材既不支持也不反对 → 只能判 `end`。这正是"素材外编造是反思的结构性盲区"这条结论的证据 |
| **好答案** | `end` | `end` | 素材不足时好答案也不该被改 —— 否则反思会无休止地改写正确的东西 |

> ⚠️ **【实测 2026-11-27】④ 这一行的前提被实测推翻了** —— 48 格全跑完（**3 遍**），
> **编造型 × 标准素材 12/12 判 `rewrite`**（原判"判不出"）。
> critique 原文：「『超时会自动往监控面板推一条告警』在检索素材中没有依据，属于未经支持的扩展」。
>
> → **reflect 并不只做"答案 vs 素材"的比对，它还会判"答案里的事在素材里有没有依据"** ——
> 这恰好是**忠实性**该做的事。语料当初把 ④ 当成"结构性盲区"，是**把 prompt 的能力想小了**。
>
> **真值表原样不动**（改期望值属于设计变更，要人判断）；
> 脚本把这 4 格记进 `ud_over` 桶（"期望不可判定、实际判了 rewrite"），
> 在**不可判定率**那一栏单独显示（实测 **0/12** → 不可判定率 **0%**）。

| 用例 | 期望 | 备注 |
|---|---|---|

> → **假阳性率均值 33.3%（8/24）里没有一条是忠实性误报** ——
> **8/8 的 critique 都明说"内容与素材一致"，8/8 都提到引用/来源标注缺失**。
> **忠实性误报实为 0/24**，引用维度是**唯一**的假阳性来源
> （这正是 good-1 / good-2 成对设计要分离出来的东西）。
>
> ⚠️ 这不是"reflect 有毛病"，是**prompt 的引用规则比真值表严** ——
> 真值表假设"好答案 = 不带引用也算好"，生产 prompt 不这么认为。两条数要分开报。
>
> ⚠️ **假阳性率逐遍会漂**：25.0% → 37.5% → 37.5%（极差 12.5 个百分点）。
> 48 格里只有 **1 格**（`B01-good-1-S`）三遍判定不完全一致（`end` / `rewrite` / `rewrite`），
> 其余 47 格三遍完全一致 —— **漂的是这一个格，不是全局噪声**。

## §6 指标

| 指标 | 定义 | 期望 |
|---|---|---|
| **真阳性率** | ①②③ 中判 `rewrite` 的比例 | 越高越好 |
| **假阳性率** | 好答案被判 `rewrite` 的比例 | **越低越好**（误报 → 反思不停 → 烧 token） |
| **不可判定率** | ④ 中判 `end` 的比例 | 记录为**已知边界**，不追求降低 |
| **改后改善率** | 判了 `rewrite` → synth 重写 → 重写后质量分比原来高多少 | **这个才是"反思有用"的证据** |

> **不可判定率单独报，不与真阳性混算** ——
> ④ 的 `end` 是**正确行为**（素材没说的东西不该被质疑），
> 把它算进"漏判"会低估反思节点。
>
> **报告必须分项报**：真阳性 / 假阳性 / 不可判定，
> 不要只报一个"准确率" —— 三者的业务含义完全不同。

## §7 数据文件格式（`test/eval_quality/data/reflect_ablation_cases.json`）

```json
[
  {
    "id": "B01-good-1-S",
    "question_id": "B01",
    "material_kind": "standard",
    "material_source": "txt/项目速览_md.txt:586 + :591 + txt/工业化评估与遗留清单_md.txt:227",
    "material": "……逐字照抄 §3 的素材……",
    "answer_kind": "good",
    "answer": "……",
    "expect_action": "end",
    "expect_class": "true_negative",
    "note": ""
  }
]
```

| 字段 | 取值 |
|---|---|
| `id` | `<题号>-<答案类型>-<素材类型>`，`素材类型` ∈ `S`(标准) / `N`(无关) |
| `material_kind` | `standard` / `irrelevant` |
| `answer_kind` | `good` / `contradiction` / `missing` / `offtopic` / `fabricated` |
| `expect_action` | `end` / `rewrite`（**注意：没有 `re_iterate`** —— 见下） |
| `expect_class` | `true_negative` / `false_positive` / `true_positive` / `undetermined` |

> **为什么 `expect_action` 里没有 `re_iterate`**：
> `REFLECT_PROMPT` 的硬约束（`reflect_prompt.py:56`）规定工具 timeout/error/empty 时不应判 `re_iterate`。
> 线 B 的 `tool_status` 恒为 `success`，不触发那条约束，
> 但 `re_iterate`（"素材不够，再查一次"）在**有素材**的情形下本来就不该出现 ——
> 若真出现，**记为异常并单独报告**，不并进四个指标。

## §9 本轮实测结果【实测 2026-11-27】

> 快照：`test/eval_quality/results/reflect_ablation_2026-11-27-3.json`
> （`meta.repeat = 3`，`cases_file_sha256 = 1746ab61…`，`git_commit = 10d5f90`）
> 执行体 MiniMax-M3.1-Flash，**144 次判定，判分错误 0**。
> （1 遍的旧快照 `reflect_ablation_2026-11-27-2.json` 保留，作为独立一次采样对照）

### 9.1 逐遍分布（每遍 = 一次独立 reflect 判定）

| 遍 | 真阳性率 | 假阳性率 | 不可判定率 | `re_iterate` 异常 | 故障 |
|---|---|---|---|---|---|
| 1 | 100.0% | 25.0% | 0.0% | 24 | 0 |
| 2 | 100.0% | 37.5% | 0.0% | 24 | 0 |
| 3 | 100.0% | 37.5% | 0.0% | 24 | 0 |

### 9.2 跨遍统计

| 指标 | 均值 | 最小 | 最大 | 极差 |
|---|---|---|---|---|
| **真阳性率** | **100.0%** | 100.0% | 100.0% | **0.0** |
| **假阳性率** | **33.3%** | 25.0% | 37.5% | **12.5 个百分点** |
| **不可判定率** | **0.0%** | 0.0% | 0.0% | 0.0 |

> ⚠️ **均值是 3 遍的估计，不是稳定基线** —— 假阳性率在 25% ↔ 37.5% 之间漂，
> 写进简历要带极差。

### 9.3 两条轴分开报（§5.2 的结论）

| 轴 | 判定次数 | 真阳性率 | 假阳性率 | 不可判定率 | `re_iterate` 率 |
|---|---|---|---|---|---|
| **轴一 · 标准素材**（测忠实性） | 72 | **100%**（36/36） | **33.3%**（8/24） | **0%**（0/12） | **0%** |
| **轴二 · 无关素材**（测素材充分性） | 72 | — | — | — | **100%**（72/72 判 `re_iterate`） |

### 9.4 四条结论

1. **忠实性判别力满分且零漂移**：矛盾型 / 缺项型 / 答非所问型 × 标准素材
   **36/36 全部判 `rewrite`**，三遍一模一样，一次没漏。
2. **假阳性 8/24 全部来自「引用」规则，不是忠实性误报** —— 8 条 critique
   **全部**明说"内容与素材一致"且**全部**提到引用/来源标注缺失。
   → **忠实性误报实为 0/24**（见 §5.4 的 good-1 / good-2 对照）。
3. **素材充分性 72/72 全对**：面对明显无关的素材，reflect 一律判 `re_iterate`
   （"素材不够 / 需要再查"），**没有一次误判成 `end`**。
   → 真值表在这一格上写的 `end` 是**按旧认知定的**，实测证明 reflect 判得更对。
4. **稳定性很好**：48 格里 **47 格三遍判定完全一致**；唯一翻转的是
   `B01-good-1-S`（`end` / `rewrite` / `rewrite`，众数 `rewrite`）
   —— 而它翻转的方向正是"无引用的好答案被判改"，
   **和另两个同型格（B03、B04）三遍都判 `rewrite` 是一致的**。
   → 假阳性率逐遍从 25% 涨到 37.5%，**涨的就是这一格**。

### 9.5 被实测推翻的一个前提

**编造型（④）× 标准素材 12/12 判 `rewrite`**，而真值表预期"判不出" ——
见 §5.3 的实测注。**"素材外编造是反思的结构性盲区"这条结论不成立。**

### 9.6 逐格明细（标准素材 24 格 × 3 遍）

| 用例 | 期望 | 3 遍判定 |
|---|---|---|
| B01-good-2-S / B02-good-1-S / B02-good-2-S / B03-good-2-S / B04-good-2-S | `end` | `end` `end` `end` |
| **B01-good-1-S** | `end` | **`end` `rewrite` `rewrite`** ← 唯一翻转格 |
| B03-good-1-S / B04-good-1-S | `end` | `rewrite` `rewrite` `rewrite` |
| B01/B02/B03/B04 × bad-1 / bad-2 / bad-3（12 格） | `rewrite` | `rewrite` `rewrite` `rewrite` |
| B01/B02/B03/B04 × bad-4（4 格，④ 编造） | `end`（不可判定） | `rewrite` `rewrite` `rewrite` |

> 无关素材的 24 格 × 3 遍 **72/72 判 `re_iterate`**，无一例外。

### 9.7 改后改善率（`--improve`，**"反思有没有用"的直接证据**）

快照 `test/eval_quality/results/reflect_ablation_2026-11-27-4.json`
（`meta.repeat = 3`，`judge_model = MiniMax-M2.5`）。

**测法**：对**多数判定为 `rewrite`** 的格 → 把 reflect 的 critique 喂给生产 `synth_node`
重写 → 用**线 A 同一把尺子**（`judge_answer_quality.py` + B 组 `must_contain`）给重写后的答案打分
→ 比原来高多少。**每格只重写一次**（单次采样）。

**参与重写的 19 格** = 12 格真·坏答案（①矛盾 / ②缺项 / ③答非所问）+ 4 格 ④编造 + 3 格 good-1。

| 组 | n | 均值 Δ`hit_rate` | 改善 / 不变 / 变差 |
|---|---:|---:|---|
| **真·坏答案**（①矛盾 / ②缺项 / ③答非所问） | 12 | **+0.5139** | **11 / 0 / 1** |
| ④编造型（reflect 本就误判这 4 格） | 4 | −0.0417 | 1 / 2 / 1 |
| good-1（假阳性，好答案被误改） | 3 | −0.1667 | 0 / 2 / 1 |
| **合计** | 19 | **+0.2895** | 12 / 4 / 3 |

**幻觉被修好 3 例**：`B02-bad-1-S` / `B03-bad-1-S` / `B04-bad-1-S`（幻觉 1 → 0）。

**三条读法**：

1. **反思对真·坏答案确实有用** —— 11/12 变好，平均 **+0.51 `hit_rate`**。
   这是设计稿 §7.3 说的"**这个才是反思有用的证据**"，也是
   `docs/status/测试现状.md` §8.5 结论 7「反思是否让答案变好，依然无法测量」
   这个缺口**第一次被填上**。
2. **但假阳性有代价** —— 3 个被误改的好答案里，`B01-good-1-S` 从 **1.0 掉到 0.5**（−0.5），
   这一组平均 **−0.17**。→ **"反思有用"和"反思误伤"必须分开报**，
   合起来的 **+0.29 是净值，掩盖了"+0.51 / −0.17"这个真实结构**。
3. **④编造那 4 格重写后基本原地踏步**（1 变好 / 2 不变 / 1 变差）——
   因为 reflect 在这 4 格上**本来就误判**（不可判定率 0%），重写只是让它换一种说法，
   并没有真的补上素材里没有的事实。

**⚠️ 这 19 格只重写了 1 次** → 单次采样，不能当基线。

### 9.8 两次独立跑的复现性（意外收获）

本轮跑了**两次完整的 3 遍**（`-3.json` 是纯判定，`-4.json` 是判定 + `--improve`），
两次是**独立进程、独立采样**（执行体 `temperature=0.7`，`configs/model_config.yaml` 的
`MODEL_DEFAULTS.minimax`）：

| 对比项 | 结果 |
|---|---|
| 逐遍三项指标 | **完全相同**（真阳性 100/100/100，假阳性 25.0/37.5/37.5%，不可判定 0/0/0） |
| 逐格三遍判定向量 | **48/48 格完全相同** |
| 每格的 critique 措辞 | **144/144 格都不同** ← 证明确实是两次独立采样，不是缓存 |

→ **reflect 的判定对这个语料非常稳，漂的是措辞不是判定**。
这条比单次跑更有说服力：**线 B 的四个指标可以当稳定结论用**（线 A 仍不行，
线 A 的瓶颈在检索端，波动来自真实检索而不是判定）。
