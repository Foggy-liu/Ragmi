## §2 Agent 层详解（v2.2 当前形态）

### 2.1 图结构

```text
START → iter
          ├─ tool_calls 存在        → tools → iter        （无条件边，ReAct 循环）
          ├─ 无 tool_call（含 READY） → synth → reflect   （无条件边）
          └─ expired=True           → END

reflect
  ├─ end        → END
  ├─ rewrite    → synth      （iter_count 重置）
  ├─ re_iterate → iter       （iter_count 重置）
  └─ reflection_count ≥ MAX_REFL → 强制 end

两条条件边在 expired=True 时都直接走 "__end__"（见 §2.5）。
```

代码位置：`agent/graph.py`（`build_graph()`，无 checkpointer）。

### 2.2 四个节点

| 节点 | 文件 | 职责 | 关键点 |
|---|---|---|---|
| **iter**（决策节点） | `agent/nodes/iter_node.py` | 纯决策：要不要调工具 | `bind_tools(ALL_TOOLS)`；不调工具时输出 `READY` 占位，**不写答案** |
| **tools**（工具节点） | LangGraph 官方 `ToolNode` | 执行工具 | `ToolNode(ALL_TOOLS, wrap_tool_call=status_wrapper)`，**不是自写子类** |
| **synth**（综合节点） | `agent/nodes/synth_node.py` | 基于素材写答案 | 不挂 `bind_tools`；按 `last_critique` 是否空切换 prompt 模式 |
| **reflect**（反思节点） | `agent/nodes/reflect_node.py` | 评审答案 | `with_structured_output(ReflectOutput)`（Pydantic），失败兜底 `rewrite` |

**决策 / 综合必须拆开** —— v2.1 的 `agent_node` 同时干这两件事，互相干扰（双角色 bug）。
`synth → reflect` 是**无条件边**：综合完自动接反思，不需要再问"现在该反思了吗"。

### 2.3 两个计数器（`agent/state.py`）

| 字段 | 上限 | reducer | 重置时机 |
|---|---|---|---|
| `iter_count` | `MAX_ITER=3` | `_reset_or_inc` | reflect 判 rewrite / re_iterate 时归 0 |
| `reflection_count` | `MAX_REFL=3` | `_inc_refl` | **永不重置**（绝对上限，防死循环） |

- `synth_count` / `MAX_SYNTH` **已删除**：职责转移给 reflect 后它结构性不可达
  （reflect 每次 rewrite 都把它写回 0，而所有回到 synth 的路径都必经 reflect）。
- **工具循环（iter → tools → iter）的唯一刹车是 `MAX_ITER`** —— 它根本不经过 reflect 节点。
  改路由时两个刹车都要保留。

### 2.4 工具状态（`agent/nodes/status_tool_wrapper.py`）

用官方钩子 `wrap_tool_call` 拦截每次工具调用，写 `state["tool_status"]`。

**key = 调用 id，不是工具名。** 调用 id 由模型生成、每次唯一。同一轮 MiniMax 常常
并发调同一个工具 2~3 次，按工具名做 key 会让后一次覆盖前一次（实测：成功的被 timeout 冲掉）。

value 结构：`{tool, status, code, retryable}`

| status | code | retryable | 触发条件 |
|---|---|---|---|
| `success` | `OK` | — | 工具返回非空内容 |
| `empty` | `EMPTY_RESULT` | — | 工具返回空字符串 |
| `timeout` | `TOOL_TIMEOUT` | ✅ | 工具抛 `AgentTimeoutError` |
| `error` | `TOOL_ERROR` | ❌ | 工具抛 `AgentToolError` 或其他异常 |

失败时 ToolMessage 的 content 是**结构化 JSON**：
```json
{"code": "TOOL_TIMEOUT", "status": "timeout", "retryable": true, "message": "调用超时：..."}
```
成功时 content 保持原样（原始检索片段），不包装。

`retryable` 目前**只能做到"timeout=True，其余 False"** —— 更细的分类（限流/服务不可用 → 可重试，
参数错/代码 bug → 不可重试）还需要 `RetrievalError` 带更细的错误码。
✅ 2026-11-17（P2-7）：`core/rags/rags.py` 的 `except Exception: return []` 已改掉 ——
检索失败抛 `RetrievalError`（保留 `__cause__`），工具层据此区分
「超时 → `AgentTimeoutError`（可重试）」和「其他 → `AgentToolError`（不可重试）」。

### 2.5 超时机制（3 层，`configs/agent_config.yaml`）

```text
第 1 层  异常归一化   agent/errors.py
         AgentError / AgentTimeoutError（可重试） / AgentToolError（不可重试）
         工具层把第三方异常翻译成自家异常，只翻译一次

第 2 层  单次动作超时 agent/timeout.py :: Timer
         Timer(TOOL_TIMEOUT).call(fn, ...) —— 超时抛 AgentTimeoutError

第 3 层  整图总时限   state["deadline"] + agent/timeout.py :: is_expired()
         runtime.ask() 写入 deadline = time.time() + TOTAL_TIMEOUT
         每个节点动手前协作式检查，超时就地收手
```

配置：`timeout.{llm:30, tool:30, total:90}`，由 `agent/constants.py` 加载并 assert 校验。

### 2.6 循环预算（`agent/runtime.py:25-26`）

```python
_STEPS_PER_ROUND = 2 * MAX_ITER + 2          # = 8
RECURSION_LIMIT = _STEPS_PER_ROUND * (MAX_REFL + 1) + 10   # = 42
```

最坏情况 32 步（8×4）会撞 LangGraph 默认上限 25 → `GraphRecursionError`。
显式推导而不是写死，以后改常量不会再撞。

### 2.7 素材来源（`agent/nodes/material.py`）

`collect_round_material(messages)` 取"**最后一条 HumanMessage 之后的全部 ToolMessage**"，
iter / synth / reflect **三个节点统一用它取素材**。

### 2.8 状态 Schema（9 字段，`agent/state.py`）

```python
messages:           Annotated[list, add_messages]
iter_count:         Annotated[int, _inc_iter]        # 重置或累加
reflection_count:   Annotated[int, _inc_refl]        # 纯累加
tool_status:        Annotated[dict[str, dict], _merge_tool_status]
last_critique:      str
next_action:        str      # end / rewrite / re_iterate
deadline:           float    # 图级总时限（绝对时间戳）
expired:            bool     # 已超时标志 → 条件边直接 END
last_answer:        str      # synth 最近一次写出的答案（超时兜底交出去）
```

**字段必须显式声明**，否则 LangGraph 不会把它写进 state
（`next_action` 曾经因此恒为缺省值，`runtime.last_action` 恒为 `"end"`）。

`last_answer` 不能靠"倒着找最后一条 AIMessage"推导 —— messages 里混着 iter 的占位消息
（`"READY"` / `"已达迭代上限，结束"`），会把占位消息当答案交出去。

**内部信号是唯一的**（`agent/constants.py`）：

```python
SIGNAL_READY    = "READY"
SIGNAL_MAX_ITER = "已达迭代上限，结束"
SIGNAL_EXPIRED  = "已达总时限，停止思考"
INTERNAL_SIGNALS = frozenset({SIGNAL_READY, SIGNAL_MAX_ITER, SIGNAL_EXPIRED})
```

生产方（`iter_node`）和消费方（`runtime._extract_answer`）都引用常量，不写字面量；
测试侧 `test/helpers.py` 也 import 它 —— 否则"答案不是占位"那条断言会变成永真。

**2026-11-17 修**（F9a_x）：`_extract_answer` 之前只跳过 `READY`，
所以图超时收摊时会把「已达总时限，停止思考」当成答案交给用户。
现在跳过全部 `INTERNAL_SIGNALS`，图停在占位上时 `ask()` 兜底成
「回答超时：思考时间超过总时限」。

### 2.9 运行时返回（`agent/runtime.py::ask`）

- `debug=False` → `str`
- `debug=True` → `{"answer", "iter_count", "reflection_count", "tool_called", "last_action"}`（**5 字段**）
- `score` 字段**已删除**（v2.1 由 `last_reflection_pass` 推导，v2.2 用 `last_action` 替代）
- 异常统一被 `except Exception` 吞成友好消息，**不抛 HTTP 500**

### 2.10 工具清单（`agent/tools/__init__.py`）

| 工具 | 实现 | 状态 |
|---|---|---|
| `rag_search(query)` | `RagModel.retrieve()` top_k=5 | ✅ 真实可用（懒加载单例） |
| `calculator(expr)` | **AST 白名单求值**（`ast.parse` + 手工递归，无 `eval`） | ✅ 2026-11-17 修掉 RCE（**P1-2**） |
| `weather(city)` | 固定字符串 | 🔴 占位 |
| `web_search(query)` | 固定字符串 | 🔴 占位 |

`calculator` 原来写的是 `str(eval(expression))` —— **直接执行 LLM 传来的字符串**，
`__import__('os').system(...)` 一击即中。现在只认 `+ - * / // % **` 和一元正负号、
只准数字字面量（`bool` 显式排除 —— 它是 `int` 的子类），指数上限 100、表达式长度上限 200，
其余一律返回 `ERROR: ...` 字符串（不抛异常 —— 工具层要的是"给模型一句能读的失败原因"）。
覆盖用例见 `test/test_tools.py`（26 条）。

`rag_search` 检索为空时返回**空字符串**（v2.2 改的）—— 原来塞中文兜底串，
会让 status 永远判成 `success`，"检索为空"这个信号就丢了。

`rag_search` 的 **docstring 就是 Function Calling 的描述**，LLM 全靠它决定"什么时候该查知识库"，
这是**领域耦合度最高的一行代码**（详见 `docs/note/项目领域耦合.md`）。

### 2.11 ⚠️ 没有多轮记忆

- `runtime.ask()` 每次 invoke 都传全新的 `{"messages": [HumanMessage(question)]}`
- `session_id` → `thread_id` 传了，但 `workflow.compile()` **没传 checkpointer**，LangGraph 直接丢掉
- 三个 LLM 节点**从不把 `state["messages"]` 发给 LLM**（每次从零拼 prompt：
  原问题 + 工具素材 + 计数器）
- **引燃点**：一旦为了做记忆而把 `state["messages"]` 传给 LLM（最自然的实现方式），
  iter 的占位消息（`"READY"`）会一起进历史，且悬空 tool_calls 会让 MiniMax 直接 400。
  **顺序必须是：先修占位消息 → 再上 checkpointer。**

### 2.12 think 剥离（`agent/llm_wrapper.py`）

推理模型会在 `AIMessage.content` 里塞 `<think>…</think>`，直接污染三处：
① 传给 synth 的答案 ② Pydantic 结构化输出解析 ③ 写进 `state["messages"]` 的历史。

`ThinkingStripRunnable` 包装在 `bind_tools` / `with_structured_output` / `with_config` 之后，
invoke 时用正则剥掉完整块**和**孤儿 `</think>`（推理模型被 max_tokens 截断时会只留后半截）。

**三个 LLM 节点全部包了**：`iter_node.py:38`、`synth_node.py:32`、`reflect_node.py:49`。

```text
        │  utils/docs/txt_main.py（Scanner + MD5 哈希过滤，增量）
        │  哈希索引：txt/.file_filter.json
        │  规则：MD5 相同（= 内容相同）且产物文件仍存在 → 跳过
        │     ⚠️ 2026-11-25 修：此前还要求 mtime 未变，而上传接口用 'wb' 覆盖写源文件
        │        → 源文件 mtime 必然比产物新 → 每次上传都被判成"需要处理"，
        │        而 output.py 永不覆盖、只会造 _1/_2/... 副本 → txt/ 里堆出同内容副本。
        │        现在 mtime 不再参与判定："内容变了哈希就变"由哈希本身回答。
        │     索引只存**文件名**（不存绝对路径）→ 宿主机与容器共用同一份索引。
        ▼
txt/*.txt                           ← 解析产物
        │  PDF: pymupdf + pytesseract OCR(chi_sim+eng) + CLAHE 二值化
        │  DOCX: python-docx   MD: markdown → HTML → BeautifulSoup
        ▼
utils/txt_spliter/spliter.py
        │  RecursiveCharacterTextSplitter(chunk_size=300, chunk_overlap=30)
        │  ✅ 参数来自 configs/model_config.yaml 的 EMBEDDING_CONFIG.text_splitter
        │     （2026-11-17 修，**P1-7**；此前写死 300、YAML 里的 280 从未被读取）
        │  + 自定义小块合并（< 80 字符并入下一块，上限 300）
        ▼
utils/txt_spliter/vector_main.py
        │  ① 直接 HTTP POST {OLLAMA}/api/embed，batch=32
        │     模型名 / base_url 由 resolve_embed_settings() 在**调用时**解析（2026-11-17 修，P3-9；
        │     此前在模块导入时读环境变量 → .env 还没 load_dotenv → 被静默忽略）
        │  ② 建带时间戳集合 txt_data_<ts>，schema = {id, vector, text}
        │  ③ insert
        │  ④ create_index(AUTOINDEX, COSINE)
        │  ⑤ alter_alias / create_alias：原子把别名 txt_data 指向新集合
        │     ⚠️ 旧集合永不删除
        │  ⚠️ embed / insert 无 try/except
        ▼
Milvus: 别名 "txt_data" → 实际集合 "txt_data_<ts>"
```

**别名原子切换是本项目工程做得最好的一处**：先建新集合 → 灌数据 → 建索引 → 最后切别名，
任何一步失败旧别名还指向老集合，服务不中断。

> ⚠️ **但切别名的瞬间，新集合的数据可能还没对 query 可见**（2026-11-16 实测）。
> Milvus 的 `insert()` 是**异步落盘**的 —— 返回只代表 WAL 收下，segment 还没 flush。
> 所以 `insert → create_index → load_collection → alter_alias` 走完的那一刻，
> `query()` 可能返回 **0 行**（1667 行时命中；3 行的对照实验里延迟为 0，**窗口大小跟数据量有关**）。
> 影响：切完别名后的**很短一段时间**内，检索可能查不到刚灌进去的数据（服务不会崩，
> 只是返回空 → Agent 侧表现为 `empty` 状态）。数据最终一定会可见（`count(*)` 实测 1667，没丢）。
> 修法（产品侧，本轮**未做**）：`alter_alias` 之后显式 `flush()` + 轮询 `count(*)` > 0 再切别名。

### 4.2 检索（在线，每问一次）

```text
query → core/rags/rags.py::_search_similar_chunks(query, top_k=5)
      → EmbeddingModel.embedding（复用，模型名/base_url 来自 YAML+环境变量，timeout=60s）
        .embed_query(query)
      → pymilvus client.search(collection_name=别名, limit=5, output_fields=['text'])
      → List[str]   ← 纯 chunk，不含来源 / 页码 / 相似度分数
```

**嵌入模型名的唯一事实来源**：`EmbeddingModel._resolve_model_name()`
（`EMBEDDING_MODEL` 环境变量 > YAML `DEFAULT_EMBEDDING_MODEL.model_name`）。
索引端 `vector_main.py` 走 `resolve_embed_settings()` 取同一个值 —— ⚠️ 两端分叉
**不会报错**（`bge-large` 与 `bge-m3` 都是 1024 维），只会让检索结果全是噪声（P1-9）。

**检索失败 ≠ 检索为空**（P2-7）：失败抛 `RetrievalError`（保留原始异常作 `__cause__`），
为空才返回 `[]`。`/rag` 直连链路吞掉异常保持 200；Agent 工具层把异常翻译成
`AgentToolError`（不可重试）/ `AgentTimeoutError`（可重试）。

### 5.2 后端与依赖注入

```text
main.py
 ├─ lifespan: setup_logging → 建 documents/ → Milvus 探活（失败不阻塞启动）
 ├─ model_manager = ModelManager(); load_config_models()
 ├─ default_model = LLMmodel.create_minimax()      ← 读 YAML DEFAULT_MODEL
 ├─ app.state.model_manager = model_manager
 └─ include_router × 4 + mount("/api", appfile)
```

**依赖注入方式**：`api/dependencies.py` 的 `get_model_manager(request)` 取 `request.app.state.model_manager`。
FastAPI 的 `Depends` **按请求缓存**（`use_cache=True` 的意思是"这次请求里依赖被调几次都只算一次"），
**跨请求不复用** —— 所以「贵」的依赖必须自己做成 app 级单例：

| 依赖 | 每次请求的成本 | 做法 |
|---|---|---|
| `get_chat_model` | 极低（只存一下 model_manager） | 每次请求现建，无所谓 |
| `get_rag_model` | **~0.45 秒**（其中 ~0.42s 是建 embedding HTTP 客户端：同步+异步两个 httpx 客户端各自建 SSL 上下文；另有 YAML 读 + 两次探活 RPC） | **app 级单例**：挂在 `app.state.rag_model` 上，全进程只建一次（P1-4）。连不上时**不缓存**，下次请求重试 |

`/agent/chat` 路由**不用** `Depends`，直接 `from agent.runtime import ask` —— 这就是 Agent 能自给自足的原因。

### 5.3 数据存储选型

| 用途 | 选型 | 评价 |
|---|---|---|
| 向量存储 | **Milvus standalone**（Docker） | ✅ 选型正确：HNSW/IVF/AUTOINDEX、标量过滤、别名原子切换，生产级 |
| 文档元数据 | **本地文件系统**（`documents/` + `txt/` + `txt/.file_filter.json`） | 🟡 单机够用，多副本部署会不一致 |
| 会话历史 | **进程内存 dict**（`utils/message/message.py`） | 🔴 多 worker / 重启即丢；Agent 侧更是完全没历史 |

**Milvus 用法值得肯定的两点**：
1. **别名原子切换**（`alter_alias`/`create_alias`）—— 重建索引不中断服务。

- 检索结果**只返回 `text`**，丢掉 `id`/来源文件/页码/相似度分数 → 无法做引用溯源、无法做去重、无法 rerank。

- `vector_main.py` 的 embed/insert **无 try/except** → 中途失败留下半截集合。
- ~~`load_dotenv` 导入未调用 → `.env` 的 `OLLAMA_BASE_URL` / `EMBEDDING_MODEL` 被忽略~~
  —— ✅ 2026-11-17 已修（P3-9），改由 `resolve_embed_settings()` 在调用时解析。

#### D7 pymilvus 2.6 只认 `uri`，`host`/`port` 会被静默忽略 —— 宿主机上"能用"，容器里必失败

**2026-11-17 部署时踩到。**`pymilvus 2.6.14` 的 `MilvusClient.__init__` 签名是
`(uri="http://localhost:19530", user, password, db_name, token, timeout, **kwargs)` ——
**没有 `host` / `port` 参数**。写成 `MilvusClient(host=..., port=...)` 时，这两个 key 会落进
`**kwargs` 被 `ConnectionConfig.from_uri()` 忽略，**实际连的是默认的 `http://localhost:19530`**。

| 环境 | `localhost` 指向 | 结果 |
|---|---|---|
| 宿主机裸跑 | 宿主机自己（= Milvus 所在） | **碰巧能用** —— 这个 bug 一直没暴露 |
| 容器内 | 容器自己 | **必然失败**：`MilvusException: Fail connecting to server on localhost:19530` |

> 这个错最阴的地方：**宿主机测试全绿，容器起不来**。而宿主机 `127.0.0.1` 恰好就是 Milvus，
> 所以"改成 `uri=`"在宿主机上没有任何行为差异，只有容器才暴露。

**已修的三处**（全部改成 `uri=f"http://{host}:{port}"`）：

| 位置 | 修前 | 修后 |
|---|---|---|
| `main.py:41` lifespan 探活 | `MilvusClient(host=..., port=...)` | `MilvusClient(uri=...)` |
| `core/rags/rags.py:86` | 已是 `uri=` ✅ | — |
| `utils/txt_spliter/vector_main.py:90` | 已是 `uri=` ✅ | — |
| `test/test_vector_split.py:50` | `MilvusClient(host="127.0.0.1", port="19530")` | `MilvusClient(uri="http://127.0.0.1:19530")` |

**教训**：`MilvusClient` 一律传 `uri`；任何"host/port 也能用"的写法在容器里都是定时炸弹。

#### D8 `requirements.txt` 必须锁**全依赖闭包**，不能只锁直接依赖

**2026-11-17 部署时踩到。**只锁直接依赖时，pip 会把传递依赖解析到**更新的版本**，
容器里直接炸：

同类漂移还有 `opencv-python 4.12→5.0`、`pymupdf 1.26→2.1`、`numpy 2.2→2.4`。

**已修**：`requirements.txt` 改成 **139 包全锁定**，闭包按 **linux 标记**求（容器是 linux，
宿主机是 windows —— 标记不同会解出不同的闭包）。改依赖的顺序：先改「直接依赖」段，

#### D10 宿主机上的旧后端会"截胡" 8000 端口

#### 5.6.4 镜像比代码旧 → 静默检索噪声（2026-11-25 实测踩到）

换 bge-m3 重建完索引后，**宿主机后端和容器后端对同一个问题的答案不一样**：

| | 解析出的嵌入模型 | `/rag` 回答「普通诉讼时效期间是多久」 |
|---|---|---|
| 宿主机 `python main.py` | `bge-m3:latest` | ✅ **普通诉讼时效期间为三年** |
| 容器 `ragmi-api`（旧镜像） | `bge-large:latest` | ❌ **所给文档未包含普通诉讼时效期间的信息** |

**根因**：`docker-compose.yml` 里 api 服务只挂了 `./documents` 和 `./txt`，
**`configs/` 是在 `Dockerfile` 的 `COPY . .` 阶段烤进镜像的** → 容器拿到的是**构建那一刻**的
`model_config.yaml`。索引是宿主机用 bge-m3 建的，容器用 bge-large 去查 → **两边维度都是 1024，
Milvus 不报错，检索结果全是噪声** —— 这正是 CLAUDE.md 里点名的那条"静默分叉"路径。

同一个坑还有第二层：容器里的 `utils/docs/manager/filter.py` 也是旧的，
拿新格式索引（只存文件名）去跑旧代码（按绝对路径 `Path(...).exists()` 判断）
→ **恒为 False → 每次上传都重新解析 → 又造出一串 `_1` 副本**。

**修法**：`docker compose build api` + `up -d --force-recreate`（`requirements.txt` 没动，
pip 层命中缓存，只重建 `COPY . .` 一层，实测 **几十秒**）。修完复测：

- 容器内 `EmbeddingModel._resolve_model_name()` → `bge-m3:latest` ✅
- 容器内 `/rag`「普通诉讼时效期间是多久」→ **普通诉讼时效期间为三年** ✅
- 容器内 `/rag`「学习计划有哪几个阶段」→ **4 个阶段**（表格完整）✅
- 容器内跑 `utils.docs.txt_main.main()` → **跳过 12 个 / 需要处理 0 个** ✅

> 💡 **结论写进检查项**：`configs/model_config.yaml` 一改，**容器必须重建**，否则索引端和
> 检索端分叉。这不是"忘了重启"，是"重启也没用 —— 得重建镜像"。
> 另一个可选做法是把 `./configs:/app/configs` 也挂进去，代价是镜像不再自包含、
> 配置改动不再需要重建（但也就失去了"镜像即版本"的一致性保证）。
