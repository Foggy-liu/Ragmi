### 3.2 B 类 · e2e —— 通过，但 25 分钟

```bash
pytest test/test_vector_split.py -v -s
# 1 passed in 1529.34s (0:25:29)
```

实测输出：`1667` 个片段 → alias `txt_data` → `txt_data_1794754853`，`query` 返回 10 行。

**为什么慢**：每次跑都要把 `txt/` 下 22 个文件（1.1 MB）重新切成 **1667 块**并**全量重新 embed**
（bge-large，1024 维，CPU 推理）。实测单批 32 块 ≈ 18 秒 → 光 embedding 就 ~16 分钟。

> **2026-11-16 踩过的坑（已修 —— 改的是测试，不是产品）**：
> 当晚第一次跑全量 `pytest -v` 时这个用例**失败**了 —— `query()` 返回 0 行。
> 事后查证：**数据没丢**（`count(*)` = 1667，几分钟后同一个 query 也查得到）。
> 根因是 **Milvus 的 `insert()` 异步落盘**：`insert()` 返回只代表 WAL 收下了，
> segment 还没 flush，所以在 `insert → create_index → load_collection → alter_alias`
> 走完的**瞬间**，query 可能还看不到数据（1667 行时命中；3 行的对照实验里延迟为 0）。
> 修法：断言改成**轮询**（`test/test_vector_split.py::_wait_for_rows`，最多等 180 秒），
> 而不是查一次就下结论。产品代码 `utils/txt_spliter/vector_main.py` **一行没动**。
> **复验通过**：`pytest test/test_vector_split.py -v` → **1 passed in 1792.13s（29:52）**；
> 复验后 alias 指向 `txt_data_1794845929`，`count(*)` = 1667（数据一条没少）。

**结论**：它是"改了摄取链路后跑一次"的**验收用例**，不是"每次提交都跑"的回归用例。
~~目前它混在 `pytest` 默认流程里，会让人以为 `pytest` 很慢 —— 建议加标记让默认跳过。~~
→ **2026-11-16 已解决**：加了 `@pytest.mark.slow`，`pytest -m "not slow and not e2e"` 会跳过它。

## §4 归档评估集在 v2.2 上的实测跑分（本次最有价值的发现）

`archive/scripts/run_agent_eval.py`（真实 LLM 模式，MiniMax + Milvus）跑完 12 个 case：

```
Tool Routing Accuracy: 8/12 = 66.7%
Agent Stability      : 12/12 = 100.0%
Exceptions: 0,  Wrong Tool: 4
```

### 4.1 66.7% 是脚本口径失真

脚本用 `actual = "rag" if tool_called else "chat"`，而 `tool_called` 的真实定义是
`bool(state["tool_status"])`（`agent/runtime.py:113`）—— **调了任何工具都为 True**。
逐 case 复查实际调了哪个工具后：

| Case | 期望 | 脚本判定 | 实际调用 | 真实结论 |
|---|---|---|---|---|
| T02 `1+1等于多少` | chat | ✗ rag | `calculator` | ✅ **判错，实际路由正确**（v1 时代没 calculator，期望值才是 chat） |
| T09 `上海今天天气怎么样` | chat | ✗ rag | `weather` | ✅ **判错，实际路由正确**（同上） |
| T06 `RAG 的核心定义是什么` | rag | ✗ chat | 无 | ❌ **真错**：该走检索却没走 |
| T10 `介绍下 LangGraph` | chat | ✗ rag | `rag_search` ×3 | ❌ **真错**：不该检索却检索 3 轮，`iter_count` 打满 `MAX_ITER=3`，单 case 耗时 106 秒 |

### 4.2 修正后的数字

**按"是否调了正确工具"重新计：10/12 = 83.3%**（真正错的只有 T06、T10）。

| 版本 | 工具路由准确率 | 稳定性 | 来源 |
|---|---|---|---|
| v1（2026-07） | 75%（9/12） | — | `v1_baseline_results.json`（历史快照） |
| v2（2026-08） | 92% | — | 历史记录 |
| v2.1（2026-08） | 91.7% | — | `agent_eval_results.json`（历史快照，未复跑） |
| **v2.2（2026-11-15 实测）** | **83.3%**（脚本口径 66.7%） | **100%（0 异常）** | 本次实跑 |

### 4.3 结论（与 v2.1 同一个诚实结论）

**反思机制不提升路由准确率。** T06（"RAG 的核心定义是什么"）这类路由错误事后修不了 ——
v2.1 当时就得出过同样结论。v2.2 的价值在别处：

- 稳定性从"会抛异常"变成 **12/12 零异常**
- `tool_calls` 悬空从 **2/7 → 0**
- 工具状态**结构化可观测**（`status` / `code` / `retryable`）

### 4.4 ⚠️ 但这个数字还不可复用

评估集的 `expected_tool` 是 **v1 时代的二值设计**（只有 `chat` / `rag`），
**没跟上 v2.2 的 4 个工具**（`rag_search` / `calculator` / `weather` / `web_search`）。
要让这个指标有意义，得先把评估集改成"期望工具名"。

### 复现命令

```bash
# 快回归（秒级；跳过 slow 与 e2e）
pytest -m "not slow and not e2e" -v

# 浏览器层（需 Playwright + Chromium）
pytest -m e2e -v --tracing=retain-on-failure

# 真环境冒烟（慢、花钱；含 25 分 29 秒的向量切分）
pytest -m slow -v

# 只跑冒烟、跳过 25 分钟的向量切分
pytest -m slow -v --deselect test/test_vector_split.py

# C 类（探针，从仓库根目录跑）
PYTHONIOENCODING=utf-8 python test/probes/probe_tool_status_overwrite.py
PYTHONIOENCODING=utf-8 python test/probes/probe_dangling_tool_calls.py
PYTHONIOENCODING=utf-8 python test/probes/probe_minimax_dangling_400.py

# D 类（归档脚本，必须设 PYTHONPATH 指向仓库根）
cd test/archive/scripts
PYTHONIOENCODING=utf-8 PYTHONPATH="D:/PythonProject/ragmi" python run_agent_eval.py
```

> Windows 上 `PYTHONIOENCODING=utf-8` 是必须的 —— 脚本里打印 `✓` / `✗` 会触发 GBK 编码错误。
