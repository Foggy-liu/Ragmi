## §0 一句话结论 + 四个真实数字

| 指标 | 实测值（2026-11-18 / 2026-11-25 更新） | 说明 |
|---|---|---|
| **总收集项** | **112** | `pytest --collect-only`（2026-11-25 加 `test/test_file_filter.py` 9 条） |
| **快回归** | **99 passed / 0 failed / 7.5–8.9 秒**（Milvus 在线时，2026-11-25 复测 6 次） | 不调真实 LLM；⚠️ **Milvus 停着会变成 ~109 秒**（见下方注） |
| **浏览器端到端** | **8 passed / 0 failed / 65.15 秒** | Playwright + 假后端 + 真 Streamlit |
| **真环境冒烟** | **4 passed / 0 failed / 74.17 秒** | 真 MiniMax + 真 Milvus（花钱） |

> ⚠️ **快回归的耗时取决于 Milvus 在不在跑**（2026-11-25 在 99 条用例上重测）：
> Milvus **在线 → 7.5–8.9 秒**（连续 6 次实测：8.89 / 7.49 / 7.60 / 7.89 / 7.83 / 7.72 s）；
> Milvus **停着 → 108.70 秒**。
> Milvus 停着时的原因是 `main.py` 的 lifespan 会探一次 Milvus（`MilvusClient.list_collections()`），
> **不通时这次探活阻塞约 10–11 秒**；而 `test_api_contract.py` 的 12 个用例**各自新建 `TestClient`**
> → 每个用例都重新触发一次 lifespan。
> **慢的不是用例，是探活**（`--durations=5` 里 12 条 setup 各占 ~11.1 s 就是它）。
>
> Milvus 在线时成本也在同样那 12 个 lifespan 里，只是每次只花 **~0.55 s**
> （`OllamaEmbeddings()` 构造 = httpx 客户端 + SSL 上下文，占 0.46 s）→ 12 × 0.55 ≈ 6.7 s；
> **其余 87 条只要 1.43 s**（`test_api_contract.py` 单跑 6.66 s，其余单跑 1.43 s）。
>
> ⚠️ **这个数对机器负载敏感。**同一天在**刚跑完索引重建 + Docker 镜像重建**（机器满载）时，
> 同一套用例测到 **19.3–21.3 s**；机器缓下来后又回到 7.5–8.9 s。
> 差异来自**每个 lifespan 的固定开销在 ~1.6 s 与 ~0.55 s 之间浮动**。
> **不是代码改动、也不是嵌入模型切换造成的** —— 两个候选解释都实测排除：
> ① **Ollama 模型冷/热无差别**（先把 bge-m3 卸载再跑 → 7.83 s；热着跑 → 7.72 s）；
> ② **`import main` 不是元凶**（`OllamaEmbeddings()` 构造：裸进程 0.46 s，import 过 `main` 之后 0.48 s）。

**一句话**：**该有的回归网都在，逻辑层是绿的；但性能维度的测试是 0 条** ——
并发、压力、容量上限**一条都没测**（见 §4），这是当前最大的测试盲区。

## §0.1 先搞懂：什么叫"测试类型"

> 这一节给不了解测试的人。术语只出现一次，后面都用大白话。

| 测试类型 | 大白话 | 回答什么问题 | 快不快 | 本项目对应 |
|---|---|---|---|---|
| **单元测试** | 一次只测一个小函数，给它特定输入，看输出对不对 | "这段代码算得对吗？" | 毫秒 | `test_tools.py` `test_splitter.py` `test_rag_model.py` |
| **流程测试** | 把整个 Agent 图跑一遍，用假 LLM 控制它的每个决策 | "Agent 的流程走不走得通？会不会死循环？" | 秒 | `test_agent_flow.py` `test_agent_timeout.py` |
| **接口测试** | 直接调后端接口，看请求/响应字段对不对 | "前端传的东西后端收得对吗？" | 秒 | `test_api_contract.py` |
| **集成测试** | 换成真数据库、真模型，看真实依赖通不通 | "真的连上 Milvus / MiniMax 能跑吗？" | 分钟（花钱） | `test_eval_smoke.py` `test_vector_split.py` |
| **端到端测试** | 开真浏览器点真页面 | "用户实际用起来顺不顺？" | 分钟 | `test/e2e/test_browser_e2e.py` `test/e2e/real_stack_check.py` |
| **性能测试** | 压着打，看多快、多久崩 | "能扛多少并发？延迟多少？" | 取决于压多久 | ⚠️ **没有**（§4） |

**关键区别（决定测试有没有意义）**：

- **单元/流程测试用假的**（假 LLM、假检索、假后端）→ 快、稳、能精确制造异常 → **用来防回归**
- **集成/端到端用真的** → 慢、贵、不稳定 → **用来确认"真的能跑"**

本项目的分层就是这个思路：**逻辑用假的钉死，链路用真的确认**。

## §2 怎么衡量一个机制好不好（指标定义）

> 你问的"我不懂要用什么数据来衡量这些机制"——这里是答案。
> 每个机制给出：**指标名 / 怎么算 / 合格线 / 本项目实测值 / 达没达标**。

### 2.1 超时机制

| 指标 | 怎么算 | 合格线 | 实测 | 达标 |
|---|---|---|---|---|
| **超时兜底正确率** | 超时发生后，返回给用户的是**人类话术**（不是内部占位、不是异常栈）的次数 ÷ 超时总次数 | **100%** | F9a_x / F9b / F9c 三条用例 + S4 实跑全过 | ✅ |
| **超时上界** | 从 `ask()` 进入到返回的最坏耗时 | ≤ `TOTAL_TIMEOUT(90s)` + 收尾开销 | 实测最慢单次 **32.6 s**（`/agent/chat` 真实 ReAct 循环） | ✅ |
| **超时发生率** | 真跑时有多少比例真的撞上超时 | 越低越好，**>5% 就要查** | 12 case 实跑 **0 次超时** | ✅ |
| **工具超时识别率** | 工具抛 `AgentTimeoutError` 时，状态被记成 `timeout` 而不是 `error` 的比例 | **100%** | 单测 + 探针各一条，全过 | ✅ |
| **崩溃不外泄** | 底层异常被翻译成自家异常、且 API 层仍返 200 的比例 | **100%** | `ask()` 兜底 + `/rag` 吞异常两条用例全过 | ✅ |

### 2.2 反思机制（Reflection）

| 指标 | 怎么算 | 合格线 | 实测（12 case 真 LLM） | 达标 |
|---|---|---|---|---|
| **反思失控率** | 撞到 `MAX_REFL=3` 兜底强收手的比例 | **< 10%** | **0%** —— 12 个 case 最多反思 2 轮 | ✅ |
| **最终决策分布** | 最后一轮 reflect 判 `end`/`rewrite`/`re_iterate` 的占比 | `re_iterate` 不该占多数 | **`{end: 12}`** —— 从不失控 | ✅ |
| **反思轮数分布** | `reflection_count` 的取值分布 | 应集中在 1 | **`{1: 10, 2: 2}`** —— **10/12 的 case 反思只跑了 1 轮** | ⚠️ 多数 case 反思**没做事** |
| **反思有效率** | 判 `rewrite` 后**答案是否真的变好** | — | ❌ **无法自动测量** —— 需要 LLM-as-judge，且天然 flaky（§4 缺口 5） | ❌ 盲区 |
| **刹车有效性** | 恒判 `re_iterate` 时能否停下 | 必须停 | F7 用例：节点进 4 次、LLM 只调 3 次 → **能停** | ✅ |

> **怎么读这组数字**：`reflection_count=1` 意味着 reflect 节点**只跑了一次就判 end** ——
> 它没有改写、没有重试，等于"反思机制在这 10 个 case 上是空转的"。
> `reflection_count=2` 意味着第一轮判了 `rewrite`/`re_iterate`（图才会回到 reflect），
> 第二轮才判 `end`。**这两个数字要一起看**，只看最终决策会得出"反思从不介入"的错误结论。

## §5 归档评估集的历史（口径失真的教训）

> **这一节保留，因为它解释了"83.3%"这个数字为什么曾经不可信。**

`test/eval/run_agent_eval.py`（当时在 `test/archive/scripts/`，2026-11-22 迁出）在 **2026-11-15**
用旧口径跑出 **66.7%**，逐 case 复查后修正为 **83.3%**（10/12）。失真的原因：

| Case | 期望 | 脚本判定 | 实际调用 | 真实结论 |
|---|---|---|---|---|
| T02 `1+1等于多少` | chat | ✗ rag | `calculator` | ✅ **脚本判错，实际路由正确**（v1 时代没 calculator，期望值才是 chat） |
| T09 `上海今天天气怎么样` | chat | ✗ rag | `weather` | ✅ **脚本判错，实际路由正确**（同上） |
| T06 `RAG 的核心定义是什么` | rag | ✗ chat | 无 | ❌ **真错**：该走检索却没走 |
| T10 `介绍下 LangGraph` | chat | ✗ rag | `rag_search` ×3 | ❌ **真错**：不该检索却检索 3 轮，`iter_count` 打满，单 case 耗时 106 秒 |

**根因**：脚本用 `tool_called = bool(state["tool_status"])` 判定"是否走检索" ——
而这在 v2.2 里是"**调了任何工具**"。调 `calculator` / `weather` 被误判成 `rag`。

**2026-11-18 修复**：改为直接读 `AIMessage.tool_calls` 里的**工具名**，
只有真的调了 `rag_search` 才算走检索。

> **另外两个遗留问题（尚未解决）**：
> 1. **评估集口径仍是二值**（`chat` / `rag`），没跟上 v2.2 的 4 个工具
>    （`rag_search` / `calculator` / `weather` / `web_search`）→ **P0-1 未闭环**。
> 2. **`reflect` 的"工具失败时不判 `re_iterate`"硬约束**在真实 LLM 上验证过一次
>    （S4，见 §3.2），但**单次采样，不能当稳定指标**。

### ⚠️ 修好脚本后重跑的结果（2026-11-18）

| 口径 | 日期 | 路由准确率 | 稳定性 |
|---|---|---|---|
| 旧口径（`tool_called` = 调了任何工具） | 2026-11-15 | 66.7%（8/12） | 100% |
| 修正口径（看实际工具名） | 2026-11-15 | 83.3%（10/12） | 100% |
| **修正口径 + 脚本修好（路径/字段/工具名）** | **2026-11-18** | **75.0%（9/12）** | **100%** |

**两次修正口径之间的差异全部来自 T07 一次翻转** ——
"Python 的 list 和 tuple 有什么区别"（期望 `chat`，不该检索）：
2026-11-15 判对了（没检索），2026-11-18 判错了（检索了 2 轮）。

> **这条差异本身就是结论**：**LLM 路由有随机性**。同一套代码、同一批 case、
> 同一天，路由准确率就能从 83.3% 掉到 75.0%。所以：
> - **83.3% 和 75.0% 都不是基线** —— 它们都是单次采样；
> - 想让这个数字有意义，必须**重建评估集（脱离二值口径）+ 接进 CI 多次跑**（P0-1）；
> - **对外自述时不要把"路由准确率"当亮点讲** —— 它既不稳定，也没达到 90% 合格线。

### ⚠️ 三个必须知道的坑

1. **Windows 上 `PYTHONIOENCODING=utf-8` 是必须的** —— 脚本里打印 `✓` / `✗` 会触发 GBK 编码错误。
2. **`curl` 传中文会 400** —— Git Bash 把中文按本地代码页（GBK）发出，
   FastAPI 报 `There was an error parsing the body`。**用 `--data-binary @文件`**
   （文件是 UTF-8）才能通。**这不是后端 bug。**
3. **改了前端代码必须重启 Streamlit** —— 跑着的进程还是旧代码，
   测的是旧版本（2026-11-17 真栈体检踩到：重启后 2 个失败 → 0 个失败）。
