## 1 · 📘 LangGraph / LangChain（13 条）

### 1.1 📘 `reducer`（归约器）

- **作用**：规定"节点返回的新值，怎么跟 state 里的旧值合并"。LangGraph 默认是**覆盖**，但有些字段要**累加**（计数器）、有些要**合并**（字典）、有些要**追加**（消息列表）。
- **落在哪**：`agent/state.py:23`（`_reset_or_inc`）、`:43`（`_inc_refl`）、`:48`（`_merge_tool_status`）
- **本项目怎么用**：9 个 state 字段里 4 个各挂一个 reducer。关键在 `iter_count` 挂的是**带重置语义**的自定义 reducer —— 节点返回 `0` 表示"重置"，返回 `>0` 表示"累加"（`agent/state.py:34-36`）。
- **不用它会怎样**：计数器会**每次被覆盖而不是累加**。`iter_count` 永远是 1 → `MAX_ITER` 边界检查 `iter_count + 1 >= MAX_ITER` 永远不成立 → **Agent 无限循环调工具**，直到撞 `recursion_limit` 才停。
- **自测**：为什么 `iter_count` 的 reducer 要自定义，而不是用 LangGraph 的默认覆盖？因为节点返回的是**增量**（`iter_node` 返回 `1` 表示 +1），覆盖语义下计数器永远停在 1。另外 reflect 节点需要把它**清零**，纯累加型 reducer 也做不到（"旧值 + 0 = 旧值"）。

### 1.2 📘 `Annotated`（把归约器绑到字段上）

- **作用**：Python 标准库语法，用来给一个类型声明附加**元数据**。LangGraph 靠它把 reducer 挂到 state 字段上。
- **落在哪**：`agent/state.py:90-98`
- **本项目怎么用**：`iter_count: Annotated[int, _inc_iter]` —— 左边是类型，右边是"合并规则"。
- **不用它会怎样**：字段变成**裸类型**，LangGraph 不知道该怎么合并 → 每次覆盖 → 计数器失效（同 1.1）。
- **自测**：`Annotated[int, _inc_iter]` 和 `Annotated[int, _inc_refl]` 的区别在哪？为什么 `last_critique: str` 不需要 `Annotated`？

### 1.3 📘 `add_messages`（LangGraph 内置的消息归约器）

- **作用**：LangGraph 内置的 reducer，专门处理消息列表 —— 新消息**追加**进历史，并且按 `id` 去重/替换同一条消息。
- **落在哪**：`agent/state.py:19`（导入）、`:90`（挂在 `messages` 字段上）
- **本项目怎么用**：所有节点返回 `{"messages": [AIMessage(...)]}` 或 `{"messages": [ToolMessage(...)]}`，框架自动往历史里追加。**这就是节点之间唯一的通信方式之一**（另一个是 state 的其他字段）。
- **不用它会怎样**：如果用默认覆盖 reducer，每写一条消息就把历史**清空** → synth 节点看不到 iter 之前的任何东西 → 工具素材全丢 → Agent 退化成"每轮从零开始"。**注意**：`collect_round_material`（§3.16）正是靠 `messages` 保留了历史才能取到本轮素材。
- **自测**：`add_messages` 挂在哪个字段上？工具返回的 `ToolMessage` 是谁写进 `messages` 的 —— 工具自己，还是 `ToolNode`？

### 1.4 📘 `compile()`（编译）

- **作用**：把"图的定义"（节点、边、状态契约）变成**可执行对象**。定义期和运行期是分开的。
- **落在哪**：`agent/graph.py:71`（`return workflow.compile()`）
- **本项目怎么用**：`build_graph()` 负责定义 + 编译；`runtime._get_graph()`（`agent/runtime.py:31`）**懒加载并缓存**编译结果 —— 全进程只编译一次。
- **不用它会怎样**：每次请求都重建图 → 每次都要重新注册 4 个节点 4 条边 → 图定义本身不贵但白白重复；更糟的是**多份图实例**会让调试时状态对不上（你 debug 的是 A 图，跑的是 B 图）。
- **自测**：为什么 `runtime.py` 用 `_get_graph()` 这个函数，而不是在模块顶层直接 `graph = build_graph()`？（提示：跟"启动时必须连上 Milvus / 读 YAML"有关）

### 1.5 📘 `bind_tools`（绑定工具）

- **作用**：把工具的**名称、参数 schema、描述**交给 LLM，让它有能力发起函数调用。绑定后 LLM 返回的 `AIMessage` 里可能带 `tool_calls`。
- **落在哪**：`agent/nodes/iter_node.py:39-41`（`llm_instance.chat.bind_tools(ALL_TOOLS)`）
- **本项目怎么用**：**只有 iter 节点挂**。synth / reflect 不挂 —— 它们的输出必须是纯文本 / 固定结构，挂了会出现"本该写答案却发了 tool_calls"的错乱。
- **不用它会怎样**：不挂 → LLM 不知道有检索工具 → **永远不调工具** → Agent 退化成纯闲聊。挂错节点 → 写答案的节点突然发起工具调用 → 图状态错乱、答案被工具调用占位。
- **自测**：4 个节点里哪几个挂了 `bind_tools`？为什么 reflect 节点不用挂？

### 1.6 📘 `tool_calls`（工具调用请求）

- **作用**：LLM 说"我要调 X，参数是 Y"的结构化请求，挂在 `AIMessage.tool_calls` 上。**一个 AIMessage 可以带多个 tool_calls**（并发调多个工具）。
- **落在哪**：`agent/nodes/iter_node.py:101`（LLM 返回的 AIMessage 上）、`agent/nodes/should_continue.py`（路由判据）
- **本项目怎么用**：`should_continue` 靠"有没有 tool_calls"决定走 `tools` 还是 `synth`。**MiniMax 常常一次决策并发发 2~3 个 `rag_search`** —— 这个并发事实直接决定了 `tool_status` 的 key 必须是调用 id（§3.6）。
- **不用它会怎样**：如果按"工具名"记账（而不是调用 id），并发调用会互相覆盖 —— **实测**：一次决策发了 2 个 `rag_search`，一个成功一个超时，结果状态字典里只剩后一条，成功的状态被 timeout 冲掉。日志上显示"这个工具失败了"，实际上一半是成功的。
- **自测**：MiniMax 一次决策发了 2 个 `rag_search`，其中 1 个成功 1 个超时。`tool_status` 里应该有几条？key 是什么？

### 1.7 📘 `ToolMessage`（工具回执）

- **作用**：工具执行结果**回给 LLM** 的消息类型。**必须与对应 `tool_call` 的 `id` 配对**（`tool_call_id` 字段）。
- **落在哪**：`agent/nodes/status_tool_wrapper.py:123`（失败时构造）、`:105`（成功时用 `result` 自带的内容）
- **本项目怎么用**：成功时内容是**原始检索片段**（不做包装）；失败时内容是**结构化 JSON 载荷**：
  ```json
  {"code": "TOOL_TIMEOUT", "status": "timeout", "retryable": true, "message": "调用超时：..."}
  ```
- **不用它会怎样**：**这是本项目最硬的约束之一**。有 `tool_calls` 却没有配对的 `ToolMessage` → 图状态非法 → 下一次 LLM 调用被 MiniMax 判为 `400 invalid params, tool call and result not match` → 整个请求失败。
- **自测**：工具执行**失败**时，为什么还要写 `ToolMessage`？失败信息为什么不直接抛出去？

### 1.8 📘 `wrap_tool_call`（工具调用钩子）

- **作用**：LangGraph 官方提供的拦截点，**每一次**工具调用都会经过你给的这个函数，你可以包住它、观察结果、改写返回。
- **落在哪**：`agent/graph.py:25`（`ToolNode(ALL_TOOLS, wrap_tool_call=status_wrapper)`）、实现在 `agent/nodes/status_tool_wrapper.py:78`
- **本项目怎么用**：在这个钩子里把每次调用的结果翻译成 `tool_status` 条目（成功/空/超时/错误 4 态）。**这是官方扩展点，不碰框架内部实现。**
- **不用它会怎样**：没有它就**看不到工具到底成功没成功** —— 检索失败和检索为空混为一谈，reflect 节点拿到的素材里没有失败信息，只能靠 LLM 猜。
- **不用它会怎样（另一种）**：**想用 `wrap_tool_call` 之外的"正确姿势"——继承 `ToolNode` 重写 `__call__` —— 会静默失效**。`ToolNode.__init__` 把被调用的方法钉死成 `_func`，LangGraph 走的是 `node.invoke(...)` → `self.func`（父类原版），子类重写的 `__call__` **永远不会被执行**。这段结论写在 `agent/nodes/status_tool_wrapper.py:33-37` 的 docstring 里。
- **自测**：为什么不能通过继承 `ToolNode` 并重写 `__call__` 来拦截工具调用？（提示：看 `ToolNode.__init__` 做了什么）

### 1.9 📘 `Command`（命令）

- **作用**：节点返回的"要写回 state 的内容"，可以同时更新多个字段。
- **落在哪**：`agent/nodes/status_tool_wrapper.py:104`、`:122`
- **本项目怎么用**：
  ```python
  Command(update={
      "messages": [ToolMessage(...)],
      "tool_status": {tool_call_id: {...}},
  })
  ```
  一次返回，**同时**写消息和写状态 —— 两者必须原子地对应上（同一个调用 id 的一对）。
- **不用它会怎样**：如果工具只更新 `messages` 不更新 `tool_status`（或者反过来），就会出现"消息里有这次调用、状态里没有" → 状态与事实脱节 → reflect 节点基于错误信息做决策。
- **自测**：`Command(update=...)` 一次最多能更新几个字段？本项目为什么非要一次更新两个？

### 1.10 📘 `with_structured_output`（结构化输出）

- **作用**：让 LLM 的输出被 **Pydantic** 校验成固定结构，而不是自由文本。
- **落在哪**：`agent/nodes/reflect_node.py:51`（`with_structured_output(ReflectOutput)`）
- **本项目怎么用**：`ReflectOutput`（`agent/nodes/reflect_node.py:33` 附近）定义三个字段：`is_sufficient: bool`、`critique: str`、`next_action: Literal["end", "rewrite", "re_iterate"]`。**决策被限制在 3 个值里**，LLM 没法自由发挥出一个 `retry` 或 `done` 之类的第四种。
- **不用它会怎样**：改用自由文本解析（比如让 LLM 输出 `答案是：OK` 再正则抠）→ LLM 换个说法就解析失败 → 反思机制随机失效。而且**没法做穷举校验**：`Literal` 保证 `next_action` 只可能是那 3 个值之一。
- **自测**：`with_structured_output` 相比"让 LLM 输出 JSON 再 `json.loads`"，多了哪一层保障？解析失败时本项目怎么兜底？

### 1.11 📘 `checkpointer`（检查点）/ `thread_id`

- **作用**：`checkpointer` 负责把图的状态**持久化**；`thread_id` 是"会话键"，告诉 checkpointer 这次调用属于哪条会话。
- **落在哪**：`agent/runtime.py:92-93`（传了 `thread_id`）、但**没有装 checkpointer**
- **本项目怎么用**：**本项目没有装 checkpointer**，所以 `thread_id` 传了也**没人读** → **Agent 多轮记忆未实现**。每次 `ask()` 都传全新的 `{"messages": [HumanMessage(question)]}`。
- **不用它会怎样**（反过来说）：如果误以为"传了 `thread_id` 就有记忆" → 面试或联调时用户问"它记得我刚才说的吗"，实际不记得 → 演示翻车。这是**当前最需要说清的一个能力边界**（详见 [`项目能力与边界.md`](./项目能力与边界.md)）。
- **⚠️ 附带陷阱**：要做多轮记忆，不能直接把现在的 `messages` 存下来 —— iter 的占位消息（`"READY"` / `"已达迭代上限，结束"`）会一起进历史。§3.1–3.3 讲这三个信号为什么集中定义。
- **自测**：项目里 `session_id` → `thread_id` 传了，但为什么 Agent 还是**不记得上一轮**？

### 1.12 📘 `Runnable`（可运行单元）

- **作用**：LangChain 里**所有可调用对象的统一接口**。有了它，`bind_tools` / `with_structured_output` / `invoke` 才能一层层套娃地传递下去。
- **落在哪**：`agent/llm_wrapper.py:67`（`ThinkingStripRunnable` 包装 `Runnable`）
- **本项目怎么用**：`ThinkingStripRunnable` 是个包装器，把"剥 `<think>` 块"这件事**透明地叠在**任何 Runnable 上，调用方感觉不到差别。
- **不用它会怎样**：如果剥 think 的逻辑散落在每个节点的 prompt 拼装里 → 4 个节点 4 份实现 → 漏一处 → 推理模型的 `<think>` 内容漏进答案或漏进 `tool_calls` 解析。
- **自测**：`ThinkingStripRunnable` 为什么要包在**最内层**（`llm_instance.chat.bind_tools(...)` 的外面）而不是最外层？

### 1.13 📘 `total=False`（TypedDict 全字段可选）

- **作用**：Python 的 `TypedDict` 语法开关。加上它，state 里**每个字段都可以不出现**（第一次 invoke 时通常只有 `messages` 和 `deadline`）。
- **落在哪**：`agent/state.py:59`（`class AgentState(TypedDict, total=False)`）
- **本项目怎么用**：所有节点都按"字段可能不存在"来写代码 —— 一律用 `state.get("iter_count") or 0` 而不是 `state["iter_count"]`。
- **不用它会怎样**：用 `total=True`（默认）→ 静态上要求所有字段都必填 → 第一次 invoke 就少 7 个字段 → 类型检查报错；更实际的问题是**代码里到处 `state["xxx"]` 会 KeyError**。
- **自测**：`agent/state.py:101` 的 `initial_state()` 造了一个 9 字段全填满的 dict，但 `runtime.ask()` 实际传进去的只有 2 个字段 —— 为什么不用 `initial_state()`？

## 2 · 📘 Milvus（10 条）

> **前提**：Milvus 是本项目的向量数据库（pymilvus 2.6.14）。
> 摄取侧写 `utils/txt_spliter/vector_main.py`，检索侧读 `core/rags/rags.py`。

### 2.1 📘 `collection`（集合）

- **作用**：Milvus 里的**向量数据表**，类比关系型数据库的表。
- **落在哪**：`utils/txt_spliter/vector_main.py:93`（造名）、`:110`（创建）
- **本项目怎么用**：真实集合名是 `txt_data_<时间戳>`（`new_collection_name = f"{alias_name}_{int(time.time())}"`）—— **每次重建都新建一个**，旧的**不删**（留作回滚 / 手工清理）。
- **不用它会怎样**：如果复用同一个集合名 → 新旧向量混在一起 → 旧文档的残片还在库里被检索出来 → 用户问 A 文档，答案里出现早已删除的 B 文档内容，而且**没法靠"重建"解决**（数据已经混了）。
- **自测**：集合名里为什么要带时间戳？为什么重建完旧集合不删？

### 2.2 📘 `alias`（别名）

- **作用**：一个**稳定的名字**，指向某个真实集合。查询只认 alias，不认真实集合名。
- **落在哪**：`utils/txt_spliter/vector_main.py:92`（取名）、`:156` / `:161`（切换）；检索侧 `core/rags/rags.py`（按 alias 查）
- **本项目怎么用**：alias 名固定来自 `configs/model_config.yaml` 的 `collection_name`（默认 `txt_data`）。**摄取侧和检索侧都只认这个名字**，真实集合名谁都不关心。
- **不用它会怎样**：如果检索侧直接写死真实集合名 `txt_data_<时间戳>` → 每次重建索引都要改代码 + 改配置 + 同步重启检索服务 → 重建索引 = 停机。用 alias 则**重建时只改 alias 指向，代码一行不动**。
- **自测**：alias 和"配置里的 `collection_name`"是同一个东西吗？为什么说"alias 是本项目摄取侧唯一有设计含量的地方"？

### 2.3 📘 `schema` / `field`（字段定义）

- **作用**：集合的**列结构** —— 有哪些字段、什么类型、谁是主键。
- **落在哪**：`utils/txt_spliter/vector_main.py:104-107`
- **本项目怎么用**：3 个字段 —— `id`（INT64，主键，自增）、`vector`（FLOAT_VECTOR，1024 维）、`text`（VARCHAR，存原始文本片段）。
- **不用它会怎样**：少定义 `id` 主键 → insert 报错或重复；`vector` 维度定义错 → 写入时维度校验失败，或者**能写进去但检索全部返回噪声**（维度对了但模型换了，见下）。
- **⚠️ 连带陷阱**：`vector` 是 1024 维，但 `bge-large` 和 `bge-m3` **都是** 1024 维 —— 索引侧和检索侧模型名不一致时**不会报错**，只会"每一条检索都返回噪声"。这正是 `resolve_embed_settings()` 存在的理由（§6.1）。
- **自测**：集合有几个字段？如果索引端用 `bge-m3`、检索端用 `bge-large`，会发生什么？

### 2.4 📘 `load_collection`（加载）

- **作用**：Milvus 把集合**载入内存**后才能查。集合是磁盘上的文件，`load` 才是把它拉进内存建索引。
- **落在哪**：`utils/txt_spliter/vector_main.py:144`（索引侧建完就 load）、`core/rags/rags.py:106`（检索侧发现不是 `Loaded` 就补 load）
- **本项目怎么用**：**两侧都做了**。检索侧的那次 load 是**幂等兜底** —— 如果集合没被载入，检索会直接失败。
- **不用它会怎样**：不 load 就查 → Milvus 抛"collection not loaded" → 检索失败。而这个失败**看起来像"没检索到"** → 很容易被误判成"库里没有这个内容"，方向完全错了。
- **自测**：为什么检索侧还要再 load 一次？这次 load 是什么角色？

### 2.5 📘 `segment`（数据段）/ insert 异步落盘

- **作用**：集合底层的数据分块。**insert 返回成功 ≠ 数据立刻可查** —— 数据可能还在内存 segment 里没落盘、没建索引。
- **落在哪**：`utils/txt_spliter/vector_main.py:131`（insert）
- **本项目怎么用**：**切 alias 之前没有 flush** —— 所以切完之后的一小段时间里，新 alias 指向的集合里有**部分数据查不到**。这是已知缺口 **P3-10**（记在 [`项目现状.md`](./项目现状.md) §8）。
- **不用它会怎样**：切完 alias 立刻用前端提问 → "刚上传的文档明明解析过了却检索不到" → 看起来像上传功能坏了，其实是数据还没落盘。这是个**时间窗口很短但很迷惑**的 bug。
- **自测**：重建索引后立刻提问可能检索不到新文档，为什么？P3-10 的根因是什么？

### 2.6 📘 `flush`（落盘）

- **作用**：强制把未落盘的数据**刷下去**，并保证可查。
- **落在哪**：`utils/txt_spliter/vector_main.py` —— **全文件没有调用**，这是缺口本身
- **本项目怎么用**：**没做**。P3-10 的最小修法就是在切 alias 前加一次 `client.flush(collection_name)`。
- **不用它会怎样**：见 2.5 —— 切完 alias 有一段"数据不可查"的窗口期。

### 3.1 📘 `READY` / `SIGNAL_READY`

- **作用**：iter 节点发出的**流程标记** —— "我不调工具了，你去写答案"。不是答案本身。

- **不用它会怎样**：iter 的输出就没有"我放弃了"这个表达 → 路由函数无法区分"不需要工具"和"LLM 挂了" → 图要么死循环、要么直接跳过 synth 交白。

### 3.2 📘 `SIGNAL_MAX_ITER` / `SIGNAL_EXPIRED`

- **作用**：另外两种"**收摊**"标记 —— 迭代上限到了 / 图级总时限到了。

### 3.4 📘 `iter_count` / `reflection_count`（两个计数器）

- **作用**：两个**互不相干**的计数器，各管自己的节点。**前者可重置，后者永不重置**。

### 3.7 📘 `code` / `retryable`

- **作用**：`code` = 机器可读的失败码；`retryable` = "**这次失败重试有没有意义**"。
- **落在哪**：`agent/nodes/status_tool_wrapper.py:59-64`（词表）、`:113-121`（JSON 载荷）
- **本项目怎么用**：当前**只有 timeout 是 `retryable: true`**。更细的分类（限流 / 服务不可用 → 可重试；参数错 / 代码 bug → 不可重试）**暂时做不了**，因为工具层目前只拿到 `AgentToolError` 这一个"其他错误"的桶，看不出底层到底怎么了。
- **不用它会怎样**：把"不可重试的错"标成可重试 → reflect 判 `re_iterate` → `iter → tools(错) → iter` 死循环。

  - 硬约束描述的是"**本 Agent 不靠 re_iterate 重试**"（防死循环优先）
  两者不矛盾，但**必须分开讲** —— 混起来讲会得出"retryable=true 却不让重试，是不是代码写错了"的错误结论。

- **作用**：把一个**贵的、且希望全进程只建一次**的对象，挂在 FastAPI 的 `app.state` 上。
- **落在哪**：`api/dependencies.py:38-53`
- **本项目怎么用**：`get_rag_model` 是 app 级单例，存在 `app.state.rag_model`。**原因**：FastAPI 的 `Depends` 缓存**只跨一次请求**，不跨请求 —— 所以 `Depends(get_rag_model)` 每请求都会重建。而 `RagModel.__init__` 实测约 **0.45 s**（[实测] 2026-11-17），其中约 **0.42 s 是建嵌入模型的 HTTP 客户端**（两个 httpx 客户端各建一次 SSL context），剩下的才是 YAML 读取和两次健康检查 RPC；**实际检索只要约 0.10 s**。
- **不用它会怎样**：每请求重建 `RagModel` → 每请求多付 ~0.45 s → 且**每个请求都建两个 httpx 客户端**（连接池不复用）→ 高并发下连接数和内存都被放大。
- **⚠️ 配套的两个细节**（少一个就出事）：
  1. **失败的连接不缓存** —— 有个 `is_ready` 门槛，只有成功建好的才写进 `app.state`；下一次请求会重试。**否则** Milvus 启动慢会让第一次请求永久失败。
  2. **注意这不是"每请求新建 Milvus 连接"** —— pymilvus 自己缓存 gRPC channel（第二个客户端 0.000 s）。真正贵的是嵌入 HTTP 客户端（见 §2.9 的纠正）。
- **自测**：FastAPI 的 `Depends` 缓存到底跨不跨请求？本项目为什么只有 `get_rag_model` 做了 app 级单例，`get_chat_model` 没有？

### 3.9 📘 `原子切换 alias`

- **作用**：新集合建好之后，让**稳定的 alias** 指向它，旧集合保留 —— 重建索引期间**查询不中断、不报错、不返回旧数据**。
- **落在哪**：`utils/txt_spliter/vector_main.py:146`（"原子切换 alias" 注释）、`:156`（`alter_alias`）、`:161`（`create_alias`，首次没有 alias 时走这条）
- **本项目怎么用**（完整序列）：
  ```
  ① 解析文件 → 切块
  ② 调 Ollama /api/embed 批量算向量
  ③ 建新集合 txt_data_<时间戳>（3 字段 schema）
  ④ insert 数据
  ⑤ 建 AUTOINDEX + COSINE 索引
  ⑥ load_collection（新集合载入内存）
  ⑦ alter_alias：把 alias 从旧集合改指新集合  ← 这一步是"原子"的
  ⑧ 旧集合保留（手工清理 / 回滚）
  ```
  **"原子"的准确含义**：alias 改指是 Milvus 内部的**单次指针更新** —— 不是"先删 alias 再建 alias"（那样中间有个**查不到**的窗口），而是一次改指。所以查询要么看到旧集合、要么看到新集合，**不会看到"没有集合"**。
- **不用它会怎样**：两种典型坏法：
  - **先删 alias 再建 alias** → 中间有个窗口查不到 → 线上报"collection not found"。
  - **直接改配置里的集合名**（`txt_data_<时间戳>` 写进 YAML）→ 检索侧和摄取侧要同时改、同时重启 → 重建索引 = 停机；而且旧版本回滚时配置又得改回去。
- **自测**："原子"两个字具体指什么？如果实现成"先删 alias 再 create"，会出什么问题？

### 3.10 📘 `RetrievalError`（检索失败 ≠ 检索为空）

- **作用**：把"**检索失败**"（Milvus 连不上、查询报错）和"**检索为空**"（正常查了但没匹配到）**严格区分开**。
- **落在哪**：`core/rags/rags.py:11`（定义）、`:145-147`（抛出点）
- **本项目怎么用**：`retrieve()` 抛 `RetrievalError` 表示失败，**返回 `[]` 只表示"确实没检索到"**。工具层 `agent/tools/rag_tool.py` 把它翻译成 `AgentTimeoutError`（`__cause__` 是超时类）或 `AgentToolError`。
- **不用它会怎样**：**这是 P2-7 修的核心**。改之前 `retrieve()` 里是 `except Exception: return []` —— **异常被吞成空列表** → 工具层看到"空" → 状态记成 `empty` 而不是 `error`/`timeout` → **Milvus 挂了和"库里没这内容"在日志里长得一模一样** → 排查方向从一开始就跑偏。
- **⚠️ 有一处刻意的不一致**：`/rag` 直接对话接口（`core/rags/rags.py:197-201`）**仍然吞掉** `RetrievalError` 并返回友好回答 —— 那是**故意的**：直连接口要"永远 200"，不能把后端故障直接甩给前端。但 **Agent 工具层必须能感知失败**。同一个异常，两条链路两种策略，这是有意的设计而不是遗漏。

### 3.11 📘 `AgentError` / `AgentTimeoutError` / `AgentToolError`

- **作用**：工具层的**异常归一化** —— 把一堆第三方库的异常（`httpx.ReadTimeout` / pymilvus 的各种错 / `openai.APITimeoutError`）翻译成**两个语义清晰的**自家异常。
- **落在哪**：`agent/errors.py:33`（`AgentError`）、`:37`（`AgentTimeoutError`）、`:41`（`AgentToolError`）、`:45`（`is_timeout`）
- **本项目怎么用**：
  ```
  Exception
   └─ AgentError          Agent 内部可预期错误的基类
       ├─ AgentTimeoutError   超时 —— 可重试
       └─ AgentToolError      工具失败 —— 不可重试
  ```
  **归一化只发生一次，就在工具里**（`agent/tools/rag_tool.py`）。上层只认这两个。
- **不用它会怎样**：上层节点要开始判断"这个异常到底是不是超时" → 每个节点各写一遍 → 第三方异常类型漏判 → 超时被当成普通错误 → **该重试的不重试**；而且每加一个第三方库就要改 N 个节点。
- **⚠️ 一个细节**：`is_timeout()`（`agent/errors.py:45`）先做**精确类型判断**（`TimeoutError` / `httpx.TimeoutException`），再**用类名兜底**（`"timeout" in type(exc).__name__.lower()`）—— 因为 pymilvus / gRPC 的超时异常不在 httpx 体系里。
- **自测**：为什么 `TimeoutError` 和 `httpx.TimeoutException` 要放在一起判断？类名兜底是干什么用的？

### 3.12 📘 `Timer`（单次动作超时）

- **作用**：给任意同步调用套一个**时间上限**。
- **落在哪**：`agent/timeout.py:22`（类）、`:36`（`call`）
- **本项目怎么用**：`Timer(TOOL_TIMEOUT).call(model.retrieve, query, top_k=5)`。用 `ThreadPoolExecutor` 提交任务 + `fut.result(timeout=...)`。
- **不用它会怎样**：工具层没有上限 → 一次 Milvus 挂起 → **整条请求挂死**（外层 `ask()` 的总时限也救不了，因为节点根本返回不了）。
- **⚠️ 三个坑（`agent/timeout.py` 里都写了注释）**：
  1. **Python 杀不掉线程**（没有 `Thread.terminate()`）。超时只是"**不再等**"——底层线程**仍在跑**，仍占着 Milvus / Ollama 连接。这是"超时兜底"，不是"强制中断"。
  2. **不能用 `with ThreadPoolExecutor(...)`** —— `with` 退出会**等线程跑完**，超时也就失去意义了。所以是 `ex = ThreadPoolExecutor(...)` + `finally: ex.shutdown(wait=False)`（`:54` 明确注释了）。
  3. **非超时异常原样上抛**（`:48-52`）—— `Timer` **不负责翻译**，翻译归 `errors.py` 管。
- **自测**：`Timer` 超时之后，底层那个 Milvus 查询还在跑吗？这带来什么后果？

### 3.13 📘 `deadline`（图级总时限）

- **作用**：整张图的**总预算** —— 解决"每一步都没超时，但加起来能跑到十几分钟"。
- **落在哪**：`agent/runtime.py:106`（写入）、`agent/state.py:81`（字段）
- **本项目怎么用**：`ask()` 写入 `deadline = time.time() + TOTAL_TIMEOUT`（**绝对时间戳**，默认 90 s），随 state 传给所有节点。**为什么放 state 而不是全局变量**：state 是 LangGraph 里跨节点传数据的唯一通道，而且**每次 invoke 天然隔离** —— 两个并发请求各有一份 state，不会互相污染。全局变量做不到这点。
- **不用它会怎样**：只有单步超时（`Timer`）而没有总时限 → 每步都"没超时"，但 ReAct 循环可以跑 3 轮 × 多个工具 → 总耗时不可控；而且**如果总时限是全局变量，两个并发请求会互相覆盖 deadline** → A 请求被 B 请求的截止时间截断。
- **自测**：为什么 `deadline` 存绝对时间戳而不是"还能再跑多少秒"？

### 3.14 📘 `is_expired()`（节点进图前问一句）

- **作用**：协作式检查 —— 每个节点**动手之前**先问"超没超总时限"，超了就地收手。
- **落在哪**：`agent/timeout.py:57`（定义）
  - **`is_expired(state)` 直接调用 3 处**（三个 LLM 节点动手前）：`agent/nodes/iter_node.py:57`、`agent/nodes/synth_node.py:47`、`agent/nodes/reflect_node.py:77`
  - **另外 2 处查的是标志位**（不是重新比时间）：`agent/nodes/should_continue.py:17` 和 `:41` —— 两个条件边读 `state.get("expired")`。**标志位由节点设置**（超时时节点写 `expired: True`），条件边只负责"看到标志就 END"。
- **本项目怎么用**：超时了**不是抛异常**，而是走"正常流程"：写 `SIGNAL_EXPIRED` → 条件边看到 `expired=True` → 直接 END → 把**已经写好的答案**（`last_answer`）交出去。
- **不用它会怎样**：没有协作式检查 → 一个节点可能跑完（30 s）+ 下一个节点再跑 30 s + … → 用户等 3 分钟才收到一句"超时了"。有 `is_expired` 之后，**超时的瞬间就收摊**，用户拿到的是**已生成的半成品答案**而不是空。
- **为什么是协作式而不是强制中断**：LangGraph 没有"在任意指令处打断节点"的机制；强制中断要么改框架，要么每层都套线程（而线程杀不掉，见 §3.12）。**协作式的代价**：节点内部的阻塞调用仍会跑完那一小段。
- **自测**：一共有几处 `is_expired()` 检查？为什么**两条条件边**也要查？

### 3.16 📘 `collect_round_material`（本轮素材）

### 3.19 📘 悬空 `tool_calls`（有 tool_calls 但没有 ToolMessage 的 AIMessage）

- **作用**：一种**非法消息状态** —— 消息序列里有一条 AIMessage 声明了要调工具，但没有任何对应的 ToolMessage 应答。
- **落在哪**：`agent/nodes/iter_node.py:64-74`（那段长注释就是在讲这个）、`:75`（修法）

### 5.1 LangGraph 图：4 节点 / 4 条边 / 2 个计数器

> **先验** `[概念需补]` §1.1 `reducer` · §1.2 `Annotated` · §1.4 `compile()` —— "图 / 节点 / 边 / 条件边"全是框架词，先看 §1 再读这张拓扑。
> **本项目特有选择**：v2.1 的 `agent_node` **一个节点干两件事**（决定调不调工具 + 写最终答案），两种 LLM 模式互相干扰 → v2.2 拆成 `iter`（只决策）+ `synth`（只综合），中间用 `READY` 信号交接。**代价**：多一次 LLM 调用；**收益**：两种模式互不污染。

```
START → iter
          ├─ 有 tool_calls → tools → iter        （ReAct 循环）
          └─ 无 tool_call  → synth → reflect
                                    ├─ end         → END
                                    ├─ rewrite     → synth（iter_count 归零）
                                    ├─ re_iterate  → iter （iter_count 归零）
                                    └─ reflection_count ≥ MAX_REFL → 强制 END
```

- **4 个节点**：`iter`（纯决策，不写答案）/ `tools` / `synth`（综合）/ `reflect`
- **4 条边**：2 条无条件（`tools→iter`、`synth→reflect`）+ 2 条条件（`should_continue`、`after_reflect`）
- **v2.1 → v2.2 为什么要拆节点**：v2.1 的 `agent_node` 同时干"决定要不要调工具"和"写最终答案"两件事，**两种 LLM 模式互相干扰**。v2.2 拆成 `iter` + `synth`，用 `READY` 信号交接。
- **`recursion_limit` 必须显式给**：最坏情况 = 每轮 `2*MAX_ITER + 2` 步 × `(MAX_REFL + 1)` 轮 = `8 × 4 = 32` 步 > LangGraph 默认 25 → 撞 `GraphRecursionError` → `ask()` 兜底成"agent 调用异常"而不是给出答案。所以 `RECURSION_LIMIT = _STEPS_PER_ROUND * (MAX_REFL + 1) + 10 = 42`（`agent/runtime.py:24-25`）。
- **去哪看**：`agent/graph.py`（全文 71 行）；设计决策见 `docs/plan/v2.2-graph-design.md`

### 5.2 状态契约：9 字段 + 3 个 reducer

> **先验** `[概念需补]` §1.1 `reducer`（归约器）· §1.2 `Annotated` · §1.3 `add_messages` —— "字段为什么要挂 reducer""`Annotated` 是什么"这两问不补，下面的表看不懂。
> **本项目特有选择**：`iter_count` 挂的是**自定义** reducer（`_reset_or_inc`）。LangGraph 的默认行为是**覆盖**（最后一次写赢）—— 用默认的话 `iter_count` 每次都被写成 1，永远不涨，`MAX_ITER` 边界检查永不触发 → 无限循环调工具。自定义 reducer 把节点的返回值改成**增量语义**：返回 `1` = "+1"，返回 `0` = "清零"。顺带拿到了"清零"能力 —— 而纯累加型 reducer（像 `reflection_count` 用的 `_inc_refl`）写 `0` 是清不掉的（旧 + 0 = 旧）。别的方案（拆两个字段 / 让节点直接返回绝对值）也行，但要多一个字段，或者把"累加"这件事搬回每个节点里各写一遍。

| 字段 | reducer | 谁写 | 作用 |
|---|---|---|---|
| `messages` | `add_messages` | 全节点 | 消息历史（唯一的节点间通信通道之一） |
| `iter_count` | `_reset_or_inc` | iter / reflect | 工具循环计数（可重置） |
| `reflection_count` | `_inc_refl` | reflect | 反思次数（永不重置） |
| `tool_status` | `_merge_tool_status` | `wrap_tool_call` | 每次工具调用的状态 |
| `last_critique` | 覆盖 | reflect | 反思意见，synth 重写时读 |
| `next_action` | 覆盖 | reflect | 反思决策 |
| `deadline` | 覆盖 | runtime | 图级总时限（绝对时间戳） |
| `expired` | 覆盖 | iter | 已超时标志 |
| `last_answer` | 覆盖 | synth | 超时兜底时交出去的答案 |

- **字段必须显式声明**，否则 LangGraph 不会把它写进 state（`next_action` 曾因此恒为缺省值）。
- **`last_answer` 不能靠"倒着找最后一条 AIMessage"推导** —— messages 里混着 iter 的占位消息（`"READY"`），会把占位消息当成答案交出去。
- **去哪看**：`agent/state.py`（全文 114 行）

### 5.3 关键机制专节 · 超时与异常三层

> **先验** `[概念需补]` §3.11 `AgentError` / `AgentTimeoutError` / `AgentToolError` · §3.12 `Timer` · §3.13 `deadline` · §3.14 `is_expired()` —— 三个异常类名和两个超时词先对齐，这节就不绕。
> **本项目特有选择**：切三层不是为了"多一层更保险"，而是**职责不重叠**：归一化管"错误叫什么"、第 2 层管"这一次等多久"、第 3 层管"整张图还能跑多久"。别的方案（只留总时限 / 只留单次超时）都有明确死角 —— 只留总时限，工具线程会把连接占着不放；只留单次超时，10 个节点各等 30 s 也能跑 5 分钟。

> **这是本项目"设计含量最高"的一处机制**，也是面试里最能体现工程直觉的一处。
> 详细来龙去脉见 `docs/note/超时与异常机制设计.md`（**本地，不进仓**），但那篇文档的 §六 有 3 条已过时（见文末）。

#### 三层职责，切得互不重叠

| 层 | 位置 | 管什么 | 不管什么 |
|---|---|---|---|
| **第 1 层 异常归一化** | `agent/errors.py` + 工具函数 | 第三方异常 → `AgentTimeoutError` / `AgentToolError` | 不管时间 |
| **第 2 层 单次动作超时** | `agent/timeout.py :: Timer` | "这一次调用最多等 N 秒" | 不管全局预算 |
| **第 3 层 图级总时限** | `state["deadline"]` + `is_expired()` | "整张图最多跑 N 秒" | 不管单次调用 |

- **为什么必须切三层**：v2.1 之前**三层全断** —— 异常没归一化（上层要判 httpx/pymilvus/openai 三种超时）、超时只挂在 LLM 调用上（工具层没有上限）、也没有总时限（每步都没超时但能跑十几分钟）。
- **归一化只做一次**，在工具里（`agent/tools/rag_tool.py`）。下游**不再翻译**第三方异常类型。

#### 请求时序图

```
用户提问
  │
  ▼
runtime.ask()
  ├─ deadline = now + 90s                      ← 第 3 层的起点
  ├─ config = {recursion_limit: 42, configurable:{thread_id}}
  ▼
┌─ iter ───────────────────────────────────────────────────────────┐
│ ① is_expired(state)?          是 → 写 SIGNAL_EXPIRED, expired=True │
│ ② iter_count+1 >= MAX_ITER?   是 → 写 SIGNAL_MAX_ITER（不调 LLM）   │
│ ③ llm.invoke(prompt)   ← 自身带 30s timeout（构造参数 timeout=）    │
│     ├─ 抛异常 → 写 SIGNAL_READY → 去 synth                        │
│     └─ 正常   → AIMessage(tool_calls=[...]) 或 content="READY"     │
└─────────────────────────┬─────────────────────────────────────────┘
                          ▼
                 should_continue(state)
                   ├─ expired?          → END
                   ├─ iter_count 超限?  → synth
                   ├─ 有 tool_calls?    → tools
                   └─ 否则              → synth
                          ▼
┌─ tools（ToolNode + wrap_tool_call）──────────────────────────────┐
│ execute(request) → rag_tool                                     │
│    └─ Timer(30s).call(RagModel.retrieve, ...)      ← 第 2 层      │
│         ├─ 超时 → AgentTimeoutError → status=timeout             │
│         ├─ RetrievalError → AgentToolError → status=error        │
│         └─ 正常 → content                                        │
│    → Command(update={messages:[ToolMessage], tool_status:{id:{..}}})│
└─────────────────────────┬─────────────────────────────────────────┘
                          ▼ 回到 iter（ReAct 循环）
```

#### 三条硬规则

1. **`.with_config({"timeout": N})` 是死代码** —— `langchain_core` 从不读 `RunnableConfig["timeout"]`。超时只能在**构造时**传：`LLMmodel.create_minimax("MiniMax-M3.1-Flash", timeout=LLM_TIMEOUT)`。三个 LLM 节点都走这条路。
2. **Python 杀不掉线程** —— `Timer` 只能"不再等"，底层线程仍会跑完并占着连接。**所以工具层自身也要有界**（Milvus / Ollama 客户端各自也有 timeout）。
3. **`api/api_agent.py` 的端点必须是普通 `def`，不能是 `async def`** —— `ask()` 是同步阻塞的，写在 `async def` 里会占住事件循环，把整个 FastAPI 服务卡死。FastAPI 对普通 `def` 端点会自动丢到线程池。

### 5.4 关键机制专节 · 原子切换 alias + app 级单例

> **先验** `[代码你熟·说法要对齐]` —— 这两处的**机制**你懂，本节只对齐**项目原话**和**取舍**：
> · **原子切换 alias**（`utils/txt_spliter/vector_main.py:146` 的注释原句）—— "原子"指的是 Milvus 内部的**单次指针更新**，不是"先删后建"；不是"事务"。
> · **app 级单例 / app-level singleton**（`api/dependencies.py:38-53`）—— 不是"单例化依赖"。

> 用户点名要单独展开的两个。这两处是 **RAG 侧仅有的两处"有设计含量"的地方**。

#### A. 原子切换 alias（摄取侧）

**问题**：重建向量索引 = 写一批新数据 + 让检索侧立刻用上它。怎么做才不中断服务？

**三条常见做法与各自的下场**：

| 做法 | 下场 |
|---|---|
| 复用同一个集合名 | 新旧向量混在一起 → 删掉的文档残片还在被检索到 → **没法靠"再重建一次"解决**（已经混了） |
| 先 `drop_alias` 再 `create_alias` | 中间有个**查不到**的窗口 → 线上报 "collection not found" |
| **改配置里的集合名** | 检索侧和摄取侧要同时改配置、同时重启 → **重建索引 = 停机**；回滚还要再改回去 |

**本项目的做法**：**真实集合名带时间戳（每次都是新表），对外只暴露一个稳定的 alias。**

```
旧:  alias("txt_data") ──→ txt_data_20261120_1030
新:  alias("txt_data") ──→ txt_data_20261122_2136     ← 一次 alter_alias 指过去
```

- **"原子"的准确含义**：alias 改指是 Milvus 内部的**单次指针更新**，不是"先删后建"。所以查询**要么看到旧集合、要么看到新集合，不会看到"没有集合"**。这是"原子"这个词在这儿的唯一含义。
- **旧集合不删** —— 留作手工清理 / 回滚。这是**有意的**：重建索引是有风险的操作，保留回滚路径比省几 GB 磁盘重要。
- **代码位置**：`utils/txt_spliter/vector_main.py:146`（"原子切换 alias" 注释）、`:156`（`alter_alias`）、`:161`（`create_alias`，首次没有 alias 时走这条）
- **⚠️ 已知缺口 P3-10**：切 alias **之前没有 `flush`** → 切完的一小段时间里新集合有部分数据查不到。**最小修法**：在切 alias 前加一次 `client.flush(collection_name)`。

#### B. app 级单例（检索侧）

**问题**：`Depends` 的缓存**只跨一次请求**，不跨请求。所以 `Depends(get_rag_model)` **每请求都会重建** `RagModel`。

**代价实测**（[实测] 2026-11-17）：

| 项 | 耗时 |
|---|---|
| `RagModel.__init__` 合计 | **~0.45 s** |
| └ 其中建嵌入 HTTP 客户端 | **~0.42 s**（两个 httpx 客户端各建一次 SSL context） |
| └ YAML 读取 + 两次健康检查 RPC | ~0.03 s |
| **真正的检索** | **~0.10 s** |

**也就是说：每请求 90% 的时间花在"建客户端"上，而不是"查数据"。**

**做法**：挂在 `app.state.rag_model` 上，全进程只建一次（`api/dependencies.py:38-53`）。

**两个必须配套的细节**：

1. **失败的连接不缓存** —— 有 `is_ready` 门槛，只有建好的才写进 `app.state`；下次请求会重试。**否则** Milvus 启动慢会让第一次请求**永久失败**（进程生命周期内再也不重试）。
2. **⚠️ 别把锅甩给 Milvus 连接** —— pymilvus 2.6 有自己的 `ConnectionManager`，按地址缓存 gRPC channel，**第二个客户端的连接开销是 0.000 s**。真正贵的是**嵌入模型的 HTTP 客户端**（每次都新建两个 httpx 客户端，连接池不复用）。

**代码位置**：`api/dependencies.py:38-53`；实测记录见 `docs/status/项目现状.md`

### 5.5 工具调用状态机（tool_status）

> **先验** `[概念需补]` §1.7 `ToolMessage` · §1.8 `wrap_tool_call`（工具调用钩子）· §1.9 `Command` —— "失败也必须写 ToolMessage""钩子为什么官方能拦"这两问不补，看不懂为什么状态能写进 state。
> **本项目特有选择**：`tool_status` 的 key 是**调用 id**、不是工具名（§3.6）—— 因为 MiniMax 一次决策会并发发 2~3 个 `rag_search`。别的方案（按工具名记账）会把成功的那条状态冲掉，且**不报错**。

见 §3.6 / §3.7 / §1.6 / §1.7 / §1.8 / §1.9。这里只补**整体**：

```
LLM 发 tool_calls
      ↓
ToolNode(wrap_tool_call=status_wrapper)
      ↓
status_wrapper(request, execute)
   ├─ execute() 成功 + content 非空 → Command(messages=[result], tool_status={id:{status:success}})
   ├─ execute() 成功 + content 为空 → Command(..., status:empty)
   ├─ AgentTimeoutError              → Command(ToolMessage(JSON 载荷), status:timeout)
   └─ 其他异常                        → Command(ToolMessage(JSON 载荷), status:error)
      ↓
should_continue 读 tool_status → 决定路由
reflect 读 format_tool_status() → 决定 end/rewrite/re_iterate
```

- **失败也必须写 ToolMessage**（§1.7）—— 否则图状态非法，MiniMax 报 400。
- **失败时内容是结构化 JSON，不是中文散文** —— 因为 ToolMessage 是**给 LLM 看的**，结构化载荷比散文明确；而且能被测试直接断言，不依赖 prompt 措辞。
- **成功时内容保持原样**（原始检索片段），不做包装 —— 符合 CLAUDE.md 里的硬约束"Agent 工具输出保持原始 chunk，最终综合交给 Agent LLM"。

### 5.6 反思机制与两个刹车

> **先验** `[概念需补]` §1.10 `with_structured_output` · §3.17 `next_action` · §3.19 悬空 `tool_calls` —— "反思"在这个项目里**不是**一个框架组件，是 `reflect` 节点 + 一个 Pydantic 结构 + 三个决策值。
> **本项目特有选择**：**两个计数器分离**（`iter_count` 可重置 / `reflection_count` 永不重置）。别的方案（v2.1 的单计数器）会让反思触发条件短路 —— 混用"决策次数"和"综合次数"，两个上限互相干扰。

- **反思**：synth 写完答案 → reflect 用 `with_structured_output(ReflectOutput)` 审一遍 → 给 `next_action`（end / rewrite / re_iterate）。
- **两个刹车**（**都必须在**，改路由时不能只留一个）：

| 刹车 | 守什么 | 上限 | 能否重置 |
|---|---|---|---|
| `MAX_ITER` | **工具循环**（`iter → tools → iter`） | 3 | reflect 判 rewrite / re_iterate 时**重置** |
| `MAX_REFL` | **反思循环**（`synth → reflect → synth`） | 3 | **永不重置**（绝对上限） |

- **⚠️ 最容易记错的一点**：`MAX_REFL` **不是工具循环的刹车** —— 工具循环根本不经过 reflect 节点。**工具死循环了调 `MAX_REFL` 一点用都没有。**
- **reflect prompt 的硬约束**：工具 timeout / error / empty 时**不应**判 `re_iterate` → 否则 `iter → tools(超时) → iter` 死循环。这条约束和载荷里的 `retryable: true` 语义不同（见 §3.7）。
- **⚠️ 当前测试覆盖的缺口**：这条硬约束**测不到** —— 脚本化的假 reflect 无法覆盖（真 LLM 探针 S4 天然 flaky）。见 [`测试体系.md`](./测试体系.md) §6。

### 6.2 `ThinkingStripRunnable` 为什么要包在最内层

> **先验** `[概念需补]` §1.12 `Runnable`（可运行单元）· §3.15 `ThinkingStripRunnable` —— "Runnable"是 LangChain 的统一可调用接口，先有这个词才看得懂"包一层"是什么意思。

### 6.3 `collect_round_material` 的轮次边界

> **先验** `[概念需补]` §3.16 `collect_round_material`（本轮素材）—— **本轮素材**是本项目自有的说法（不是框架词）。"轮次"的定义是**最后一条 HumanMessage 之后的全部 ToolMessage**，不是"最后一条消息"。

见 §3.16。一句话：**用"最后一条 HumanMessage"划轮次，三个节点共用同一个口径 —— 否则 reflect 看到的素材范围和 synth 看到的不一样，反思结论就不可信。**

### 6.4 `calculator` 的 AST 白名单（`eval()` RCE 修复）

> **先验** `[本项目特有选择]` —— 没有框架术语要补，全部是**安全设计取舍**：白名单 vs 黑名单、AST 解析 vs 正则匹配，代价是什么（不支持变量、函数、科学计数法），为什么值得。

- **作用**：`calculator` 工具算数学表达式，**但绝不能 `eval()`**。
- **落在哪**：`agent/tools/calculator_tool.py`（手写 AST 白名单）；回归网在 `test/test_tools.py`
- **本项目怎么用**：解析成 AST，**只允许**算术节点（数字、+ - * / // % **、括号、一元正负），**任何**其他节点（函数调用、属性访问、变量名、导入、lambda、推导式…）一律拒绝。
- **不用它会怎样**：`eval()` 拼字符串 → **远程代码执行（RCE）**。LLM 的输出是**不可信输入** —— 诱导它拼出 `__import__('os').system('...')` 是标准攻击手法。而且工具是同步执行的，RCE 直接落在服务端。

- **⚠️ 这是"AI 应用自己的安全边界"，不是通用安全建议** —— 面试讲这个的杀伤力在于：**LLM 的输出是输入，不是答案**。

**一句话总结分界线**：本项目真正用到了 LangGraph 的**状态管理**（reducer / `add_messages` / `Command`）、
**工具编排**（`ToolNode` + `wrap_tool_call`）、**结构化输出**（`with_structured_output`）三层；
**没用** checkpointer（所以没有记忆）、**没用**子图（所以没有多 Agent）、**没用** interrupt / human-in-the-loop。

**为什么不建议现在升级 Milvus**（面试时如果被问"为什么不用 Web UI"）：

1. **卷兼容**：`milvus-data` 卷里是 v2.3.14 的存储格式，跨大版本升级需要迁移步骤，不是 `docker compose pull` 就能解决的。
2. **浮动 tag**：`docker-compose.yml:3` 写的是 `milvusdb/milvus:standalone`（没有版本号），**下次 pull 会直接跳到最新镜像**——本项目已经因此停留在 2.3.14 好几个月。要升级必须先把它钉成具体版本号。
3. **收益不匹配**：可视化是开发期工具，本项目已经有 Attu + pymilvus 两条可用路径，升级 Milvus 换来的只是一个 Web UI，不值当。
