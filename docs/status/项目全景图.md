**一句话概括**：这个项目有**两个独立的时间轴**——

不需要改任何代码：新集合建好 → alias 一切 → 线上立刻读新数据。

## §2 两条时间轴的详细流程

### 2.1 离线：文档 → 向量（`documents/` → Milvus）

```text
① 上传（前端）  POST /api/batch-upload-and-parse
   └─ api/api_file.py
      ├─ 路径穿越校验：(input_dir / name).resolve() 必须还在 input_dir 内
      ├─ 类型白名单：.txt .md .docx .pdf
      ├─ 同名策略：默认跳过；overwrite=true 才覆盖
      └─ 落盘到 documents/（保留原名）
   ↓
② 解析（同步调用）  utils/docs/txt_main.py :: main()
   ├─ FileScanner.scan_documents()   按扩展名分类
   ├─ FileFilter.should_process()    MD5 哈希 + mtime → 内容没变就跳过
   ├─ ProcessorManager               .md→MarkdownProcessor
   │                                 .docx/.doc→SimpleWordProcessor
   │                                 .pdf→SimplePdfParser（pymupdf + OCR 兜底）
   │                                 （只处理非 TXT；产物是"临时 TXT"）
   ├─ TextCleanerProcessor           统一清洗（HTML 反转义 / 中文软换行合并 /
   │                                 去 emoji / 压空行）
   └─ FileFilter.record_processed()  记进 txt/.file_filter.json
   ↓
③ 切块  utils/txt_spliter/spliter.py :: Splitter.split_all_files()
   ├─ 参数**唯一来源** = configs/model_config.yaml 的 EMBEDDING_CONFIG.text_splitter
   │   （chunk_size=300 / chunk_overlap=30 / separators）
   ├─ 第 1 步：LangChain RecursiveCharacterTextSplitter 机械切
   └─ 第 2 步：智能拼接 —— 小于 80 字的碎片向后合并（合并后不超 chunk_size）
   ↓
④ 向量化 + 建集 + 切 alias  utils/txt_spliter/vector_main.py :: vector_split()
   ├─ 嵌入模型名/URL：resolve_embed_settings() ← env EMBEDDING_MODEL / OLLAMA_BASE_URL
   │   **必须**在 EmbeddingModel 构造之后调用（它的 __init__ 才 load_dotenv）
   ├─ 直连 Ollama /api/embed（批量 32）—— 不用 langchain_ollama（该库在本机会被代理）
   ├─ 建新集合 txt_data_<时间戳>（id 自增 / vector FLOAT_VECTOR / text VARCHAR）
   ├─ AUTOINDEX + COSINE → load_collection
   └─ 原子切换：alias 存在 → alter_alias；不存在 → create_alias
       ★ 旧集合**不删** → 留了回滚窗口（要人工清理）
```

### 2.2 在线：提问 → 答案

**共通的两步**：① 把 query 变成向量 ② 在 `txt_data` alias 里搜 top-5。

```text
检索（RagModel.retrieve → _search_similar_chunks）
  ├─ self._embed.embed_query(query)          ← 复用 EmbeddingModel.embedding
  ├─ client.search(collection_name="txt_data", limit=5, output_fields=["text"])
  └─ 失败 → raise RetrievalError（**不是** []）★ 这是 P2-7 的核心
```

三条链路在检索之后分叉：

| | `/chat` | `/rag` | `/agent/chat` |
|---|---|---|---|
| 入口 | `api/api_chat.py:19` | `api/api_rag.py:19` | `api/api_agent.py:28` |
| 函数类型 | `async def` ⚠️ | `async def` ⚠️ | **`def`** ✓ |
| 检索 | 无 | 直接调 `_search_similar_chunks` | 由 LLM 决定是否调 `rag_search` 工具 |
| 提示词 | 无（裸聊） | `_build_context_prompt()` 拼文档 | `agent/prompts/*_prompt.py` |
| LLM | `app.state.model_manager` 当前模型 | 同左 | **独立**：`LLMmodel.create_minimax("MiniMax-M3.1-Flash")` |
| 检索失败 | — | 吞掉 → 当"没有相关文档" | 抛 `AgentToolError` → 工具状态记 `error` |
| 会话历史 | 全局 `MessageManager` | 全局 `MessageManager` | **无**（每次 invoke 全新 state） |
| 返回 | `{"response": str}` | `{"response": str}` | `{"response": str}` |

⚠️ **`async def` 的问题**：`/chat` 和 `/rag` 是 `async def`，但内部是**同步阻塞**调用
（Milvus 搜索 + LLM HTTP）。FastAPI 对 `async def` 端点**不会**丢线程池 →
一次 `/rag` 请求会把整个事件循环占住，直到 LLM 返回（最长 60s）。
`/agent/chat` 特意写成普通 `def` 就是为了避开这个坑（`test/test_agent_timeout.py`
用 AST 静态检查钉死了这一点），但另外两条链路没做同样处理。

## §3 Agent 图的细节

### 3.1 图结构（`agent/graph.py`）

```text
START → iter
          ├─ 有 tool_calls      → tools → iter      （ReAct 循环）
          ├─ 无 tool_calls      → synth
          └─ expired            → END

synth → reflect
reflect ├─ end        → END
        ├─ rewrite    → synth   （iter_count 已重置）
        ├─ re_iterate → iter    （iter_count 已重置）
        └─ reflection_count ≥ MAX_REFL → 强制 END（不调 LLM）
```

### 3.2 四个节点各干什么

| 节点 | 文件 | 输入 | 输出 | 关键行为 |
|---|---|---|---|---|
| `iter` | `nodes/iter_node.py:44` | question + 素材 + 计数 | tool_calls 或 `READY` | 挂了 `bind_tools(ALL_TOOLS)`；`iter_count + 1 >= MAX_ITER` 时**不调 LLM** 直接返回上限信号 ★ |
| `tools` | `langgraph.prebuilt.ToolNode` | tool_calls | ToolMessage + `tool_status` | 官方 `wrap_tool_call=status_wrapper` 钩子 |
| `synth` | `nodes/synth_node.py:35` | 素材 + critique | 最终答案 | **不挂** `bind_tools`；`last_critique` 空/非空 → 首次写/重写两种 prompt |
| `reflect` | `nodes/reflect_node.py:63` | 答案 | `next_action` + `critique` | `with_structured_output(ReflectOutput)`；解析失败 → fallback `rewrite` |

### 3.3 两个计数器（`agent/state.py`）

```python
def _reset_or_inc(old, new):     # iter_count 用
    if new == 0: return 0        # 节点返回 0 = 重置
    return (old or 0) + (new or 0)   # 节点返回 >0 = 累加
```

这个"**返回 0 表示重置**"的约定是 reflect 能重置 `iter_count` 的唯一办法 ——
LangGraph 默认 reducer 是纯累加，`旧 + 0 = 旧`，做不到重置。

| 计数器 | 上限 | 重置时机 | 刹车作用 |
|---|---|---|---|
| `iter_count` | `MAX_ITER=3` | reflect 判 rewrite/re_iterate 时归 0 | 工具循环 `iter → tools → iter` 的唯一刹车 |
| `reflection_count` | `MAX_REFL=3` | **永不重置** | 反思循环的绝对上限 |

★ `MAX_REFL` **不是**工具循环的刹车 —— 工具循环根本不经过 reflect 节点。
改路由时两个都要保留。

### 3.4 超时（3 层，职责不重叠）

```text
第 1 层  异常归一化    agent/errors.py
        第三方异常 → AgentTimeoutError（可重试）/ AgentToolError（不可重试）
        工具层翻译一次，下游不再翻译

第 2 层  单次动作超时  agent/timeout.py :: Timer
        ThreadPoolExecutor + 手动 shutdown(wait=False)
        （Python 杀不掉线程 → 只能"不再等"，底层线程仍会跑完）

第 3 层  整图总时限    state["deadline"] + is_expired()
        runtime.ask() 写入 deadline = time.time() + 90
        每个节点动手前协作式检查 → 超时就地收手
```

配置在 `configs/agent_config.yaml`：`llm=30 / tool=30 / total=90`。
**改超时只改 YAML**。

### 3.5 工具状态（4 态，key 是调用 id）

```python
state["tool_status"] = {
    "call_abc123": {                      # ← 调用 id，不是工具名
        "tool": "rag_search",
        "status": "success|empty|timeout|error",
        "code": "OK|EMPTY_RESULT|TOOL_TIMEOUT|TOOL_ERROR",
        "retryable": bool,
    }
}
```

| status | code | retryable | 触发 |
|---|---|---|---|
| `success` | OK | false | 工具返回非空内容 |
| `empty` | EMPTY_RESULT | false | 工具返回空串 |
| `timeout` | TOOL_TIMEOUT | **true** | 抛 `AgentTimeoutError` |
| `error` | TOOL_ERROR | false | 抛 `AgentToolError` 或其他异常 |

失败时 ToolMessage 的内容是**结构化 JSON**，不是中文散文：

```json
{"code": "TOOL_TIMEOUT", "status": "timeout", "retryable": true, "message": "调用超时：..."}
```

★ **key 必须是调用 id**：同一轮里 MiniMax 常常并发调同一个工具 2~3 次，
按工具名做 key 会让后一次覆盖前一次（实测：成功的那条被 timeout 冲掉）。

## §4 状态存放在哪（全局地图）

| 状态 | 位置 | 生命周期 | 线程安全 |
|---|---|---|---|
| `ModelManager` | `app.state.model_manager` | 进程 | 无锁，但只写一次 |
| `RagModel` | `app.state.rag_model` | 进程（app 级单例） | 双检锁 `api/dependencies.py:35` |
| `MessageManager.sessions` | `utils/message/message.py` **模块级全局** | 进程，**只增不减** | ⚠️ 无锁 |
| LangGraph 图 | `agent/runtime.py::_graph` | 进程（懒加载单例） | 编译后只读 |
| Agent 会话状态 | 每次 `graph.invoke()` 的 state | 单次请求 | 天然隔离 |
| 向量数据 | Milvus 集合 + alias | 永久 | — |
| 上传原文 | `documents/`（容器内 bind mount） | 永久 | — |
| 解析文本 | `txt/`（容器内 bind mount） | 永久 | — |
| 切分哈希索引 | `txt/.file_filter.json` | 永久 | — |

★ **FastAPI 的 `Depends` 缓存只在单个请求内有效**，跨请求不复用。
所以"便宜"的依赖（`ChatModel`）每请求现建无妨，"贵"的（`RagModel`，实测 ~0.45s，
其中 ~0.42s 是建 embedding HTTP 客户端）必须自己做成 app 级单例。
连接失败时**不缓存** → 下次请求重试（否则启动期一次抖动会让进程永远检索不了）。

## §6 风险地图（按"什么时候会咬人"排序）

### 6.1 会让服务直接起不来

| 风险 | 触发条件 | 现状 |
|---|---|---|
| 依赖漂移 | `requirements.txt` 少锁直接依赖 → 传递依赖解析到新版 → `ImportError` | 已修（全锁定 139 包）。★ **2026-11-18 实际发生过**：镜像 build 自旧快照 → `langgraph-prebuilt 1.0.13` 与 `langgraph 1.0.5` 不兼容 → 容器起不来 |
| `python-multipart` 缺失 | FastAPI 的 `UploadFile`/`Form` 需要它，它**不是** fastapi 的硬依赖 | 已修（显式写入 requirements.txt） |
| 镜像与代码不同步 | 改了代码但没重建镜像 | ★ 2026-11-18 同一次事故的另一面 |

### 6.2 会静默给出错误结果

| 风险 | 后果 |
|---|---|
| 索引端 / 检索端嵌入模型名不一致 | 向量空间对不上 → **检索全是噪声但不报错**（维度一样 Milvus 不管） |
| Milvus `host`/`port` 参数被静默忽略 | 容器里连到 `localhost:19530` → 检索失败（现在会明确抛 `RetrievalError`） |
| `calculator` 返回 `"ERROR: ..."` 字符串而不是抛异常 | 工具状态被记成 `success` → Agent 以为算成功了 |

### 6.3 架构性缺口（已知，不影响单用户使用）

| 缺口 | 说明 |
|---|---|
| **Agent 无多轮记忆** | `runtime.ask()` 每次 invoke 都传全新的 `{"messages": [HumanMessage(question)]}`；`session_id → thread_id` 传了但图没有 checkpointer，`thread_id` 没人读。三个 LLM 节点也从不把 `state["messages"]` 发给 LLM（每次从零拼 prompt） |
| **`collect_round_material` 名不副实** | 边界是"最后一条 HumanMessage 之后"，但全流程只有一条 HumanMessage → 素材是**跨轮累积**的，不是"本轮" |
| **prompt 里的 `{question}` 占位符从不 `.format()`** | `agent/prompts/*.py` 里的花括号是字面量，真值靠**另一条** HumanMessage 带进去。改 prompt 时别以为可以用 `.format()` |
| **`MessageManager.sessions` 只增不减** | 每次新会话（不传 session_id）都新建一个条目，永不清理 → 长期跑会涨内存 |
| **`/chat` `/rag` 是 `async def` 但内部同步阻塞** | 一次请求占住事件循环直到 LLM 返回（最长 60s）。`/agent/chat` 早在 v2.2 就用普通 `def` 规避了，这两条 v1 老端点没跟进。⚠️ **单人使用下不咬人**（已降级归档，见 `项目现状.md` §8 P3-17）。⚠️ **改它不是"改两行"** —— 改成普通 `def` 会让它们进 FastAPI 线程池，`MessageManager.sessions`（`utils/message/message.py:8`，**无锁**）就从"事件循环串行化"变成"多线程无锁访问"，**必须连带加锁** |
| **`api_file.py` 的 `parse_results` 恒为 `null`** | `txt_main.main()` **从不返回字典**（只有 `return` 和 `return None`），但 api_file.py 的注释说"依赖 main() 返回结果字典" |
| **`word_txt.py` 死分支** | `process_single_docx(output_path=None)` 引用不存在的 `self.output_folder` → `AttributeError`。主流程总传 output_path，所以碰不到 |
| **`pdf_txt.py` 重复 except** | `process_single_pdf` 里连续写了两遍**一模一样**的 `except Exception`（`pdf_txt.py:236` 与 `:240`），第二个是死代码（另有一处 `:195` 在别的函数里，是正常的） |
| **`.doc` 支持不一致** | `FileScanner` 支持 `.doc`，但上传白名单 `SUPPORTED_FILE_TYPES` 不含 `.doc` → 手动放进 `documents/` 的 .doc 会被解析，上传 .doc 会被拒 |
| **3 个占位工具** | `weather` / `web_search` 是占位实现；`calculator` 只做四则运算 |
