## 0. ⚠️ 先推翻我自己的一个旧结论

之前我跟你说「`tool_calls` 悬空 → MiniMax 报 400」。**这句话当时没有实测，是我从错误信息里推的，现在实测下来它只对了一半。**

### 实测 1：直连 MiniMax API，构造悬空 tool_calls

```
POST {MINIMAX_BASE_URL}/chat/completions
messages = [user, assistant(content=None, tool_calls=[{id: "call-xxx", ...}])]   # 没有 tool 应答
→ HTTP 400
{
  "type": "error",
  "error": {
    "type": "bad_request_error",
    "message": "invalid params, tool call and result not match (2013)",
    "http_code": "400"
  }
}
```

对照组（补上 `role:"tool"` 的应答）→ **HTTP 200**，正常继续。

**所以 400 是真的**，错误码 2013 属实。（我之前说的错误文案是 "tool call result does not follow tool call"，实际是 "tool call and result not match"，以实测为准。）

### 实测 2：真实图跑一遍（有 2 个悬空）

```
=== AIMessage 发出的 tool_calls ===
  OK   id=call_7bb8f31176504aa3a3cf0d76  tool=rag_search
  OK   id=call_e13c5bf501df49df944f7b94  tool=rag_search
  OK   id=call_abcaf152a37e4575b03799c8  tool=rag_search
  OK   id=call_01a1dea6f5af73f0aa33cfdf  tool=rag_search
  OK   id=call_01a1dea6f5af73f0aa33cfdcfe0  tool=rag_search
  💥 悬空  id=call-a2b31e24-fb66-4580-8386-52756b6a7307  tool=rag_search
  💥 悬空  id=call-b8430d0a-7ea2-4fab-9edc-0aa542591bba  tool=rag_search
悬空数量: 2 / 总调用 7
tool_status = {'rag_search': 'success'}
iter_count = 3   reflection_count = 1
=== 最终答案 ===（正常输出，没报 400）
```

### 为什么有悬空却没 400？

**因为 v2.2 的三个 LLM 节点，从来不把 `state["messages"]` 发给模型。**

| 节点 | 发给 LLM 的消息 | 证据 |
|---|---|---|
| `iter` | `SystemMessage(ITER_PROMPT)` + `HumanMessage(问题 + 素材 + 计数器)` | `agent/nodes/iter_node.py:70-82` |
| `synth` | `SystemMessage(SYNTH_PROMPT)` + `HumanMessage(问题 + 素材 + 工具状态 + critique)` | `agent/nodes/synth_node.py:74-82` |
| `reflect` | `SystemMessage(REFLECT_PROMPT)` + `HumanMessage(问题 + 答案 + 素材 + 状态)` | `agent/nodes/reflect_node.py:101-110` |

素材来自 `collect_round_material(state["messages"])`（`agent/nodes/material.py`），
**它只挑 `ToolMessage`**，把 AIMessage 全部丢掉。

所以那条「有 tool_calls 但没有 ToolMessage」的 AIMessage **从来没有进过任何一次 API 请求** → MiniMax 自然不会校验 → 不会 400。

### 结论

| | 之前的说法 | 实测后的说法 |
|---|---|---|
| 悬空本身 | 存在 | ✅ 存在，而且每轮都会发生（iter #3 的 tool_calls 必被丢弃） |
| 会 400 吗 | 会 | ❌ **现在不会** —— 因为消息历史没进 API |
| 什么时候会炸 | 未知 | ⚠️ **一旦为了做多轮记忆而把 `state["messages"]` 传给 LLM，立刻炸** |

**这不是可以永远不修的 bug，而是一颗定时炸弹：它的引信就是 O-001（多轮记忆 / checkpointer）。**
O-001 一做，第一个崩的就是它。所以顺序上必须是：**先修悬空 → 再做多轮记忆**。

> 顺带暴露一个更大的问题（见 §8.1）：**现在的 Agent 完全没有多轮记忆**，一次请求的 `messages` 只有一条 HumanMessage。

## 1. 四个状态 vs 两个异常 —— 到底丢了哪一维

### 1.1 你的直觉是对的，但丢的不是「status 枚举」

先看实际映射（`agent/nodes/status_tool_wrapper.py`）：

| status | 什么时候产生 | 对应异常 | 可重试？ |
|---|---|---|---|
| `success` | 工具返回非空内容 | —（不抛异常） | — |
| `empty` | 工具返回空字符串 | —（不抛异常） | — |
| `timeout` | 工具抛 `AgentTimeoutError` | `AgentTimeoutError` | ✅ 可重试 |
| `error` | 工具抛 `AgentToolError` 或其他异常 | `AgentToolError` | ❌ 不可重试 |

**关键点：4 个 status 和 2 个异常不是同一个维度轴。**

- `status` = **结果维度**：这次调用最终怎么了。4 种结果，**没丢，全覆盖**。
- `异常` = **失败分类维度**：只在失败时才存在。`success` / `empty` 不抛异常，所以「2 个异常」覆盖的是「4 个结果里的 2 个失败项」，天然是 2 不是 4。

所以「4 个状态 vs 2 个异常」这个 1:2 的比例本身**不代表少了一维**。

### 1.2 真正缺的那一维：**「可重试性」没有成为一等公民**

现在的 `tool_status` 存的是一个字符串：

```python
tool_status = {"rag_search": "timeout"}     # 只有结果，没有「能不能再来一次」
```

LLM 想知道「这个失败要不要重试」，只能靠 **prompt 里写死的硬约束**：

```
agent/prompts/reflect_prompt.py
  工具 timeout/error/empty 时不应判 re_iterate
```

这是把「可重试性」藏在**自然语言 prompt** 里，而不是放在**结构化数据**里。工业化做法是把它做成字段。

### 1.3 具体的三处压缩（这才是真问题）

**(a) `error` 把 3 类重试语义压成 1 类**

`AgentToolError` 一律「不可重试」，但实际上：

| 底层真实错误 | 实际上该不该重试 | 现在被归成 |
|---|---|---|
| LLM 传错参数（query 拼错） | ✅ 该重试（换个参数） | error（不可重试） |
| Milvus 短暂不可用 / 429 限流 | ✅ 该重试（退避后） | error（不可重试） |
| 代码 bug（`NoneTypeError`） | ❌ 不该重试 | error（不可重试） |

→ **「不可重试」这个判断现在是在骗 LLM。**它会让 Agent 在 Milvus 抖一下时直接放弃，而不是退避重试。

**(b) `empty` 把「没有」和「坏了」压成 1 类**

`core/rags/rags.py` 里检索失败也是 `return []`（`except Exception: return []`），
所以工具层看到的都是空字符串 → 一律 `empty`。
→ 「知识库里确实没有相关内容」（正常）和「Milvus 挂了」（故障）分不开。
（这条已在 CLAUDE.md「已知遗留」里记着，因为改它会连带影响 `/rag`。）

**(c) `success` 不含质量信息**

工具返回了一堆无关内容，也是 `success`。这一维工业上叫「结果可信度 / 命中质量」。

### 1.4 建议的演进方向（不是现在做）

把 status 从字符串升级成结构化对象：

```python
tool_status = {
    "call_abc123": {
        "tool": "rag_search",
        "status": "timeout",        # success / empty / timeout / error
        "retryable": True,          # ← 新增：能不能重试
        "code": "TOOL_TIMEOUT",     # ← 新增：机器可读的失败码
    }
}
```

同时把 ToolMessage 的内容从中文散文改成结构化 payload：

```
现在：ToolMessage(content="查询超时")
之后：ToolMessage(content='{"code":"TOOL_TIMEOUT","retryable":true,"msg":"检索超时"}')
```

**为什么这条重要**：LLM 是靠语义猜的，不是靠代码。散文它也能猜，但**结构化 payload 可以被程序断言、可以被 eval 打分、可以不依赖 prompt 措辞**。
prompt 里写「timeout 时不要 re_iterate」是软约束；`retryable: false` 是硬数据。

> **适配度判断**：你现在的 4 状态设计，对**个人项目 / 面试作品**是**足够且正确**的 —— 90% 的工业系统也就做到「结果分类 + 失败归一化」这一步。
> 上面这些是 P2 级的深化，不做不影响项目成立。但 (a) 那条（把限流误判成不可重试）在**部署到真实环境**后会真的疼。

## 2. `tool_status` 的 key 粒度 + 调用 id 到底怎么来的

### 2.1 实测：覆盖是真的

构造一轮里两次调用同一个工具（一次成功、一次超时）：

```
=== tool_status 最终值 ===
{'rag_search': 'timeout'}

=== 实际产生的 ToolMessage ===
  id=call_ok        content='关于 正常问题 的检索结果'
  id=call_timeout   content='查询超时'

→ 状态字典里有 1 个键，两次调用只留下 1 条状态，超时的那个把成功的覆盖了
```

### 2.2 你问的「同名工具干扰」—— 现在到底会不会被咬到？

分两种情况，**第二种今天就在发生**：

| 情况 | 说明 | 今天会不会发生 |
|---|---|---|
| **A. 两个不同工具同名** | 注册了两个叫 `rag_search` 的工具 | ❌ 不会。工具名在注册时就唯一（`agent/tools/__init__.py` 里 `ALL_TOOLS` 是固定 4 个：`rag_search` / `calculator` / `weather` / `web_search`） |
| **B. 同一轮里并发调用同一个工具 2 次** | MiniMax 一次决策发 2~3 个 `rag_search` | ⚠️ **会，而且每次 iter 都在发生**。实测里 7 次调用里 5 次是 `rag_search`，iter #3 一次就发了 2 个 |

**所以「同名工具」这个说法不准确，真正的触发条件是「同一工具在同一轮被并发调了多次」。**
而这恰恰是 MiniMax 的稳定行为（它在 prompt8 的 trace 里就一次发 2~3 个）。

### 2.3 危害到底有多大？—— 比想象的小，但不是没有

关键在于：**工具返回的全文（材料）和工具状态（摘要）是两条独立通道。**

- **材料通道**：`collect_round_material()` 收集本轮**全部** ToolMessage，两条都在 → LLM 能看到「一次成功、一次超时」的完整事实。
- **状态通道**：`tool_status` 字典 → 只剩 1 条，且是「后写覆盖先写」（`_merge_tool_status` 做 `{**old, **new}`）。

→ **LLM 不会因此变瞎**（材料里有完整信息），但 `tool_status` 作为「摘要」是**错的**。
如果将来你只看 `tool_status` 做监控/告警/评估，或者把状态字典塞进 prompt 的显眼位置，摘要和事实就对不上了。

### 2.4 调用 id 从哪来？—— 答案：**模型生成，我们只是接收**

这是你问的第 2 个小问题，也是很多新人的误区。链路是：

```
MiniMax 服务端  ──生成──▶  tool_call.id = "call_7bb8f31176504aa3a3cf0d76"
                                    │
                                    ▼
                      HTTP 响应 JSON 里 tool_calls[].id
                                    │
                                    ▼
        langchain_core/output_parsers/openai_tools.py:76  parse_tool_call()
                    parsed["id"] = raw_tool_call.get("id")   ← 原样取出，不改
                                    │
                                    ▼
        langgraph ToolCallRequest.tool_call = {"name", "args", "id"}
                                    │
                                    ▼
        agent/nodes/status_tool_wrapper.py:42
                    tool_call_id = tool_call["id"]           ← 我们已经在用了
```

**回答你的三个候选：**

| 你的猜测 | 对不对 |
|---|---|
| 每个工具自己设计一个调用 id？ | ❌ 不对。工具是被别人调用的，它不知道自己的调用序号 |
| 运行的时候随机生成？ | ⚠️ 半对。id 确实是「随机」的，但**不是我们随机生成的**，是**模型/API 生成的**。我们不能自己造，因为 ToolMessage 的 `tool_call_id` 必须和 AIMessage 里那个 id **一模一样**，否则对不上 |
| —— | ✅ **正解：直接用 `request.tool_call["id"]`，它已经是现成的** |

**而且我们代码里已经在用了**：`status_tool_wrapper.py:42` 的 `tool_call_id = tool_call["id"]` 就是它。
只是写 `tool_status` 的时候没用它当 key，用了 `tool_name`。所以这个 bug 的本质是：

> **id 我们手上一直有，却用错了地方 —— 拿来给 ToolMessage 配对了，却没拿来给状态字典配 key。**

### 2.5 建议的改法（before / after）

**现状**（`agent/nodes/status_tool_wrapper.py:56-59`）：

```python
    return Command(update={
        "messages": [result],
        "tool_status": {tool_name: status},      # ← 按工具名 key
    })
```

**改成**（按调用 id key，同时保留工具名，便于渲染成 prompt）：

```python
    return Command(update={
        "messages": [result],
        "tool_status": {
            tool_call_id: {"tool": tool_name, "status": status}
        },
    })
```

**连带要改的地方**（这才是工作量所在）：

| 位置 | 现在 | 要改成 |
|---|---|---|
| `agent/state.py:48-50` `_merge_tool_status` | `{**old, **new}` | 保持不变即可（按 id key 后天然不覆盖） |
| `agent/nodes/synth_node.py:34-38` `_format_tool_status` | `f"- {name}: {status}"` | `f"- {name}（{call_id}）: {status}"` 或按工具名分组聚合 |
| `agent/nodes/iter_node.py:77` | `f"- tool_status: {state.get('tool_status', {})}"` | 格式变了，但只是展示，跟着改 |
| `agent/runtime.py:113` `tool_called` | `bool(result.get("tool_status", {}))` | 不用改（bool 语义不变） |

**为什么改成 id 之后「覆盖」问题自动消失**：因为 id 天然唯一，两次同名调用是两个不同的 key。
`{**old, **new}` 合并时不会互相覆盖。

> **但要注意**：改完之后 `tool_status` 从「按工具名索引」变成「按调用索引」，
> 如果你在别处按工具名去查（我查了，目前没有），要一起改。
> 另外这也顺手把 §1.2 说的「可重试性」字段加进去的路径铺好了 —— 建议一次改到位，别改两遍。

## 3. 官方 `wrap_tool_call` 是什么

### 3.1 签名与语义

LangGraph 1.0.5 的 `ToolNode` 提供了一个**官方拦截点**：

```python
def wrap_tool_call(request: ToolCallRequest, execute: Callable[[ToolCallRequest], ToolMessage | Command]) -> ToolMessage | Command
```

- `request` —— `ToolCallRequest`，里面有 `request.tool_call = {"name": ..., "args": ..., "id": ...}`、`request.state`（当前图状态）、`request.runtime`。
- `execute` —— 真正执行这次工具调用的可调用对象。**你可以调它一次，也可以调多次（重试）**。
- 返回值 —— `ToolMessage`（普通工具结果）或 `Command(update={...})`（要顺便写 state 字段时）。

用起来就是：

```python
ToolNode(ALL_TOOLS, wrap_tool_call=status_wrapper)
```

每次工具调用都会**先经过 `status_wrapper` 一次**，你的代码决定「怎么执行、记什么状态、失败时返回什么」。

### 3.2 为什么官方要提供这个钩子？

因为 `ToolNode` 内部把「被调用的方法」钉死成了 `_func`：

```python
# langgraph/prebuilt/tool_node.py
super().__init__(self._func, self._afunc, ...)
```

而 LangGraph 调度节点走的是 `node.invoke(...)` → `self.func` → 父类原版 `_func`。
**所以你继承 `ToolNode` 再重写 `__call__`，你的代码永远不会被执行**（v2.1 踩过这个坑，v2.2 才改对）。
`wrap_tool_call` 是框架明确留给用户的扩展点：不碰内部实现、不受参数名约束、跨版本稳定。

### 3.3 对我们有什么用

1. **拦截点天然在「工具真正执行」的那一刻** —— 成功、抛异常、返回空，都在同一个地方收口。
2. **可以返回 `Command(update=...)`** —— 所以我们能顺便写 `state["tool_status"]`，而不只是返回一条 ToolMessage。
3. **失败时也能返回 ToolMessage** —— 这是防「有 tool_calls 没应答」的关键（但注意：我们在 wrapper 里自己补 ToolMessage，只能防**工具层**的悬空，防不了 `should_continue` 直接路由走导致的悬空，见 §5）。

## 4. 协作式超时、熔断、僵尸线程

### 4.1 「协作式超时」= 单次动作超时 + 全局总时限，两层

对照你的提问：

> 「协作式超时的意思就是工具节点或者是单节点的单次超时限制跟全局的超时限制这个操作是吗？」

✅ **对，就是这个意思。**我们现在的三层里，第 2、3 层是「协作式」的：

| 层 | 位置 | 检查时机 | 谁在守 |
|---|---|---|---|
| 第 2 层 单次动作超时 | `agent/timeout.py::Timer` | 工具**正在跑**的时候 | `Timer` 在外面等，超了就抛 `AgentTimeoutError` |
| 第 3 层 全局总时限 | `state["deadline"]` + `is_expired(state)` | 每个节点**动手之前** | 节点自己看一眼，超了直接收摊 |

「协作式」这个词的意思是：**没有中央执法者去 kill 谁，而是每个参与者自己在动手前看一眼表**。

### 4.2 这跟「熔断」是**两回事**

| | 协作式超时（我们有） | 熔断器 / circuit breaker（我们**没有**） |
|---|---|---|
| 触发条件 | 单次调用耗时 > N 秒，或总时长 > 总时限 | **连续失败 N 次**（比如连挂 3 次） |
| 动作 | 这一层放弃 | **短期内直接跳过这个下游**，不再打它（快速失败） |
| 恢复 | 下次自然重试 | 冷却窗口结束后半开试探 |
| 解决的问题 | 「别让用户等太久」 | 「别在明知挂掉的东西上反复浪费时间」 |
| 工业名字 | timeout / deadline / cancellation | circuit breaker（熔断降级） |

**我们目前完全没有熔断。**举例：Milvus 挂了 → 每次工具调用都要等满 30 秒超时 → 3 次 iter = 90 秒 → 撞总时限。
有熔断的话：第一次失败就标记「Milvus 疑似挂掉」，第二次直接秒失败 → 3 次 iter 几毫秒结束。

> **适配度判断**：熔断是**服务化部署**才需要的（你的 Agent 跑在 Docker 里，Milvus 是独立容器）。
> 你现在单机跑，熔断的收益不大，**可以先不做，知道有这么个东西就行**。

### 4.3 「僵尸线程占着 Milvus/Ollama 连接」—— 解决了吗？分两层看

> 「避免了 Python 线程不可杀 → 僵尸线程占着 Milvus/Ollama 连接。意思是解决了这个困扰？」

**分两层，答案不一样：**

| 层 | 有没有僵尸线程 | 说明 |
|---|---|---|
| **图级**（外层包 `graph.invoke`） | ✅ **解决了** —— 我们**没有**用外层包裹 | 原来那种写法会留下一条后台线程继续跑完整张图；现在改成每个节点自己查 `deadline`，图会正常结束，没有后台残留 |
| **工具级**（`Timer` 里那个线程） | ⚠️ **没解决** | Python 没有 `Thread.terminate()`。`Timer` 超时后只是「不再等」，**底层那个线程还在跑**，还会跑完，还会占着 Milvus 连接 |

`agent/timeout.py` 里的关键代码：

```python
finally:
    ex.shutdown(wait=False)   # ⚠️ 不能用 with
```

`with ThreadPoolExecutor(...)` 在退出时会**等所有任务跑完**（`shutdown(wait=True)`），
那样超时形同虚设。所以必须 `shutdown(wait=False)` —— 但这只是「不等了」，**不是「杀掉了」**。

**真实影响**：一次工具超时后，那个线程会在几秒~几十秒后自己结束，短暂占着一个连接。
对个人项目 / 面试作品 **完全可接受**。要彻底解决需要：
- 换进程（`multiprocessing`，可 kill，但序列化开销大）
- 或让底层调用本身可取消（httpx 的 `timeout=` 参数让连接层自己放弃 —— 这条我们已经在 LLM 层做了，Ollama embedding 层还没做，见 §8.4）

### 4.4 「不用内外层计时器」这个决定，现在依然成立

> 「工具调用和使用 rag 检索这其实就是工具问题，在这里使用一次计时器就可以了，没必要内层跟外层吧。」

✅ 你的判断是对的。RAG 检索就是 4 个工具之一的实现（`rag_search` → `RagModel.retrieve`），
所以「工具超时」一个就够，不需要再给检索单独套一层。
现在代码里也确实只有一层：`rag_tool.py:58` 的 `Timer(TOOL_TIMEOUT).call(model.retrieve, ...)`。

## 5. `tool_calls` 悬空为什么存在（重新讲一遍）

### 5.1 根因：`should_continue` 的**检查顺序**反了

`agent/nodes/should_continue.py`：

```python
def should_continue(state: dict) -> str:
    if state.get("expired"):
        return "__end__"
    if state.get("iter_count", 0) >= MAX_ITER:   # ← 先判这个
        return "synth"
    last_message = state["messages"][-1]
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "tools"                            # ← 后判这个
    return "synth"
```

**当 `iter_count >= MAX_ITER`（第 3 次决策）时，函数在第 2 行就 return 了，
根本没走到第 3~4 行去看「这条 AIMessage 有没有 tool_calls」。**

于是：

```
iter #1  发出 tool_calls(2个) → should_continue: iter_count=1 < 3 → 走 tools ✅
         tools 执行 2 次 → 产生 2 条 ToolMessage ✅
iter #2  发出 tool_calls(2个) → iter_count=2 < 3 → 走 tools ✅
         tools 执行 2 次 → 产生 2 条 ToolMessage ✅
iter #3  发出 tool_calls(2个) → iter_count=3 >= 3 → 直接 return "synth" ❌
         → 这 2 个 tool_calls 永远不会被执行
         → 那条 AIMessage 留在 messages 里，但没有对应的 ToolMessage → 悬空
```

**实测完全吻合**：7 次调用里，前 5 次有 ToolMessage，最后 iter 发出的 2 个悬空。

### 5.2 为什么以前没发现

因为**它以前是「无害」的**：
- v2.1 时 `rag_search` 有一句中文兜底串（`"（知识库中没有找到相关文档）"`），
  status 恒为 `success`，reflect 看到明文就判 `end`，图跑 7 步就结束，
  `iter_count` 根本到不了 3。
- v2.2 去掉兜底串后，iter 才真的会跑到第 3 次 → 悬空才暴露。
- 而因为三个节点都不发 `state["messages"]` 给 LLM，所以**连 400 都不会报** —— 它就一直躺着。

### 5.3 修法（两个方向，建议 ①）

**① 让 iter 在到达上限时就不发 tool_calls（推荐）**

在 `iter_node.py` 里，`iter_count >= MAX_ITER` 那个分支（现在是直接返回 `"已达迭代上限，结束"`），
**问题不在这个分支，而在于第 3 次 iter 仍然调了 LLM，LLM 仍然发了 tool_calls**。

> 看代码：`iter_node.py:58` 的边界检查读的是 `iter_count = state.get("iter_count") or 0`，
> 而 `iter_count` 在 state 里是**上一次的累计值**。第 3 次进入 iter 时 `iter_count` 已经是 2，
> `2 >= MAX_ITER(3)` 为 False → **不触发边界分支** → 照样调 LLM → 照样发 tool_calls。
> 然后 `should_continue` 拿到 `iter_count=3` 才拦截。**拦截点晚了一步。**

修法：把边界判断改成 `iter_count + 1 >= MAX_ITER`（即「再调这一次就是最后一次，也不该发工具」），
或者更稳的做法 —— 在 iter 节点里**即使 LLM 发 了 tool_calls，也要主动清掉**：

```python
    # iter 节点末尾，兜底：这一轮是最后一轮，不该再发工具
    if (iter_count + 1) >= MAX_ITER and getattr(response, "tool_calls", None):
        # 去掉 tool_calls，让 should_continue 自然路由到 synth
        response = AIMessage(content=response.content or "已达迭代上限")
```

**② 让 `should_continue` 先判 tool_calls**

把两段判断调换顺序：先看有没有 tool_calls，有就去 tools（执行掉），再看 iter_count。
这样永远不会产生悬空，但会**多跑一轮工具**（第 3 次 iter 的工具也会执行），且 `MAX_ITER` 就不是硬上限了。

> **建议 ①**，理由：① 不改变「iter 最多 3 次」这个语义上限；② 会让实际工具调用次数变成 3 轮 × N 次，
> 和「MAX_ITER=3 是硬上限」的设计意图冲突。
> 修 ① 之前**必须先有回归测试**（你之前说过「先记录，不修，等有回归测试再动」——这个判断是对的）。

## 7. 「下游不该再认第三方异常类型」是什么意思？工业化真的这么做吗

### 7.1 这句话在说什么

对比两种写法：

**❌ 下游认第三方异常（反模式）**

```python
# agent/nodes/status_tool_wrapper.py 里如果这么写：
except httpx.ReadTimeout:          # ← 下层节点知道了 httpx 的存在
    status = "timeout"
except openai.APITimeoutError:     # ← 又知道了 openai 的存在
    status = "timeout"
except pymilvus.exceptions.MilvusException:
    status = "error"
```

问题在哪：

1. **换了库就全崩**。哪天 Milvus 客户端从 `pymilvus` 换成 `milvus-lite`，这个 except 分支直接失效 —— 而且是**静默失效**（异常不再被捕获，走通用 except，状态从 `timeout` 变成 `error`）。
2. **依赖泄漏**。上层节点（本来只该懂「Agent 业务」）被迫知道基础设施细节。
3. **分类逻辑爆炸**。第三方库的异常类型有几十种，每加一个新依赖就要在每个上层节点里补 except。

**✅ 下游只认自家异常（我们现在的做法）**

```
第 1 层  原始异常（httpx.ReadTimeout / pymilvus 的各种错 / openai.APITimeoutError）
              ↓  agent/tools/rag_tool.py:63  ← 唯一的翻译点
第 2 层  归一化异常（AgentTimeoutError / AgentToolError）
              ↓  agent/nodes/status_tool_wrapper.py:46-52
第 3 层  业务状态（tool_status = {"rag_search": "timeout"}）→ 给 LLM 看
```

上层节点只写：

```python
except AgentTimeoutError:   # 只认自家的
except AgentError:          # 只认自家的
except Exception:           # 兜底（某个工具忘了归一化）
```

**「翻译一次」的意思是：翻译点唯一**。在 `rag_tool.py` 里翻译一次（离异常最近的地方），
之后所有上层都不再翻译。如果上层又翻译一遍（比如 `except httpx.ReadTimeout`），
就等于「翻译了两次」—— 同一件事有两个真相来源。

### 7.2 工业化真的这么做吗？—— **是的，这是标准做法，有正式名字**

| 说法 | 出处 | 含义 |
|---|---|---|
| **Anti-Corruption Layer（防腐层）** | Eric Evans《DDD》 | 隔离外部系统的模型，防止外部概念渗透进自己的领域模型 |
| **Ports & Adapters（六边形架构 / 端口适配器）** | Alistair Cockburn | 业务核心定义「端口」（接口），基础设施实现「适配器」；业务只认端口 |
| **Repository / Gateway Pattern** | 各家 | 数据库/外部服务必须经过一层仓储/网关，不允许直接调驱动 |
| **Exception Normalization / Error Translation** | 微软 .NET / Google SRE 实践 | 在边界把异构错误翻译成自家统一错误类型 |

在 Python 生态里也到处都是：

- `requests` → 你的代码不该 catch `urllib3.exceptions.ReadTimeoutError`，该 catch `requests.exceptions.Timeout`
- `sqlalchemy` → `sqlalchemy.exc.OperationalError`，业务层不该 catch `psycopg2` 的错
- `httpx` → `httpx.HTTPStatusError`

**我们做的事完全对应「防腐层」**：Milvus / Ollama / httpx 是「外部系统」，
`AgentTimeoutError` / `AgentToolError` 是「我们自己的模型」，
`rag_tool.py` 就是那道防腐层。

### 7.3 为什么这条在你的项目里特别有价值（面试角度）

面试官问「你的 Agent 工具失败怎么处理？」，两种答法天差地别：

- ❌ 「我在工具里 try/except 了 TimeoutError」
- ✅ 「我在工具层做了一次**异常归一化**（防腐层）：把所有第三方异常翻译成 `AgentTimeoutError`（可重试）和 `AgentToolError`（不可重试）两个语义类别，上层只认这两个，不认第三方异常类型。这样换底层库不用改上层，换成限流/参数错也能在同一个位置重新分类。」

第二种回答里出现的词 —— **异常归一化、防腐层、边界翻译、可重试语义** —— 就是工业界的词汇。
这也是为什么值得在面试里讲（见 `MEMORY.md` 的「面试策略」：只讲 v2 设计，不讲 v1 踩坑）。

## 8. 你没问、但你该知道的事

### 8.1 ⭐ 你的 Agent 现在**完全没有多轮记忆**（这是个大问题）

**代码证据**：

```python
# agent/runtime.py:90-98
result = graph.invoke(
    {"messages": [HumanMessage(question)], ...},   # ← 每次请求都是全新的 messages
    config=config,
)
```

- `state["messages"]` **每次 invoke 都从一条 HumanMessage 开始**
- `session_id` → `thread_id` 传进去了，但**图没有 checkpointer**，`thread_id` 是个没人看的参数
- 三个节点也从不读历史消息（§0 的表）

**所以：**
1. 用户说「继续刚才那个」，Agent **不知道**「刚才那个」是什么
2. `session_id` 目前是**纯装饰**
3. 你之前想做的「前端建会话 + session_id 决定历史消息列表」——**没有 checkpointer 就实现不了**，
   得先加 checkpointer（O-001）

**注意这跟 §0 的悬空 bug 是同一件事的两面**：
做多轮记忆的**最自然实现方式**就是「把 `state["messages"]` 传给 LLM」→ 悬空 AIMessage 立刻进请求 → MiniMax 400。
所以顺序必须是：**先修悬空（§5.3 方案 ①）→ 再上 checkpointer**。

### 8.2 `iter` 的占位消息会污染消息列表

`iter` 节点成功但不需要调工具时，返回 `AIMessage(content="READY")`；
异常兜底时也返回 `"READY"`；边界时返回 `"已达迭代上限，结束"`。

这些**占位消息**都进了 `state["messages"]`。目前无害（因为没人发 messages 给 LLM，
而且 `last_answer` 已经单独存了答案），但一旦做多轮记忆，这些垃圾消息会一起被发出去，
模型会看到一堆莫名其妙的 `"READY"`。**做 O-001 之前要处理掉**。

> 顺带：`iter` 的 `"READY"` 提示词在 `agent/prompts/iter_prompt.py` 里，
> 它的存在只是为了让 iter 节点「有话说」—— 因为 v2.2 把 iter 和 synth 拆开了，
> iter 输出的 content 其实没有任何下游消费者。

### 8.3 MiniMax 的 tool_call id 有**两种格式**

实测同一次运行里：

```
call_7bb8f31176504aa3a3cf0d76        ← 下划线 + 24 位 hex
call-a2b31e24-fb66-4580-8386-52756b6a7307  ← 连字符 + 标准 uuid4
```

搜遍了 `langchain_core` / `langchain_openai` / `openai` / `langgraph`，
**没有哪个库生成 `call-<uuid>`** → 说明这是 **MiniMax 服务端自己生成的**（不同代码路径两种格式）。

**影响**：不影响正确性（我们只是原样透传），但如果你以后要按 id 前缀做正则/日志分组，会踩坑。
**结论：id 一律当不透明字符串处理，不要解析它的格式。**

### 8.7 FastAPI 端点必须是普通 `def`

```python
# api/api_agent.py

def agent_chat(request: AgentRequest) -> AgentResponse:   # ← 不是 async def
```

`ask()` 是同步阻塞的（要等 LLM 30s + 工具 30s）。写在 `async def` 里会**占住事件循环**，
整个 FastAPI 服务（包括 `/chat`、`/rag`、文件上传）全部卡死。
FastAPI 对普通 `def` 端点会自动丢到线程池。**这是 v2.2 修过的 bug，别改回去。**

### 8.8 `tool_status` 出现在两处 prompt 里，格式改了就两处都要改

- `iter_node.py:77` —— 给决策节点看「当前状态」
- `synth_node.py:78` —— 给综合节点看

而且 `synth_node.py:34-38` 的 `_format_tool_status()` 会把整个 dict 塞进 prompt。
如果按 §2.5 改成嵌套结构，这个函数要重写（不然 prompt 里会出现 Python dict 的裸 repr）。
