## O-001｜多轮记忆：session_id 接入（LangGraph Checkpointer 方案）

| 项 | 内容 |
|---|---|
| **优先级** | P1（多轮对话是 Agent 的基本能力，但排在 P0 三件之后） |
| **状态** | **方案已拍板（方案 A / Checkpointer），未实施** |
| **提出日期** | 2026-11-10（prompt4 讨论 → prompt5 确认方案 A） |
| **关联问题** | `项目状态.md` P2-7（Agent 无 checkpointer，session_id 是摆设） |

### 一、背景

- `api/api_agent.py:19` 的 `AgentRequest` 已有 `session_id: str | None` 字段；
- `agent/runtime.py:66` 也已经把 `session_id` 转成了 LangGraph 的 `thread_id`；
- **但 `agent/graph.py:67` 的 `workflow.compile()` 没有传 checkpointer**，LangGraph 直接把 `thread_id` 丢掉 →
  **Agent 目前完全无多轮记忆**，`session_id` 只是个装饰。

前端 `web_page/rag_page.py` 也从未发送过 `session_id`。

### 二、方案选型（prompt4 讨论结论）

| | 方案 A：LangGraph Checkpointer | 方案 B：复用 `utils/message/message.py` |
|---|---|---|
| 做法 | `compile(checkpointer=MemorySaver())`，LangGraph 自动存取整个 state | runtime 里手动灌历史 / 存历史 |
| **计数器跨轮累积** | ⚠️ **会，必须额外处理**（见风险 R1） | ✅ 不会（state 每轮全新） |
| 改动量 | graph.py 1 行 + 前端 | runtime.py 十几行 + 前端 |
| LangGraph 原生性 | ✅ 是（面试加分） | ❌ 自己套的 |
| 能否做"中断-恢复 / 人在回路" | ✅ 能 | ❌ 不能 |

**✅ 已拍板：走方案 A。**

### 三、最终的产品交互约定（用户拍板）

> **session_id 的生命周期**

```text
【创建会话】按钮  →  点一次，生成一个全新的随机 session_id（覆盖旧 id）
【刷新页面】      →  id 不变，继续用当前会话
【重新打开页面】  →  id 不变，还是上一次那个会话
【没有对话就关掉】→  id 保留，下次打开还是它（不会自动新建）
```

**要点：**
1. **只有点「创建会话」按钮才会生成新 id**；
2. 刷新、关标签页、重新打开，都**不会**换 id；
3. 即使创建了新会话但一句话没说，id 也照样保留到下次；
4. 因此 **id 必须存在浏览器本地（localStorage）或 URL 里**，
   `st.session_state` **单独用不够**——它跟着 Streamlit 的会话走，标签页关久了就没了。

### 四、改动清单

#### ① 后端 · `agent/graph.py`

```python
from langgraph.checkpoint.memory import MemorySaver
...
return workflow.compile(checkpointer=MemorySaver())
```

#### ② 后端 · `agent/runtime.py`

`session_id` → `thread_id` 的转换**已经存在，不用改**：

```python
config = {"configurable": {"thread_id": session_id}} if session_id else None
```

但要**加一个兜底**：`MemorySaver` 在没有 `thread_id` 时会报错，
所以 `session_id` 为 `None` 时必须走"无存档"路径（`config=None`）——现有代码已经这样写了，**保持即可**。

#### ③ 后端 · `agent/state.py`（配合 R1，见风险区）

`reflection_count` 的合并规则 `_inc_refl` 是**纯累加**，**写 0 清不掉**。
要让"每轮开头清零"能生效，需要把它改成 `_reset_or_inc` 语义
（**注意**：轮内没有任何节点会往 `reflection_count` 写 0，所以改完轮内行为完全不变）。

#### ④ 前端 · `web_page/rag_page.py`

```text
a) 取 id：优先从 localStorage 读；没有则从 URL 参数 st.query_params 读；再没有才用 st.session_state
b) 存 id：localStorage.setItem("ragmi_sid", sid)  +  同步写进 st.query_params（便于刷新/分享/重开）
c) 「创建会话」按钮：sid = str(uuid.uuid4()) → 写 localStorage + query_params + 清空 st.session_state.history
d) 发送请求时带上：json={"query": query, "session_id": sid}
```

> **`st.query_params`（Streamlit 1.52.2 已支持，验证过）**
> 它是 URL 的一部分 → **刷新、复制链接、书签、重开浏览器都能保留**，
> 而且天然支持"把这次对话的链接发给同事"。
> localStorage 则是"同一台电脑同一个浏览器"的持久化。
> **两个一起用**，覆盖用户提的全部场景。

#### ⑤ 前端 · 现有的 🗑️ 按钮（`rag_page.py:52`）

现在只清 `st.session_state.history`。
建议拆成两个按钮：**「🗑️ 清空消息」**（只清界面）+ **「➕ 新建会话」**（换 id + 清界面 + 后端也开新档）。
避免用户误以为"清空 = 新会话"。

### 五、风险 / 坑（**实施前必读**）

| 编号 | 风险 | 说明 | 对策 |
|---|---|---|---|
| **R1** | ⚠️ **计数器会跨轮累积，导致 Agent 逐轮退化** | 加了 checkpointer 后，`iter_count` / `synth_count` / `reflection_count` 都会跟着存档累积。实测：第 1/2/3 轮后分别是 1/2/3。**第 4 轮起** `iter_count=3 >= MAX_ITER` → 小记者不再调工具；`reflection_count=3 >= MAX_REFL` → 审稿人直接短路收工。**Agent 会变成"不查库、不反思"的裸问答。** | 每轮开头在 `runtime.ask()` 里显式把 3 个计数器重置为 0（前提：R1 配套改 `_inc_refl` 语义，见改动 ③） |
| **R2** | 存档里塞的是完整 messages（含 ToolMessage） | 工具返回的 chunk 全文会进存档，**体积增长快** | 短期可接受；长期考虑裁剪历史或用 `SqliteSaver` 落盘 |
| **R3** | 内存版存档**重启即丢、多 worker 各存各的** | `MemorySaver` 是进程内 dict | 长期换 `langgraph-checkpoint-sqlite` / `-postgres` |
| **R4** | 老会话（无 id）会怎样？ | `session_id=None` → `config=None` → 不走存档路径，行为跟现在一致 | ✅ 现有代码已经兼容，无需额外处理 |
| **R5** | 前端如果仍不发 `session_id` | 会一直走无存档路径，功能等于没接上 | 联调时**必须先验证前端确实带上了 id** |

### 二、为什么 `MAX_SYNTH` 是遗留物

**原设计假设**：综合节点自己会判断答案是否完整、失败或超时会自己重新生成 → 所以需要上限。

v2.2 把"判断答案"独立成反思节点后，**这个职责转移了，但计数器没跟着删** → 变成不可达的僵尸参数。

### 三、为什么 `MAX_ITER` 不能删（**关键论证**）

图结构（`agent/graph.py`）：

```text
iter → tools → iter   ← 无条件边（line 48），这个环里 reflection_count 一次都不涨
synth → reflect       ← 反思节点只能从综合节点进入（line 51）
```

**工具循环里根本到不了反思节点。** 所以：

> **`MAX_REFL` 不是工具循环的刹车，`MAX_ITER` 才是。**
> 删掉 `MAX_ITER` → 决策节点反复调工具时永远出不了那个环 → 无限循环。

> ⚠️ **顺带纠正 `CLAUDE.md` 的一处说法**（待确认后修改）：
> 原文"即便 LLM 误判，`MAX_REFL=3` 兜底强制 end"——**这句对工具循环不成立**，
> 因为该路径不经过 reflect。真正的兜底是 `MAX_ITER`。

### 四、`tool_status` 不影响计数器（机械层面）

计数器的加/清**只**发生在 3 个节点自己的返回值里；`tool_status` 是独立的一格，
合并规则 `_merge_tool_status`（字典合并），**没有任何代码根据它去动计数器**。

唯一影响是**间接**的：`tool_status` 写进 prompt → 影响 LLM 判断 → 影响路由 → 影响节点被调几次。
但由于 `tool_status` 目前恒为 `{}`，**这条间接链路现在也是断的**。

### 五、三个场景对照真实代码路径

| 场景 | 用户描述 | 实际代码路径 | 结论 |
|---|---|---|---|
| ① 成功且有内容 | 综合→反思(不足)→重新综合→反思→输出 | 基本一致；额外：反思判 `rewrite` 时**同时**清 `iter_count` | ✅ 基本正确 |

#### 8.2 `StatusToolNode` 的正确修法（已对着 langgraph 1.0.5 源码逐行验证）

**根因（源码级确认）**：

```text
langgraph/prebuilt/tool_node.py:752
    super().__init__(self._func, self._afunc, name=name, tags=tags, trace=False)
      ↓ RunnableCallable.__init__  →  self.func = self._func   ← 绑定的是 _func，不是 __call__
langgraph/_internal/_runnable.py:329 (RunnableCallable.invoke)
      →  ret = self.func(*args, **kwargs)      ← 只走 _func
```

→ **子类重写 `__call__` 永远不会被执行**。LangGraph 调节点用的是 `.invoke()`，
而 `invoke` 直接调 `self.func`（= `_func`），绕开了 `__call__`。

**第二个坑（同时存在）**：
`ToolNode.__init__` 的 `handle_tool_errors` 默认值是 `_default_handle_tool_errors`，
它**只把 `ToolException` 转成 `ToolMessage(status="error")`，普通异常原样 re-raise**。
→ 所以当前代码里 `except TimeoutError` / `except Exception` 这两个分支
**就算 `__call__` 被执行了也永远不会触发**（异常早就从 `_func` 里飞出去了）。

**两个候选修法（推荐方案 1）**：

| | 方案 1：重写 `_func`（推荐） | 方案 2：重写 `invoke` |
|---|---|---|
| 写法 | `def _func(self, input, config, runtime):` | `def invoke(self, input, config=None, **kwargs):` |
| 为什么可行 | `RunnableCallable.__init__` 里 `self.func = self._func` 是**运行时按实例解析**的，子类重写的 `_func` 会被自动接住；签名保持 `(input, config, runtime)` 三个名字不变 → `func_accepts` 的 `config`/`runtime` 注入逻辑**一字不用改** | `super().invoke()` 外面套 try/except；`config=None` 由 `ensure_config()` 兜底 |
| 坑 | 参数名必须叫 `config` / `runtime`，改名会让 runtime 注入失效（报 `Missing required config key 'N/A' for 'tools'`） | 要自己处理 `config` 为 None、async 路径（`ainvoke` 不会被这个 `invoke` 覆盖，得一起写 `ainvoke`） |
| 风险 | 低 | 中（LangGraph 有可能走 async 路径） |

**改完之后的状态推导逻辑**（两处都要改）：


### 三、实施中新查实的一件事（交接单里没有）

**`super().__call__(state)` 这一行自己就会抛异常。**
langchain-core **1.4.0** 的 `Runnable` 实例层**没有** `__call__` 方法（只有一份给 IDE 看的 Protocol 声明）：

```text
Runnable         实例层有 __call__ 吗 -> False
RunnableCallable 实例层有 __call__ 吗 -> False
ToolNode         实例层有 __call__ 吗 -> False
```

→ 就算 `__call__` 真的被调用了，`status_tool_node.py:35` 的 `super().__call__(state)` 也会抛
`AttributeError`，被下面的 `except Exception` 吞掉 → 工具执行不了、状态恒为 `"error"`。
**结论：原类有 3 层问题（`__call__` 不在执行路径 / `super().__call__` 不存在 / 普通异常被 re-raise），
三层都指向"必须把逻辑挪进 `_func`"** —— 而官方钩子把这三层一次性绕开了。

### 二、**新发现：图会撞 LangGraph 的 `recursion_limit`（真 bug，已修）**

去掉兜底之后跑真实链路，**偶发** `GraphRecursionError: Recursion limit of 25 reached`。
用 `stream_mode="updates"` 抓到了完整 28 步轨迹：

```
iter tools iter tools iter synth reflect        ← 第 1 轮（reflect 判 re_iterate）
iter tools iter tools iter synth reflect        ← 第 2 轮
iter tools iter tools iter synth reflect        ← 第 3 轮
iter tools iter tools iter synth reflect        ← 第 4 轮（这里 reflect 强制 end）
```

**算账**：
- 一轮 `re_iterate` = `iter/tools` 交替最多 `2*MAX_ITER` 步 + `synth` + `reflect` = **7 步**
- `reflect` 最多被调用 **MAX_REFL+1 = 4** 次（进 reflect 时 `count=3 >= MAX_REFL=3` → 强制 end）
- 最坏 = 7 × 4 = **28 步 > LangGraph 默认 `recursion_limit=25`** → 抛 `GraphRecursionError`
- `ask()` 的 `except Exception` 吞掉 → 用户看到的是**"抱歉，agent 调用异常"**，而不是答案

**为什么之前没暴露**：旧兜底串是非空 → status 恒为 `success` → reflect 看到"检索为空"的明文 →
判 `end`，只跑 7 步。去掉兜底后素材真的空了、status 变成 `empty`，
reflect 的 critique 变成"当前并非工具超时或报错，而是检索为空，**仍应尝试扩大检索范围、更换关键词**"
→ 连判 3 次 `re_iterate` → 28 步 → 爆。**兜底串原来在替死循环挡枪。**

**两个层面的修法**：
1. **根因（prompt）**：`REFLECT_PROMPT` 的硬约束从"timeout/error 不应判 re_iterate"
   扩到 **"empty（检索为空）时同样不应判 re_iterate"** —— 同一个查询再查一遍还是空，
   素材不会凭空变出来；答案如实说明"没检索到"就够了。
2. **兜底（runtime）**：`agent/runtime.py` 显式给 `recursion_limit`，
   值从常量**推导**出来而不是写死：

   ```python
   _STEPS_PER_ROUND = 2 * MAX_ITER + 2
   RECURSION_LIMIT = _STEPS_PER_ROUND * (MAX_REFL + 1) + 10   # = 42
   ```

   这样以后调 `MAX_ITER` / `MAX_REFL` 也不会再撞默认上限。

**修后实测**：同样的问题 → 7 步结束（`iter tools iter tools iter synth reflect`），不再爆。

| 超时异常识别 | `httpx.ReadTimeout` / `grpc.FutureTimeoutError` / `openai.APITimeoutError` **没有一个**继承 builtin `TimeoutError` → 原 `except TimeoutError` 分支在真实部署里几乎不可达，全被记成 `error` |

### 二、拍板的设计（三层，职责不重叠）

```text
第 1 层  异常归一化     agent/errors.py
         AgentError / AgentTimeoutError（可重试） / AgentToolError（不可重试）
第 2 层  单次动作超时   agent/timeout.py :: Timer
第 3 层  整图总时限     state["deadline"] + is_expired()
```

- **不分内外层计时器**：RAG 检索就是工具的一种，"工具超时"一个就够。
- **deadline 放 state 不放全局变量**：state 每次 invoke 天然隔离，并发请求不串味。
- **协作式超时，不用外层包计时器**：外层包 `graph.invoke` 超时后图还在后台跑，
  而 Python 杀不掉线程 → 僵尸线程一直占着 Milvus / Ollama 连接。
  协作式是每个节点自己收手。
- **工具层自己也要有界**：`Timer` 用的也是线程，超时只能"不再等"，
  底层线程仍跑完 —— 这是 Python 的硬限制，不是设计缺陷。

### 四、顺带修掉的一个 bug（实测发现的）

**现象**：把总时限压到 1 秒跑一次，最终答案是 `"READY"`。

**根因**：`synth_node` 超时兜底从 `messages` 里倒着找"最后一条不带 `tool_calls` 的 AIMessage"，
假设"只有 synth 产的 AIMessage 不带 tool_calls"。**但 iter 节点的占位消息（`"READY"`）也不带 tool_calls**
→ 占位消息被当成答案交出去了。

**修法**：state 加一格 `last_answer: str`，synth 每写一次答案就存进去，超时兜底直接读它，不再猜。

```text
修前：answer = "READY"                            ← 占位消息泄漏
修后：answer = "回答超时：思考时间超过总时限"        ← 没有旧答案时
      answer = "<上一次写好的答案>"                 ← 有旧答案时
```

## O-006｜工具状态结构化（key 改调用 id）+ 修 `tool_calls` 悬空

| 项 | 内容 |
|---|---|
| **来源** | 2026-11-15 工业化评估（见 `工业化评估与遗留清单.md` §1 / §2 / §5） |
| **优先级** | P1（悬空那条是 O-001 多轮记忆的**引信**，必须先于它修） |
| **状态** | ✅ **已完成（2026-11-15）** |

### 背景

三件事绑在一起，都出在"工具调用状态"这一层：

1. **`tool_status` 的 key 用的是工具名**，同一轮并发调同一个工具会互相覆盖
   （实测：MiniMax 一次决策发 2 个 `rag_search`，成功那条被 timeout 冲掉）
2. **失败时 ToolMessage 塞的是中文散文**（"查询超时"），LLM 只能从散文猜语义，
   程序也没法断言
3. **`tool_calls` 悬空**：iter 最后一次决策发出的 tool_calls 永远不会被执行，
   留下一条"有 tool_calls 但没有 ToolMessage"的 AIMessage

### 拍板的设计

| 项 | 决定 | 理由 |
|---|---|---|
| `tool_status` 的 key | **调用 id**（不是工具名） | id 由模型生成、每次唯一，天然不冲突 |
| value 结构 | `{tool, status, code, retryable}` | status=结果，code=机器可读失败码，retryable=该不该重试 |
| 失败 ToolMessage 内容 | **结构化 JSON 载荷** | 给 LLM 看得更明确，也能被测试直接断言 |
| 成功 ToolMessage 内容 | **保持原始 chunks 不包装** | CLAUDE.md 约束：工具输出保持原始片段，综合交给 Agent LLM |
| `retryable` 粒度 | 目前只有 timeout=True | 更细的分类（限流 vs 代码 bug）被 `rags.py` 的 `except: return []` 堵住，要先修 A5 |
| reflect 决策语义 | **本轮不动** | 用户拍板「保守：行为不变」。reflect prompt 硬约束一字未改 |
| 悬空修法 | `iter_node` 边界判断改 `iter_count + 1 >= MAX_ITER` | 最后一轮不再调 LLM → 从根上不产生悬空；顺带省一次白跑的 LLM 调用 |

### 三、实测

```
pytest -m "not slow and not e2e" -v   → 90 passed, 13 deselected in ~8s        （0 xfailed）
pytest -m e2e -v                      → 8 passed in ~90s
pytest --collect-only                 → 103 tests collected
```

`/rag` 连打 3 次（真 Milvus + 真 MiniMax）：**3.68s → 2.29s → 1.82s**
（第一次含建连接，后两次不再重建 `RagModel`）。

**⚠️ 2026-11-17 晚间修正（把 0.45s 拆开实测后）**：
原先记的「每请求新建一条 Milvus gRPC 连接」**不准确** —— pymilvus 2.6 自带
`ConnectionManager`，按地址缓存底层 gRPC 通道，第二个 `MilvusClient` 起就是 **0.000s 复用**
（实测 `mc2._handler is mc._handler → True`）。`RagModel.__init__` 的 0.45 秒真实构成：

| 环节 | 耗时 | 能否复用 |
|---|---|---|
| `OllamaEmbeddings(...)`（内含**同步+异步两个** httpx 客户端，每个建 SSL 上下文读 CA 证书包） | **0.42s** | ✅ |
| `MilvusClient(...)` | 0.03s（第二次起 0.000s） | ✅ |
| `has_collection()` + `get_load_state()` 两次探活 RPC | 0.007s | ✅ |
| `load_dotenv()` ×2 + 读 YAML | 0.012s | ✅ |

对比：一次真正的检索只要 **0.10s** —— 也就是每请求 **~82% 的时间在做重复的准备**。
结论不变（该做成单例），但**浪费的到底是什么**说清楚了：不是 Milvus 连接，是
**embedding HTTP 客户端 + 配置读取 + 探活**。

### 四、为什么值得单独记一条

「检索失败」和「检索为空」被合并成一个 `[]`，看起来只是少了一个分支，
实际上它让**整个工具状态机制失去意义** —— Agent 拿到 `empty` 之后
只能理解成「知识库里没有」，于是拿着空素材硬答；
而真实原因可能是「Milvus 挂了」，此时正确行为是报错而不是硬答。
这类 bug 不会让程序崩，只会让答案悄悄变差 —— 属于最难发现的一类。

> **教训**：把「失败」和「空」合并成一个返回值，等于把故障信息扔在半路。
> 只要两者后续的处理动作不同，就必须是两个不同的值。

### 五、遗留

| 项 | 优先级 | 说明 |
|---|---|---|
| `retryable` 仍不能细分（限流 vs 参数错） | P2 | 前置已具备（`RetrievalError` 保留 `__cause__`），还需要 `RetrievalError` 带更细的错误码 |
| Agent 侧的 `RagModel` 还是自己的模块级单例 | P3 | `agent/tools/rag_tool.py::_ensure_rag()` 与 API 侧的 `app.state.rag_model` 是**两个实例**（各自建一套 embedding 客户端）；⚠️ 但底层 Milvus gRPC 通道是共享的（pymilvus `ConnectionManager` 按地址复用），所以不是"两条连接"，是"两套 0.42s 的客户端构造" |
| Milvus gRPC 调用本身没有显式 timeout | P3 | pymilvus 有默认超时，本次没改 |
