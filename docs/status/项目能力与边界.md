## §0 一句话结论

**RAGMI 已经是一个可以日常使用的"个人知识库问答系统"** ——
完整闭环跑通、容器化部署、112 条测试护栏、真栈全接口 19/19 通过。

**它不是玩具**（每个环节都有工程决策和回归护栏），
**但也还不是产品**（没有鉴权、没有并发验证、没有 CI、没有质量指标的自动断言）。

**当前定位**：**单人或小团队的内部知识库工具**。

## §3 明确做不到的（诚实清单）

> 每条都写"什么时候会咬人"。

| # | 做不到 | 现状 | 什么时候会咬人 |
|---|---|---|---|
| 1 | **并发** | ❌ 零数据。`/chat` `/rag` 是 `async def` 但内部同步阻塞 → 并发时占住事件循环（**P3-17**）。改它还得连带处理 `MessageManager` 无锁 | 2 个以上用户 / 同一浏览器开 2 个标签页并发提问 |
| 2 | **压力 / 容量上限** | ❌ 零数据。不知道能扛多少 QPS、哪一环先崩（容器内存？Milvus 连接数？MiniMax 限流？） | 突然来一波流量，或文档量涨 10 倍 |
| 3 | **多用户隔离** | ❌ `MessageManager.sessions` 是**进程级全局 dict**，不传 `session_id` 每次新建会话且**永不清理** | 多用户混用 → 内存单调增长；会话历史可能串（虽有 session_id 隔离机制） |
| 4 | **Agent 多轮记忆** | ❌ 无 checkpointer，`thread_id` 传了没人读；三个 LLM 节点每次从零拼 prompt | 用户追问"刚才说的那个再展开" → Agent 完全不记得上文 |
| 5 | **鉴权** | ❌ 无任何认证，CORS 放开所有源 | 只能绑本机 / 内网。**不能暴露公网** |
| 6 | **3 个占位工具** | `weather` / `web_search` 是占位实现；`calculator` 只做四则运算 | Agent 被问到需要联网/查天气的真问题时，工具返回的是假数据 |
| 7 | **检索质量保证** | ❌ 嵌入模型名对不上时**检索全是噪声但所有测试仍然全绿**（静默失败） | 有人改了 `EMBEDDING_MODEL` 或 YAML 默认值 |
| 8 | **检索精排（rerank）** | ❌ `top_k=5` 硬编码，无 rerank、无分数回传 | 知识库变大后，5 条不够，召回被稀释 |
| 9 | **多模态** | ❌ 只处理文本；PDF 靠 OCR 兜底但质量未知 | 扫描件 / 图文混排 PDF 效果差 |
| 10 | **CI / 自动化** | ❌ 仓库无 CI 配置；覆盖率**测过一次**（agent/ 91%、全项目 56%），但**没有阈值断言、没有持续集成** | 换机器 / 新人 clone 不知道跑什么；覆盖率会随改动悄悄下滑 |
| 11 | **查询改写的语义保真** | ❌ Agent 自己改写查询，**否定语义会丢** —— 实测线 A 的 B02 问「**为什么不能**直接返回空列表」，改写后「不能」没了 → 召回的片段讲"返回空列表"不讲"为什么不能返回"，该题 `retrieval_hit` **3/3 遍为 0**（而直接检索的准入检查 **10/10 全过** → 差距**只可能出在改写**） | 用户问的是"为什么不能 X"，Agent 检索到的是"X 是怎样的"，然后答非所问还答得很流畅 —— **用户看不出来** |

## §4 离"能用 / 好用 / 产品化"还差什么

### 4.1 单人日常使用 —— ✅ **现在就是**

上传文档 → 提问 → 拿到带出处的答案 → 容器一条命令起。**没有任何阻塞项。**

### 4.2 小团队内网（3–5 人）—— 还差 4 项

| # | 缺什么 | 为什么需要 | 难不难 |
|---|---|---|---|
| 1 | **鉴权**（最简单的：一个共享 token / Basic Auth） | 否则任何内网人都能读你的知识库 | 低（半天） |
| 2 | **并发验证 + 修 `/chat` `/rag` 的 `async`** | 多人同时问会互相拖死 | 中（连带 `MessageManager` 加锁） |
| 3 | **会话清理策略**（LRU / TTL） | `sessions` 只增不减，长期跑涨内存 | 低 |
| 4 | **CI**（一条 GitHub Actions 跑快回归） | 保证"改完没坏"不靠人记得跑 | 低（半天） |

### 4.3 对外服务（多用户 / 公网）—— 还差 8 项

上面 4 项 **+**：

| # | 缺什么 | 为什么需要 |
|---|---|---|
| 5 | **限流 / 配额** | MiniMax 按 token 花钱，不限流等于敞开钱包 |
| 6 | **结构化日志 + 监控**（Agent 轨迹、工具耗时、token 用量） | 现在**完全没有**：路由决策只有 prompt 里的一句话，没有结构化 trace；**工具耗时零统计、LLM 用量零统计** |
| 7 | **检索质量回归集**（人工标注问答对） | 否则嵌入模型名改错、切片参数改错都发现不了 |
| 8 | **备份 / 恢复**（Milvus 卷 + `documents/`） | 数据丢了只能重新索引（源还在 `txt/`，所以**可重建** —— 这是唯一的天然兜底） |

## §5 技术上真正的强项（已实现，可直接讲）

> 面试只讲这些 —— **全部是"做出来了"的**，不是"打算做"。

| # | 强项 | 为什么难 | 护栏 |
|---|---|---|---|
| 1 | **工具调用状态结构化**（4 态 + code + retryable，**按调用 id 而非工具名记账**） | 一轮里 MiniMax 常并发调同一工具 2–3 次；按工具名记会**静默覆盖**成功的那条 | 参数化 9 场景（原探针已退役并入 pytest） |
| 2 | **双层超时**（单次动作 / 整图 deadline）+ 一条正交的错误归一化，职责不重叠 | "不再等" ≠ "杀掉" —— Python 杀不掉线程，底层连接必须自己也有上限 | 11 条 |
| 3 | **「检索失败」≠「检索为空」** | 传统实现 `except: return []` 把两者混成一个 → 工具状态全无意义 → **超时和 bug 分不开** | 7 条 + 4 条 |
| 4 | **alias 原子切换**（重建向量库零停机，旧集合保留做回滚窗口） | 换索引不该改任何代码 | 25 分钟端到端用例 |
| 5 | **AST 白名单替掉 `eval()`** | 工具执行 LLM 传来的字符串 = 直接 RCE | 26 条 |
| 6 | **两个独立计数器 + 明确"返回 0 = 重置"的 reducer 约定** | LangGraph 默认 reducer 是**覆盖**（不是累加），覆盖语义下计数器永远停在 1、`MAX_ITER` 永不触发；纯累加型 reducer 又做不到清零；混用两个计数器会让反思条件短路 | F7 / F8 |
| 7 | **"内部占位消息"集中到常量、答案提取全量跳过** | 倒着找最后一条 AIMessage 会把 `"READY"` / `"已达迭代上限"` 当答案交出去 | F9a_x + F11 |

## §6 怎么讲这个项目（自述脚本）

> 全部基于**已实现且有护栏**的部分。

> RAGMI 是一个个人知识库问答系统。技术栈是 FastAPI + Streamlit + LangGraph，
> 检索用 Milvus，嵌入用本地 Ollama 的 bge-m3，生成用 MiniMax。
>
> **它有两条独立的时间轴**：离线是"文档 → 解析 → 切块 → 向量化 → 建时间戳集合 →
> 原子切 alias"；在线是"提问 → 检索 → 生成"。两条线唯一的交汇点是 Milvus 里的
> 一个 alias —— 这让"重建整个向量库"不需要改任何代码。
>
> **前端有三条互不相通的对话链路**：裸 LLM 直连、RAG 直连、以及 LangGraph 编排的
> ReAct Agent。
>
> **Agent 是四节点图**：iter 决策（挂工具）、tools 执行、synth 综合、reflect 反思。
> 两个独立计数器分别管工具循环和反思循环；超时分两层计时（单次动作 / 整图 deadline），
> 外加一条不计时的错误归一化线。工具调用状态按**调用 id** 记账，分成功/空/超时/错误四态，
> 失败时写结构化 JSON 载荷。
>
> **质量保证是 4 层测试共 112 条**：纯函数、Agent 流程（真图 + 假 LLM）、
> API 契约、浏览器端到端，外加真环境冒烟。每个历史缺陷都有一条回归护栏钉着 ——
> 比如 `tool_calls` 悬空、检索失败被吞成空列表、切分参数漂移、`eval()` RCE。
>
> **部署是 3 个容器**（api / web / milvus），依赖闭包全锁定 139 个包按 linux 标记求闭包，
> 踩过"镜像比代码旧导致容器静默死亡"的坑并沉淀成了检查项。
